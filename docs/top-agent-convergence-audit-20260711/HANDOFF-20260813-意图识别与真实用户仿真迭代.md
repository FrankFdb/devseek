### 2026-08-14 新增策略：带噪自然语言语义恢复

用户明确要求 DevSeek 像 Codex/Claude Code 一样理解真实输入，不要求用户每个字、格式和语法都正确。必须覆盖中文错别字、同音字、口语、省略、ASR 风格断句、中英混输以及任务中途补充/纠正要求。

源码对标结论：

- Codex `protocol/src/user_input.rs:15` 保留原始 `UserInput::Text`，其 `text_elements` 也明确不修改 literal text。
- Codex `protocol/src/models.rs:1767` 将原始文本直接作为模型 `InputText`；自然语言理解由模型承担，不存在可见的“先通用纠错、再关键词定路由”核心流程。
- Codex `core/src/session/turn_input.rs:374`、`:546` 支持把新用户输入 steering 到活跃 turn，说明后续补充和改口属于同一任务的动态合同修订。
- Codex 的 tool router、exec policy、approval 和 sandbox 与模型理解分离：模型可以猜对意思，但不能自行获得写入、删除或外部 effect 权限。
- Claude Code 核心未开源，不能声称知道其内部算法；公开 CHANGELOG 可确认实时 steering、用户显式边界和权限分类器是分离的产品能力。详细证据见 `UPSTREAM-AGENT-SOURCE-AUDIT-20260813.md`。

策略修订为“原文保真 + 模型语义恢复 + 字面量 grounding + 本地权限仲裁 + 动态合同修订 + 证据闭环”：

1. 原始输入不可变保存。新增 `OriginalInputEnvelope` 概念，携带原文、附件、turn/session id、语言提示和 protected literal spans。
2. 模型输出升级为 `SemanticIntentProposalV2`，建议字段包括：`normalized_meaning`、`correction_hypotheses`、`intent_candidates`、`protected_literals`、`ambiguities`、`confidence`、`reasoning_evidence`。纠正结果是 proposal，不覆盖原文。
3. 模型负责恢复自然语言中的错别字、同音字、语序、省略和中英混输，例如把“请吧刚才问题修好，然候跑下测试”理解为“请把刚才问题修好，然后运行测试”。不要为这些长尾输入维护关键词穷举表。
4. 路径、命令、URL、版本、hash、代码标识符和引号内文本默认不得拼写纠正。模型提出的路径/命令候选必须经过 workspace 文件、符号索引、`package.json` scripts 等真实证据 grounding。
5. 纠错不能创造权限、删除否定含义或提升 effect：`不要该源代码` 可以理解为“不要改源代码”；但不能把咨询式删除纠正成授权删除，也不能把未知路径静默替换后执行。
6. 风险分级处理：只读分析可在高置信纠正后继续并披露关键假设；普通写入必须有目标 grounding；destructive/external effect 或否定词存在歧义时必须确认或澄清。
7. 用户中途输入不是新任务孤岛。后续输入可以补充、纠正、收窄、扩大或撤销当前要求，生成 contract revision，保留来源和优先级，最新明确约束优先。
8. 多语言/关键词配置只负责高置信本地事实和安全边界，不承担通用拼写纠正，也不直接决定最终 intent。

当前实现缺口：`packages/vscode-extension/src/app/semantic-intent-interpreter.ts` 会跳过带 `web` capability 的 provider，`SemanticIntentInterpretation v1` 也没有纠正假设、受保护字面量和多候选字段。因此，当前尚未完整利用真实 DeepSeek Web 大模型处理带噪输入。后续实现必须采用 provider-agnostic semantic proposal：独立解释调用和主 agent response 的结构化语义 envelope 都要进入同一个 `TaskSemanticContract` arbiter。

### 按 Codex 源码进一步修订：从“意图预分类”转向“动作级仲裁”

重新对照本地 `openai-codex` 源码后，当前策略还需修正：Codex 的核心优势不是单独运行一个更强的 intent classifier，而是把原始输入交给主模型，在同一 turn loop 中由模型直接回答、澄清或提出工具调用；本地层针对真实 action 做逐次权限与 sandbox 仲裁。

DevSeek 当前差距：

- `semantic-route-service.ts` 先执行本地 route，再可能额外调用一次 semantic interpreter，然后重新选 workflow，存在本地分类器与主模型“双重理解”。
- `semantic-intent-interpreter.ts` 对 Web Provider 直接跳过，因此真实 DeepSeek Web 路径仍主要受本地关键词 route 控制。
- `extension.ts:408` 用关键词正则提前决定 write request/context discovery；带噪输入可能在模型看到之前走错分支。
- `permission-service.ts` 根据预判 mode 生成工具 allow/deny 集合。该策略适合作为默认最小权限提示，但不能代替对模型实际 action 的 descriptor/effect/target/risk 仲裁。
- 好的基础已经存在：`AgentToolExecutor.plan()` 会把实际工具调用转换为 action descriptor，并计算 effect、risk、protected path 和 permission；canonical executor/authority receipt 可作为统一执行权威。

后续目标结构改为：

1. 原始输入和 steering 进入 turn-scoped input store，原文不被纠错结果覆盖。
2. 主 agent 模型读取原始输入、上下文和当前合同，直接输出回答、澄清或 action proposal；semantic proposal 是同一模型理解的附属结构，不是独立路由权威。
3. `TaskSemanticContract` 收敛为 constraint contract：保存 no-write/no-run、目标 scope、protected literals、approval mode、completion obligations 和 revision，不把 task kind 当作权限令牌。
4. 每个真实 action 在执行前统一经过 `ActionAuthorityArbiter`，根据 action descriptor、effects、target、risk、sandbox、最新 contract revision 决定 `allow/confirm/deny`。
5. 工具结果回灌模型，统一 evidence tracker 维护 net diff、readback、命令输出、测试和 external-effect receipt，再由 completion contract 判定结束。
6. 用户后续改口会产生新 revision；尚未执行的旧 authority receipt 立即失效，避免模型按过期意图继续写入或运行。

组件决策：

- 保留：`TaskSemanticContract` 中的确定性约束、`AgentToolExecutor`、canonical executor、authority receipt、文件/终端 permission coordinator 和 evidence store。
- 降级：`ChatIntentDecision.mode`、`SemanticIntentInterpretation.taskKind`、learned intent 只用于 UI、上下文准备和默认 workflow，不再直接授予执行权限。
- 重构：`resolveSemanticRouteDecision()` 优先消费主模型首轮的 semantic/action envelope；独立 semantic intent 调用只作为 provider 不支持结构化主响应时的辅助 fallback。
- 收敛：所有会影响权限、上下文正确性和完成判定的关键词快捷路径迁入 shared semantic/action owner。配置 lexicon 继续存在，但只提供高置信事实和安全 veto。

这使最终方案从“关键词提取 + LLM 分类 + 本地路由”进一步优化为“原始 turn 输入 + 主模型理解/动作提案 + 本地 constraint/action 仲裁 + 工具观察循环 + evidence 完成合同”，与 Codex 公开实现更加一致。

新增仿真要求：

- 建立 clean/noisy metamorphic pairs：规范输入与带噪同义输入必须得到等价的 task kind、mutation、effect 和 completion contract。
- 覆盖中文同音/错字：`吧/把`、`在/再`、`原/源`、`该/改`，以及乱序、少标点和口语表达。
- 覆盖 advisory/direct 对偶：`应该删出 dist/cache 吗` 必须只读；`请删出 dist/cache` 必须进入 destructive confirmation。
- 覆盖外部 effect：`吧这些改动提交并推送` 应恢复为 commit/push 请求并进入确认。
- 覆盖 literal protection：`src/logim.ts`、`npm tset` 只能在 workspace/script 证据支持时建立候选映射，不能静默改写执行。
- 覆盖否定与权限反例：带噪的“不要修改”“先别运行”“不要 push”必须保持 veto；纠错不得把 advice 变成 authorization。
- 覆盖多轮 steering：先要求修复，随后说“刚才说错了，只分析，不要改”，最终合同必须撤销写权限。
- 在 top-agent runner 增加 required case `noisy-multilingual-intent-recovery`；与 `destructive-external-advice-boundary` 一起完成时，required case 应由 `49` 增至 `51`。

## 意图识别对策

当前不能继续依赖“关键词命中即判定”的方式。对标 Codex/Claude Code 的可观察行为，DevSeek 应采用“模型语义理解 + 本地契约仲裁 + 证据闭环”的分层方案。

推荐架构：

1. **确定性提取层**
   - 只提取高置信事实：显式路径、文件类型、禁止项、用户指定命令、产物路径、是否要求测试。
   - 不直接决定最终任务类型。
   - 对自然语言中的斜杠词、版本号、URL、命令片段做上下文过滤。

2. **LLM 语义候选层**
   - 让模型把用户输入解析成结构化候选，不让模型直接授权写入。
   - 输出字段建议包括：`intent`、`mutation_kind`、`deliverable_kind`、`target_paths`、`constraints`、`verification_need`、`ambiguities`、`confidence`、`reasoning_evidence`。
   - 允许多候选，例如“分析并生成报告”同时包含 read/analyze/report artifact，不应被折叠成 pure review。

3. **Canonical Task Contract 仲裁层**
   - 由本地 shared owner 融合确定性提取、LLM 候选、workspace 状态、session 记忆和实时用户 steering。
   - 写入、运行、外部 effect 必须由本地合同裁决。
   - 规则要按作用域解释：`不要修改源码` 不等于 `不要创建报告文件`；`不要创建任何文件` 才是全局写入撤销。

4. **执行与完成证据层**
   - 每种任务建立自己的完成合同。
   - 代码修改任务需要 diff、测试/编译或明确跳过原因。
   - 报告类任务需要文件写盘、readback、关键锚点/章节/用户要求覆盖，不应强制终端验证。
   - provider 没有显式 `task_complete` 时，如果本地证据已经满足合同，应允许 agentic loop 形成受控完成总结，避免继续循环调用工具。

5. **低置信澄清层**
   - 当用户输入确实含糊，例如“处理一下这个问题”，DevSeek 应问一个短问题。
   - 当用户给出可执行目标和边界时，不应反复追问。

## DeepSeek Web 兼容策略

真实入口是免费 DeepSeek 网页，必须兼容网页回复不稳定：

- DeepSeek 可能返回混合自然语言、Markdown、代码块、JSON-like 工具调用、半截工具调用。
- 解析器要容错，但不能无限重试。
- prompt 应要求模型用稳定工具协议返回；本地仍必须能处理偏离协议的回复。
- 工具调用失败后要有有界重试和错误分类；相同失败不能反复执行。
- 当报告文件已经满足合同，不应因为 provider 又输出 `ls/head/grep` 之类只读命令而重新进入大循环。
- Debug 版本测试必须记录 DeepSeek 网页原始反馈摘要、解析结果、工具执行、合同状态、缺失证据和终止原因。
