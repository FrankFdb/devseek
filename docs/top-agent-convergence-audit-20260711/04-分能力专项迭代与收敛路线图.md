# DevSeek 分能力专项迭代与收敛路线图

- 日期：2026-07-11
- 目标：每项编程智能体能力单独对标、达到顶级门槛，同时保持一个端到端内核
- 接管定位：C0～C14 capability program 与成熟度规范；GPT-5.5 不直接领取宽能力组，只领取 14 的 leaf

## 1. 路线原则

用户提出的意图、需求、设计、实现、编译测试、发布是重要能力，但顶级编程智能体还包括项目指令、上下文、工具协议、权限沙箱、mutation、验证修复、完成事实、恢复、记忆、扩展、多 Surface 和资格评测。

因此采用“**能力专项 + 纵向黄金旅程**”双轨迭代：

- 每个能力有唯一 owner、专项 fixture、指标和晋级证据，单独做到极致。
- 从第一天持续运行少量端到端黄金旅程，提前发现相邻能力接口错误。
- 不为某项能力创建平行 Agent Loop；所有能力接入同一 `AgentKernel`。
- P0/P1 能力未达到 Surface 资格前，不进入最终正式项目 holdout。
- 每迁移一个能力必须删除一个旧 owner，不能长期双写或 fallback。

## 2. 能力晋级阶梯

| 等级 | 定义 | 不足以证明什么 |
| --- | --- | --- |
| L0 `specified` | 契约、owner、输入输出、失败语义和指标已定义 | 不证明代码存在 |
| L1 `implemented` | 实现和单元测试存在 | 不证明进入产品路径 |
| L2 `deterministic-qualified` | fixture、属性测试、故障注入通过 | 不证明真实 Surface/Provider |
| L3 `runtime-qualified` | Headless 同一 Kernel 完成端到端任务 | 不证明 IDE/CLI 适配正确 |
| L4 `surface-qualified` | VS Code 与 CLI 真实入口通过同一 conformance suite | 不证明 live 模型在开放任务稳定 |
| L5 `live-qualified` | 冻结 commit、真实 Provider、唯一 case id 配额通过 | 不证明已领先竞品 |
| L6 `top-tier-qualified` | holdout 上与 Codex/Claude 同题盲评无 veto，可靠性、非劣和置信门槛达标 | 只对已测能力、版本和 applicability 成立 |

文档中的“完成”必须附带等级、commit、case id、Surface、Provider、证据链接和有效期。没有这些字段只能写“已设计”或“已有实现”。

## 3. 四条横向红线

每个专项都必须同时满足：

1. **多 Surface 一致性**：Headless、VS Code、CLI 共享领域行为，Surface 只适配输入输出。
2. **安全与隐私**：权限最小化、外部内容低信任、敏感信息不进日志、所有副作用可审计。
3. **跨平台与 Provider 可替换**：平台/模型方言只留在 Adapter，Core 不含厂商或 shell 特判。
4. **性能、成本与可观测性**：记录 token、工具次数、延迟、重试、失败阶段和证据大小，优化不能牺牲正确性。

## 4. C0：运行证据、能力账本与评测地基

**目标**：先让“完成”可证明，否则后续每项能力都会重复争论。

- 建立 product `Run Evidence Ledger`、machine-readable capability ledger、golden journey catalog、failure taxonomy 和 qualification evidence manifest；Kernel 不得反向依赖 case/oracle/L 级。
- 每个 case 使用稳定且唯一的 `caseId`，同 case 重跑不能凑配额。
- 绑定 commit、构建、VSIX、installed version、Surface、Provider 和 workspace fixture。
- Gate 区分 static、unit、deterministic、runtime、surface、live、holdout。

顶级退出指标：derived 状态不接受手工输入；CI 验证 manifest/schema/signature，对证据篡改可审计发现；报告由 ledger/manifest 生成；当前 commit 的资格可复算。

## 5. C1：统一控制内核、状态与完成事实

**对标重点**：Codex/Claude 公开行为都表现为工具观察驱动的持续反馈循环，而非由附件切换完成语义。

2026-07-11 初始缺陷：VS Code 两个 Loop、CLI 一个 Loop；Shared Application Service 主要只路由 Provider Chat；terminal status 和事件名不完全一致。

专项工作：

1. 定义 `start(TaskRequest)` / `dispatch(runId, AgentCommand)`、typed transitions 和唯一 `SettlementService/CompletionDecision`；`TaskContract` 在运行中可按用户决定修订。
2. 接入 Headless，再以 adapter 接入 VS Code/CLI。
3. 将附件降为 `ContextSource`；simple/formal 只改变阶段展开和预算。
4. 统一 run status；`waiting-user` 是可恢复非终态，终态只有 `completed/failed/blocked/cancelled`。
5. 删除 Surface 业务分流和旧 Loop 终态 owner。

2026-08-10 本地进度：三 Surface 产品路由已经进入同一 canonical Kernel；Runtime 只返回结果与 completion evidence，shared Completion authority 唯一派生终态并与 lifecycle 结算。验证会话绑定当前 run 与精确 acceptance，跨 run/替换契约证据在 host 前拒绝；较早失败只能由同 run、更新序列、完整 scope 与 acceptance 覆盖的 passed receipt 在 shared owner 内解除。旧 Headless completion adapter 已删除，v27 机器基线 123/123 通过。该结论完成 `C1-SETTLEMENT` 的强化接线，不代表后续 C9/C10 或资格完成。

专项 fixture：同一 create/modify/failing-test 请求分别在无附件、有附件、CLI、VS Code 运行，领域事件序列和终态必须等价。

顶级退出指标：产品 Coding Kernel 数量 `=1`；Completion owner `=1`；附件导致的语义偏差 `=0`。

## 6. C2：任务定向、意图与模式识别

**对标重点**：结合会话、项目事实和观察动态判断解释、审查、修改、运行或发布；高影响歧义才询问。

当前缺陷：Intent、Router、Workflow、Decomposer、TaskContract 多处解释任务，关键词和附件影响路由。

专项工作：

- 建立一个 `OrientationDecision`：目标、模式、风险、置信度、依据、需要澄清的问题。
- 以对话、repo 状态、指令链和可观察事实为输入，不以领域词表替代语义。
- 支持新证据触发 re-orient，但保留 revision lineage。
- 将“只回答”与“执行副作用”授权明确分开。

专项 fixture：含糊命令、否定约束、中途补充、附件有无、脏工作区、混合中英文、错误文件指向、发布词但无授权。

顶级退出指标：高风险误执行 `=0`；低风险不必要追问率可控；执行后契约实质翻转率持续下降；跨 Surface 决策一致。

## 7. C3：工程定向、代码库探索、上下文与指令

**对标重点**：分层项目指令、按需搜索、诊断和代码智能；上下文相关、可追踪、可压缩。

当前缺陷：Engineering Context 实现未接 Runtime；VS Code/CLI 探索能力不等价；semantic search 名称与实际能力不符。

专项工作：

- `ContextBroker` 汇聚 AGENTS/CLAUDE 指令、workspace、附件、Git、构建、诊断、外部来源和 memory。
- 指令按来源、目录作用域、优先级和冲突规则编译。
- 搜索策略从便宜到昂贵：文件/文本 → symbol/reference → diagnostics → 外部资料。
- 记录“为什么读取此上下文”和引用位置；压缩保留决策与证据，不保留无关噪声。

专项 fixture：monorepo、嵌套规则、生成目录、同名符号、跨语言调用、长会话、错误附件、项目规则冲突。

顶级退出指标：相关事实召回率、规则遵守率和影响范围命中率达到 profile 门槛；无关上下文、重复读取、无来源假设低于预注册上限。

## 8. C4：需求分析、验收与外部边界

**对标重点**：把用户目标、既有项目、外部接口和验收条件转成可追踪契约；按需读取官方资料/MCP，不臆测版本敏感事实。

2026-07-11 基线缺陷：TaskContract 未成为唯一契约，部分正式工程规则混有特定领域关键词，外部证据未统一进入需求阶段。

专项工作：

- 由 `RequirementDecisionPort` 统一输出 functional、quality、constraint、non-goal、source、confidence 和不可变 revision lineage。
- 由 `ExternalBoundaryPort` / `SourceGroundingPort` 识别外部系统、API 版本、运行环境、法律/许可证、部署和数据边界，并把来源精确绑定到 boundary、locator、内容摘要及 tool/effect evidence。
- 由 `AcceptanceContractPort` 将每项 acceptance 绑定 deliverable、verifier、scope、evidence kind 和 external boundary；主观 oracle、来源缺失、来源冲突或重要未确认假设 fail closed。
- 需求 revision 与设计、计划、测试、完成证据双向追踪；发现新证据时扩展同一 revision owner，不建立 Surface 本地契约。

2026-08-07 本地进度：C4 四项 capability 已由 shared Kernel 接入 VS Code、CLI、Headless，旧 VS Code `requirement-contract.ts` 及其专属测试已删除；I15 对非目标、外部来源精确归属、弱 oracle 和 revision lineage 做了独立用户仿真。当前仍需把实时 Web/MCP/Provider 来源获取、clarification/steer 和外部新证据驱动的 requirement/design revision 接入反馈循环，并用正式项目 profile 验证退出指标；因此只记 `wired`，不产生 qualification claim。

专项 fixture：已有项目增量需求、版本敏感 API、模糊验收、互相冲突说明、不可访问外部资源、领域陌生任务。

顶级退出指标：目标遗漏率、不可验证需求比例、无来源关键假设低于 profile 上限；正式任务 100% acceptance 可追踪。

## 9. C5：软件设计、影响分析与计划

**对标重点**：复杂任务先探索再规划，计划可审阅、可因新证据调整；实现符合项目责任边界。

2026-07-11 基线缺陷：Architect+Editor 受附件路由影响；设计原则主要停留在 prompt/文档，缺少可执行依赖约束。

专项工作：

- 由 `DesignDecisionPort` 输出 `DesignDecision`、备选方案、trade-off 和 `ImpactSet`；由 `ChangePlanPort` 输出 migration/deletion/rollback、dependency checks 与 acceptance mapping。
- 简单任务生成最小设计；跨模块/高风险任务显式计划并允许用户 review。
- 设计阶段只读，发现证据不足返回探索；实现偏离必须创建 plan revision。
- 将 dependency direction、owner 和禁止旁路转成静态 architecture tests。

2026-08-07 本地进度：C5 两项 capability 已由 shared Kernel 生成并随产品输出/session context 进入三 Surface，低层工具 authority 必须消费当前 plan 并拒绝越界 target/effect；I15 覆盖影响集、回退、验收映射和越权拒绝，I16 证明自然多文件任务中的工具目标可在副作用前形成 evidence-bound plan revision，严格范围、glob 与 workspace 边界仍 fail closed。当前仍需将用户可审阅 plan、clarification/steer 和外部新证据驱动的 requirement/design revision 接入完整状态机，并补齐跨语言影响图与正式项目资格；不得恢复附件驱动的 Architect 平行路径。

专项 fixture：单文件修复、跨包 API 变更、兼容迁移、性能/安全权衡、用户方案与仓库原则冲突。

顶级退出指标：独立 review 的重大设计缺陷率、实现中返工率和任务外 diff 持续下降；所有高风险改动有回退路径。

## 10. C6：Provider、工具协议与执行

**对标重点**：Core 只消费结构化工具调用，工具结果作为观察反馈；Provider 和扩展方言被隔离。

当前缺陷：Extension 与 CLI 分别解析 JSON/XML/diff，工具 dispatch 分散，大型 parser 进入 Core。

专项工作：

- Provider Adapter 负责方言 → `ToolCall`，Core 不解析模型自由文本协议。
- 统一 ToolRegistry、schema validation、ToolExecutor、timeout、retry、idempotency 和 result envelope。
- 区分工具失败、策略拒绝、用户拒绝、平台失败和无效模型输出。
- 捕获真实 Provider trace 做脱敏 replay，减少 live 配额消耗。
- 把 DeepSeek Web auth/session、DOM/page fingerprint、request↔stream correlation、reconnect/cancel/dedup、rate-limit/backoff 做成独立 `C6-DEEPSEEK-WEB-CONNECTOR`，不让 connector 可靠性被 Provider normalization 大项吞掉。

专项 fixture：缺字段、重复 tool call、半截 streaming、Provider 重连、工具超时、大输出、恶意工具结果、跨 Provider 同任务。

顶级退出指标：Core Provider 方言类型 `=0`；工具 dispatcher owner `=1`；重复副作用 `=0`；错误分类准确。

## 11. C7：权限、沙箱与 mutation 事务

**对标重点**：Codex 公开区分 sandbox 与 approval；Claude 工具、Hooks、MCP 也处在明确权限边界。权限必须是运行时强制边界。

当前缺陷：新 CAS/atomic commit 主要只接 Markdown；旧 write/delete/mkdir 仍可旁路；MCP 和 CLI 不共享 PermissionKernel。

专项工作：

- 统一文件、终端、网络、MCP、Git、发布权限域和 risk policy。
- 所有 write/edit/delete/mkdir/move/undo 迁移到 `WorkspaceMutationTransactionService`；一次 run 使用多个短事务和 saga/checkpoint，不持有跨用户等待的长事务。
- baseline、CAS、atomic commit、readback、commit token、rollback、用户脏改保护成为强制协议。
- OS/platform sandbox 与用户 approval 分层，默认最小权限。

专项 fixture：用户同时修改、symlink/path traversal、权限拒绝、重复恢复、部分写入、进程越界、MCP 高风险调用、undo。

顶级退出指标：mutation 旁路 `=0`；未授权副作用 `=0`；验证隐藏写入 `=0`；冲突时用户改动丢失 `=0`。

## 12. C8：代码实现与集成质量

**对标重点**：理解现有实现后做最小完整修改，遵守项目风格和责任边界，避免只修截图路径。

当前缺陷：多个专用 task/executor 产生不同实现策略；新增能力常通过大文件和领域特判叠加。

专项工作：

- 执行计划按小步 mutation + readback + diagnostics 运行。
- 修改前审计 sibling entry points、状态流、协议边界和恢复路径。
- 将重复语义收口为一个 abstraction，并同步增加回归和架构守卫。
- 建立 diff scope、complexity delta、duplication/owner delta 指标。

专项 fixture：简单创建、局部修改、跨文件接口、重构、依赖升级、代码生成约束、已有用户改动。

顶级退出指标：任务外 diff、重复实现、回退缺陷、用户改动覆盖为零；改动符合 architecture tests。

## 13. C9：构建、验证、诊断与有界修复

**对标重点**：提供可运行 verifier，使用测试/构建/截图等证据；失败进入下一轮，而非自报完成。

2026-07-11 初始缺陷：VS Code/CLI 两套 verifier 和 repair；无 verifier 可默认成功；验证阶段存在修改文件的实现。

专项工作：

- 从 Engineering Context 和 acceptance 生成 `VerificationPlan`。
- 区分 compile/type/lint/unit/integration/e2e/package/runtime/artifact checks。
- Verification 对用户源码/交付物只读；构建临时产物进入声明目录。失败生成 Diagnosis，按根因返回 requirements/design/implementation。
- 修复预算按风险、进展和重复失败决定，不写死“最多两轮”。
- 独立 verifier 或 hook 检查 completion evidence。

2026-08-10 本地进度：C1 已提供 run-bound `VerificationPort` 会话和唯一 Completion/Settlement 消费边界，三 Surface canonical 产品路径不能以自报 completed、外来 run 回执或替换 acceptance 绕过它；I17 五个独立用户场景已验证上述反例及 repair 后重验证。这里仅建立了 C9 的协议地基：ledger 中 `C9-INDEPENDENT-VERIFICATION` 仍保持 `proposed`，因为它要求的 `C9-VERIFIER-SELECTION` 与 `C9-BUILD-ORCHESTRATION` 尚未 `wired`；diagnostic normalization、bounded repair、regression selection 和跨项目 verifier 发现也仍未完成。

专项 fixture：编译错误、陈旧制品、flaky test、测试命令缺失、测试通过但行为错、错误修复引入回归、无限失败循环。

顶级退出指标：假成功 `=0`；无 verifier 标为 unverified；同一失败重复无进展时诚实 blocked；验证覆盖所有 acceptance。

## 14. C10：独立审查、Git、交付与发布

**对标重点**：基于 diff、验证和风险交付；commit/CI/release 是条件能力且需用户授权。

当前缺陷：review/PR 辅助多为纯函数或测试；DevSeek 自身有 VSIX 发布链，但用户项目没有通用发布状态机。

专项工作：

- Reviewer 使用独立上下文，从契约、diff、测试和风险做 veto 判定。
- 交付 manifest 说明修改、证据、未验证项、残余风险和后续任务。
- Git commit、PR、CI、artifact、部署、smoke、观测、rollback 作为授权后的可选子流程。
- 制品绑定 source commit、build id、checksum 和 installed version。

专项 fixture：测试通过但越界、安全回归、脏工作区、部分 staged、CI 失败、制品版本错配、部署后回退。

顶级退出指标：重大 review 漏检趋近零；未经授权外部提交/发布 `=0`；source→artifact→installed identity 可追溯。

## 15. C11：用户协作、中断、恢复与幂等

**对标重点**：用户可 steer/取消，长任务能从结构化事实恢复，不重复副作用。

当前进展与缺口：`C11-CHECKPOINT` 已由 shared owner 接入 VS Code/Headless；`C11-RESUME-IDEMPOTENCY` 已实现稳定 effect key、completed skip、indeterminate block、failed-no-effect retry 与防篡改回执，但 C7 workspace/external effect authority 尚未提供真实产品回执，因此仍为 `implemented` 而非 `wired`。cancel、steer、用户协作、Surface 可达性和 background automation 仍待后续专项。

专项工作：

- checkpoint 保存 task revision、state、plan、evidence、receipts、未决 decision 和 workspace baseline。
- 建立 `C11-USER-COLLABORATION` 与 `C11-SURFACE-ACCESSIBILITY` 原子能力：必要澄清、可理解进度、计划/diff 审批、steer/cancel 回执、错误说明、键盘与辅助功能可达。
- resume 先检查工作区漂移和已提交 receipt，再继续或 replan。
- steer 创建新契约/计划 revision；cancel 先持久化 cancelling 与 in-flight 集、冻结新 effect，再 reconcile/compensate 并由 Settlement 写终态，不能把取消当瞬时 flag。
- crash、Provider disconnect、窗口切换、版本升级均有恢复策略。
- C11 profile 必须给 `D-G08-CANCEL` 与 `D-G08-RESUME` 各建独立 coverage slot：前者验证 cancellation saga 且终态拒绝 resume，后者只从非终态 interruption/crash 恢复；二者不得串成一个 run 或互相代替。

专项 fixture：mutation 前/中/后崩溃、用户中途修改、新窗口接管、权限等待、重复 resume、版本不兼容 checkpoint。

顶级退出指标：重复副作用和用户修改覆盖 `=0`；恢复后契约/事实一致；取消有可观测回执且不再产生副作用；关键状态不靠视觉颜色单独表达；无法安全恢复时明确 blocked。

## 16. C12：长上下文、记忆与证据治理

**对标重点**：分层项目规则和按需上下文；子任务隔离噪声；压缩不丢关键决策。

当前进展与缺口：`C12-MEMORY-POLICY`、`C12-RUN-EVIDENCE-RETENTION`、`C12-CONTEXT-COMPACTION` 已全部 `wired`。规范压缩收据保留 TaskContract、ContextGraph 来源、MemoryPolicy、完成前缀、待办、证据引用、父收据和重验证要求，并在 VS Code 活跃 agentic 路径负责预算触发；子任务隔离、跨进程长期压力与后续 C13 扩展组合仍需独立验收。

专项工作：

- 区分 instructions、workspace facts、task memory、user preference、ephemeral observations。
- 所有长期记忆有来源、作用域、有效期和撤销方式。
- compaction 保留契约 revision、决策、失败、receipts、未决风险和引用。
- 防止外部内容通过 memory 提升为指令。

顶级退出指标：长会话规则/目标漂移为零；过时记忆误用和敏感信息泄漏为零；上下文成本可控。

## 17. C13：Skills、Hooks、MCP、Subagents 与工作树

**对标重点**：逐项使用竞品已公开的对应机制作参考：Codex 公开 Skills 和 Subagents；Claude Code 公开 Hooks、Subagents 和 memory/instructions。不把一方的能力外推为另一方也具有，MCP/worktree 也只按各自可核实的公开资料对标。这些扩展提升规模和复用，但不得绕过主 harness。

当前缺陷：Skills/Hooks/Subagents 多为 descriptor 或 planner 壳；MCP 能调用但权限未接通。

专项工作：

- Skills 渐进发现、显式输入输出、版本和 verifier。
- Hooks 绑定 typed lifecycle event，定义 veto/warning/evidence。
- MCP 经统一 registry、permission、timeout、audit、low-trust result。
- Subagent 具有 `TaskSlice`、独立上下文/工具/权限、owned paths 和 evidence contract；写任务用独立 worktree 或互斥路径。
- 若产品提供 Plugin/marketplace，必须单独实现签名、来源、权限清单、安装/更新/卸载/撤销和 supply-chain evidence；不能把“目录能加载”当插件安全。
- Peer agent team、background automation、visual computer use、headless SDK/cloud 各有独立 conditional/deferred profile；不为功能对称强塞进 core-coding，也不在开始宣称后继续 N/A。

顶级退出指标：所有扩展调用可追踪至主 run；无权限旁路；并行写冲突 `=0`；子 Agent 无权宣布主任务完成。

## 18. C14：正式项目与顶级资格

C14 不是新的实现能力，而是对原子能力的组合验收。本文不再复制一套进入条件；唯一口径是 [05 第 10 节的正式晋级协议](05-黄金用户旅程与正式项目资格方案.md#10-唯一正式晋级协议)。06 是治理设计规范；machine-readable capability/profile 实例是 `docs/process/devseek-capability-ledger.json` 与 `docs/process/devseek-milestone-profiles.json`。

两个名称不得混淆：

- `RC smoke` 用少量冻结候选 live case 阻断明显回退，`3 canary + 2 medium + 1 formal` 只属于这一层。
- `L6 top-tier-qualified` 需要更大的 sealed holdout、成对盲评、预注册非劣界/置信要求和无 veto，不能由 3/2/1 推导。

正式方法见 [`05-黄金用户旅程与正式项目资格方案.md`](05-黄金用户旅程与正式项目资格方案.md)。

## 19. 可计算指标与最小样本契约

各 C 节的“持续下降、趋近零、成本可控”只是目标说明，**不能作为晋级判据**。每个原子 capability 的 Qualification Profile 必须冻结：`metric_id/formula/direction`、corpus id/version/hash、适用 strata、最小 N、阈值、hard veto、置信方法、runner/toolchain 和 TTL。没有这些字段只能停在 L0。

统一公式：`rate = 满足 oracle 的唯一 execution / 全部预注册且可判定 execution`；不能删分母，infra-invalid 单列并受 [05 第 7.4 节](05-黄金用户旅程与正式项目资格方案.md) 上限约束。普通比例默认报告点估计与预注册的单侧 95% 区间；相关 variants 按 task-family cluster 计算，不能假装独立。零容忍表示观察数必须为 0 且达到最小 N，并不外推为数学上的永不发生。power analysis 只能上调 N，不能观察结果后降低阈值。

下表是 profile 的**最低种子门槛**；每个原子 id 仍需独立行和 evidence，不能用领域平均数让失败原子晋级：

| 能力域 / 适用原子 | versioned corpus 与最小 N | 规范指标与最低阈值 | hard veto / 置信与有效期 |
| --- | --- | --- | --- |
| C0 ledger/catalog/evidence/aggregator | schema mutation corpus 全字段 + 1000 个生成事件序列 | schema、dependency、hash-chain、聚合复算 `100%`；同 key 重复计数 `0` | 篡改未检出、失败被覆盖即 veto；hash 变化立即失效 |

| C7 permission/sandbox/mutation/platform | path/effect/fault sequence `N>=1000`；每声明平台至少 100 个 conformance 序列 | 未授权 effect、path escape、丢用户改动、mutation bypass、source hidden write 均 `0` | 任一项即 veto；平台分别出结论，OS/adapter/hash 变化失效 |

每次报告必须同时列 `N planned/started/valid/infra-invalid/pass/fail/veto`、点估计、区间、corpus/profile hash 和到期时间。安全零容忍项不因总分或竞品也失败而豁免；效率指标只有在正确性/安全硬门禁通过后才可优化。

## 20. 实施里程碑与能力依赖

为了减少打包、live 和正式项目迭代，产品候选只设四个收敛里程碑；里程碑内部仍按原子能力依赖过门禁，不把多项能力混成一个“整体完成”。

| 候选里程碑 | 内部门禁 | 主能力 | 必须交付 |
| --- | --- | --- | --- |
| R1 基础 Coding Kernel | Gate 0 可测量 | root target：`C0-QUALIFICATION-AGGREGATOR`；Gate profile 最低 wired/L2 | product Run Evidence Ledger、capability ledger、signed plan/catalog、append-only attempt/manifest、旧宣称降级 |
| R1 基础 Coding Kernel | Gate 1 最薄单内核纵切 | root targets：`C1-SURFACE-ADAPTER-CONFORMANCE`、`C6-PROVIDER-NORMALIZATION`、`C6-DEEPSEEK-WEB-CONNECTOR`、`C7-DIRTY-WORKTREE`、`C7-PLATFORM-ADAPTER-CONFORMANCE`、`C8-INTEGRATION-CONFORMANCE`、`C9-BOUNDED-REPAIR`、`C9-REGRESSION-SELECTION`、`C10-DELIVERY-MANIFEST`；roots 最低 wired/L2，C2～C5 依赖只用 `r1-minimal-contract` wired/L1 | D-G01～D-G04 切换 smoke；统一状态、权限、mutation、verification、review、completion；不声称 L4 |
| R2 软件工程大脑 | Gate 2 只读工程脑 | root targets：`C3-INSTRUCTION-PRECEDENCE`、`C4-SOURCE-GROUNDING`、`C5-DESIGN-DECISION`；完整 C2～C5 profile 目标 L4 | intent、contract、context、requirements、design 全 corpus 晋级，D-G00/D-G05/D-G06/D-G09 |
| R2 软件工程大脑 | Gate 3 完整行动闭环 | root targets：`C6-CAPABILITY-NEGOTIATION`、`C8-INTEGRATION-CONFORMANCE`、`C9-REGRESSION-SELECTION`、`C10-DELIVERY-MANIFEST`；从 R1 L2 smoke 深化到完整 L4 profile | Provider/tool 收口、全部副作用迁移、build/diagnose/repair/review，旧 Loop 删除 |
| R3 可靠性与规模 | Gate 4 可靠交付 | root targets：`C10-ROLLBACK`（release profile）、`C11-SURFACE-ACCESSIBILITY`、`C11-RESUME-IDEMPOTENCY`、`C12-MEMORY-POLICY`、`C12-CONTEXT-COMPACTION`；automation 按 scope | delivery、resume/steer/cancel、Surface UX、memory/compaction |
| R3 可靠性与规模 | Gate 5 可控扩展 | root target：`C13-EXTENSION-CONFORMANCE`；Plugin/peer team/headless SDK 为独立 conditional root | 每个扩展独立晋级，不增加第二内核 |
| R4 冻结资格 | Gate 6 RC 与顶级资格 | root target：`C14-RELEASE-DECISION` | same-trace natural UI × real DeepSeek、RC smoke、sealed holdout、成对盲评；按 qualification profile 选择性做发布/恢复演练 |

表中只维护 root targets 和目标级别；实际 work package 由 06 的 typed architecture edge + Qualification/Milestone Profile 自动展开。机器生成物必须对每个节点冻结 `requirements[]{required_implementation_state,required_claim{profile_id,profile_sha256,claim_scope,surface,provider,platform_profile,minimum_level}} + work_mode(root|seam)`，并逐条保留不可排序的 `required_by/relation/contract_sha256`。`required_implementation_state_view` 只能是非权威汇总视图；真正裁决以每个精确 tuple 对应的 state/level 为准。同一精确 tuple 的多路径要求分别取最严 state 和 level，不同作用域必须保留为不同 `requirements[]` 元素；每条 `selection_path` 也保存自己的完整 `required_claim` 和有效 state。纯 ID topology 闭包不能当 work manifest；当前种子的 Gate 0+1 纯拓扑闭包会触及 45/76 项，正因如此，R1 必须把 C2～C5 明确标为 `seam: wired/L1`，而不是把 45 项都宣称 L4。Gate 2 再用完整 corpus/profile 提升 C2～C5，Gate 3 再把 R1 的 C6/C8/C9/C10 smoke 提升到 L4，因而不是重复工作。

生成 manifest 还必须验证 missing-id/cycle/applicability/profile completeness，禁止手抄一长串依赖后逐渐漂移。这不是等 R3 才第一次做端到端测试。每个 Gate 都运行受影响的已公开 development journeys；sealed holdout 从不进入日常回归。测试选择由 capability dependency/impact hash 计算，不是无条件“每次全跑”。

R1 的 Slice 只能在**同一未发布迁移分支/候选**内递进，Slice 之间不打包给用户、不安装为日常版、不宣称产品闭环。允许临时 legacy adapter 的唯一条件是：它只做无业务语义的 delegator，不得构造另一终态、不得双写、不得执行 mutation。R1 对外发布前，所有声明的 product entrypoints 必须通过 reachability/conformance，相关旧 semantic owner 总数必须 `=0`；禁止上线两个 Kernel 再慢慢收口。

四个里程碑以 [`08-决策结论与最短收敛实施方案.md`](08-决策结论与最短收敛实施方案.md) 为总路线；截至 2026-07-12，G0-A/B/C/D 均已形成各自本地实现纵切，但所有相关 capability 仍是空 claim、level view `null`，也没有 live。G0-C 的本地 Manifest/独立复算完成不等于 Gate 0：真实 runner 全入口、独立 protected trust/retention、冻结 candidate 与逐 tuple `wired/L2` 仍待闭合。实施与非资格边界见 [13](archive/13-G0-C资格证据清单与独立聚合协议实施报告.md)、[12](archive/12-G0-D统一运行证据账本实施报告.md)、[11](archive/11-G0-B签名资格协议实施报告.md) 与 [10](archive/10-G0-A机器能力账本实施与迭代计划.md)。Gate 0 通过前，R1 任何 Slice 都不得开始。

## 21. 单项迭代标准作业

每项能力严格执行：

1. **定基线**：先选 5～20 个最小 development fixture，记录 DevSeek 基线和 Codex/Claude 的公开可观察行为；真正晋级的最小 N 由 qualification profile 和统计计划确定。
2. **找 authority**：列出现有所有解释/执行此语义的代码点，确定唯一 semantic authority/port；允许它由多个内聚组件实现，不把所有代码塞进一个 God Service。
3. **定契约**：定义输入、输出、状态、失败、权限、证据和指标。
4. **先测后迁移**：阶段微评测 + 相邻契约测试 + 至少一个全链路黄金旅程。
5. **纵切接入**：在未发布迁移候选中接入一条真实路径；如果必须保留旧 API，它只能做无业务语义 delegator，不得双写或构造终态。
6. **收口所有入口**：声明的 sibling entrypoints 全部通过 reachability/conformance 后，再删除旧 semantic owner/分支，并新增 import/调用静态守卫；未达到该门禁不得发布候选。
7. **故障注入**：权限拒绝、超时、冲突、无 verifier、断线、恢复等至少一种。
8. **日常跨面资格**：专项平时做 Headless → VS Code/CLI 并最高推进到 L4；真实 Provider micro-probe 在 wave freeze 批量运行，完整 live/holdout 只在 RC 运行。
9. **对标复盘**：用未公开 `H-CAP-*` 专项案例盲评正确性、干预次数、证据和成本；最终 `H-FORMAL-*` 只验证组合能力。
10. **更新账本**：自动生成 implementation state 与逐 profile/scope/Surface/Provider/platform 的 qualification claims，无作用域 level 只生成最低值视图；再按 DAG 选择下一个可并行原子能力，不要求前一大组先到 L6。

## 22. 降低迭代工作量的方法

- 真实 Provider 只在冻结 wave/RC 使用；平时使用捕获 trace replay 和 deterministic fault injection。
- package/install 只在 Surface 边界变化或 RC 时执行；纯 Core 变更走 Headless conformance。
- 建立 test impact graph，只跑受影响专项 + 核心黄金集；夜间运行全量。
- 每个语义只保留一个 owner，减少重复修复和测试组合爆炸。
- 能力状态、报告和 traceability 从 ledger 自动生成，停止手工复制完成信息。
- 黄金集保持小而高信号；探索性大样本在 RC 阶段运行，不让日常循环变慢。
- 使用 failure budget：同类失败第二次必须修 owner/边界/门禁，不允许继续增加样例特判。
- 日常证据只在 capability authority、case/oracle 版本和所有传递依赖 hash 未变，且 impact proof 通过时继承；冻结 RC 的 live/holdout 证据不继承，任何产品改动均清零。
- 网页/Provider 指纹、竞品版本/配置、artifact、case version 或能力依赖改变时自动失效；时间 TTL 由 profile 声明。

## 23. Gate 0 通过后才允许开始的三个纵切

以下是 R1 的第一组产品纵切，不是当前开工许可。当前 Gate 0 未通过、无 live、无有效 qualification claim；禁止以 G0-A/B/C/D 的 deterministic 实现完成替代 Gate 0 裁决。

1. **D-G01 简单创建**：无附件 VS Code 请求创建最小程序，统一 Kernel → transaction → readback → verifier → completion。
2. **D-G02 局部修改**：带/不带附件结果等价，保护脏工作区，运行项目测试。
3. **D-G03 失败修复**：从真实 failing test 出发，诊断、修改、重验；禁止无 verifier 默认成功。

Gate 0 真正通过后，这三条稳定并删除对应旧路，再扩展到跨文件 medium 和 formal 项目。它们直接验证当前最明显的“简单程序功能回退”是否真正收敛；在 Gate 0 前提前迁移会绕过本路线图自己的证据前置条件。
