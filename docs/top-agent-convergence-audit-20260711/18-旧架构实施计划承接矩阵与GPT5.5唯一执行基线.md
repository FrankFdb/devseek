## 1. 最终判断

旧需求与架构文档并非全部错误，但它们不能继续充当迭代队列：正确的 Headless Core、Surface/Provider 解耦、Evidence、恢复和工程闭环方向，与错误的多 owner、模型自判完成、历史 Phase 状态、弱测试资格解释混在一起。尤其 `ARCH-05` 是有价值的历史实施记录，却已被后续代码、机器账本和反证审计部分证伪；继续按它的 Phase 领取任务会复活旧顺序和旧完成定义。

本目录在本次修订后已经充分承接旧文档中的**有效需求、架构意图、历史实现和未完成缺口**，并把 R1～R3 的宽能力组拆成 GPT-5.5 可单窗口执行的 leaf cards。因此：

- **人工规划与执行层已充分**：任务只从 14 领取；15 选择当前卡，16 约束执行，17 提供静态事实，18 路由旧文档；旧文档只作定向证据。
- **机器治理层仍未完成**：Active Baseline selector、legacy inventory、自动 banner/status 仍是 `G0-01～03`；本次 Markdown 指向不能伪装这些门已经实现。
- **产品与资格层远未完成**：七个 C0 只有 2 项 machine `wired`，仍有 5 个 repository blocker、6 个 external-authority blocker 和零 claim。

“充分”只表示下一模型无需重新做全仓文档审计即可正确开始原子任务，不表示 DevSeek 已达到顶级、Gate 0 已通过或旧代码无需继续重构。

## 5. `ARCH-05` 的最终处置

`ARCH-05` 中的长篇原则和 Phase 结果保留为历史证据，不删除；但它的任务选择权、状态权和“下一阶段”相对时间词全部撤销。其有效遗留曾在 [归档 14 §3.8](archive/14-未完成事项与后续整体迭代计划.md#38-arch-05-phase-遗留承接) 映射到原 atomic IDs，当前任务状态只以 [PLAN](PLAN-当前收敛迭代计划.md) 为准，规则如下：

1. 旧 Phase 0～12 是历史实施分组，不是当前 Phase verification runner，也不是 GPT-5.5 作业卡。
2. 旧“已实现/测试通过”只在 10～13/17 或 machine ledger 能复算时成立；否则只保留为历史 observation。
3. 旧 `L` 等级、canary/medium/formal 数字、stable/top-tier 描述没有精确 protected claim 时全部撤销。
4. 一个旧 Phase 跨多个 semantic authority 时，必须拆到 14 的 child IDs；禁止一次提交“完成整个旧 Phase”。
5. 旧文档新发现且矩阵未覆盖的有效要求，先登记到 14 的最小 leaf，不得直接实施。

由此，后续无需再次按 `ARCH-05` 做全量审计；只在当前卡的 source references 明确指向它时定向读取对应章节。

## 7. GPT-5.5 防偏航规则

1. 一窗口、一 atomic ID、一个 semantic authority、一个集成 owner；子代理只读复审或无写冲突验证。
2. 每卡先补齐 14 §5 输入卡，先产生可失败 oracle，再改唯一 owner；没有 oracle 不实施。
3. 任何旧文档中的“立即、下一轮、已完成、100%、stable”都先查本文和机器 SSOT，不按自然语言继承。
4. 任一前置未 `PASS` 只允许当前卡 `BLOCKED/FAIL`，不得选择看似可做的后续任务。
5. docs-only handoff commit 不要求重打未变源码的 VSIX；必须分别报告 15 定义的五类身份及 applicability，用户窗口动态 receipt 另行单列。
6. 用户同窗口、真实 Provider、账号、网络、外部基础设施和 holdout 授权不跨窗口继承。
7. Extension/Bridge 行为真正变化时才按 `AGENTS.md` 执行 compile/package/install；纯文档卡不得制造无意义 release。
8. 每卡提交后停止；不自动进入下一卡，不从历史路线顺手扩张。
