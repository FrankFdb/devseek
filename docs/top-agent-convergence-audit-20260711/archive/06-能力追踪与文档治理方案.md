# DevSeek 能力追踪与文档治理方案

- 日期：2026-07-11
- 目标：让需求、设计、实现、测试和“完成”状态只有一个可复算事实源
- 接管定位：治理目标规范，不是当前 machine SSOT；实际状态来自 `docs/process` ledger/profile/inventory/report 与 checker，实施卡为 G0-01～03

## 1. 当前治理问题

DevSeek 不是缺文档，而是文档状态和事实层级过多：

- `docs/requirements`、`docs/architecture`、测试计划、接管计划和 release audit 都能描述“当前方向”。
- 一项能力可能在需求中写完成、在架构中写已落地、在代码中只有类和单测、在最新 live 报告中又是未运行。
- 阶段报告按时间持续生成，但历史说明和 quick entry 没有可靠降级，读者很难知道哪份仍有效。
- 测试证据可能只保存在 `/tmp`，或 catalog 链接已经不存在，`passed` 仍长期保留。
- 同一语义有多个 owner 时，文档只记录功能名称，不记录“产品主入口的决定权究竟属于哪个契约”。
- “实现到哪一步”和“证据证明到哪一层”被压成一个 `status`，类存在、入口接线和真实产品资格因而可以互相冒充。
- 同一 case 重跑可能覆盖最后结果或被重复计数，失败历史无法参与候选 veto。

文档数量增加本身不会收敛；必须把能力状态、资格策略和不可变证据分开建模，再由工具生成 Markdown 视图。

## 2. 七类单一事实源及其边界

| 事实类型 | 唯一 SSOT | 内容 | 禁止事项 |
| --- | --- | --- | --- |
| 产品能力 | Capability Ledger | 原子能力、semantic authority、实现状态、逐作用域资格 claims、依赖 | 在多份 Markdown 手写不同完成状态 |
| 目标架构 | Active Architecture Baseline | 依赖方向、ports、契约、状态机、ADR | release log 反向成为当前架构规范 |
| 当前工作 | Iteration Backlog | 当前 capability/work package、依赖、退出条件 | 用长篇接管文档复制全部历史 |
| 产品运行事实 | Run Evidence Ledger | run/event/tool/mutation/effect/verification/completion 的只追加事实与 receipt | 让产品内核认识 case、oracle、L 级或资格配额 |
| 资格规则 | Qualification Profile | 要证明什么、适用面、case、attempt/veto、统计和有效期 | 把规则藏在 runner 默认值或报告中 |
| 资格事实 | Qualification Preregistration Plan + Attempt Events + Evidence Manifest | 候选级冻结计划、运行证据引用、独立 oracle/adjudication 和聚合产物 | 在计划外现造 slot、回写产品 ledger，或用 `/tmp` 路径、口头结论计入配额 |
| 历史审计 | Migration Manifest + Changelog/Archive | 旧 REQ/标题的裁决、替代关系、banner、历史证据 | 历史文档继续自称 active/SSOT |

五类核心 machine-readable ledger/profile/plan/event 对象不能合并：

1. **Capability Ledger** 回答“产品声明实现了什么、由哪个语义边界裁决、当前证据最多支持哪一级”。
2. **Qualification Profile** 回答“某个原子能力在指定 Surface/Provider 上要达到什么等级、必须跑哪些 case、什么失败会关闭候选”。
3. **Run Evidence Ledger** 回答“被测产品的 run 实际观测到什么”。它由 Kernel/宿主产生，不引用 qualification profile、case、oracle 或等级。
4. **Qualification Preregistration Plan** 回答“冻结候选允许在哪些预检/覆盖槽位、顺序、时间窗和预算内执行”。它在任何外部动作前由独立 plan authority 签名注册，注册后不可增删或重排 slot。
5. **Qualification Attempt Event / Evidence Manifest** 回答“某个冻结候选在某 case 上如何引用运行证据并被独立裁决”。Attempt 事件只能追加，Manifest 是签名聚合输出；二者都不能回写产品 ledger、政策或覆盖旧结果。

Markdown 报告只是上述事实源的生成视图，不再是状态数据库；禁止人工编辑生成区。

## 3. Capability Ledger 规范

### 3.1 原子能力条目

以下是 schema 示例，不是对当前实现状态的宣称：

```yaml

  - packages/vscode-extension/src/agent-loop.ts
  - packages/cli/src/index.ts

architecture_dependencies:
  - capability_id: C7-PERMISSION-DECISION
    relation: control
    required_implementation_state: wired
    contract_sha256: "..."
  - capability_id: C7-SANDBOX-POLICY
    relation: safety
    required_implementation_state: wired
    contract_sha256: "..."

    relation: runtime
    required_implementation_state: wired
    contract_sha256: "..."

  - AC-MUTATION-001
qualification_profile: qualification/profiles/C7-WORKSPACE-MUTATION.yaml
qualification_evidence_manifest_refs:
  - {manifest_id: qem-01JZ-example, sha256: "..."}
known_gaps:
  - code owner and product entrypoints are not yet migrated
last_verified_at: null
```

条目约束：

- `capability_id` 必须原子、稳定且不复用；Phase、Wave、文件名和某个测试场景都不能充当能力 id。
- `domain` 只用于分组；资格与依赖必须绑定原子 `capability_id`，不得只写 `C7` 这种大组。
- `semantic_authority.key + port` 对同一决定语义唯一；允许 coordinator、policy、adapter、store 等多个内聚组件协作实现。
- `implementation_components` 是实现拓扑，不获得平行决定权；Surface/Provider adapter 只能翻译输入输出。
- `priority` 和 `applicability` 是每个原子条目的必填值，不得由领域名或缺省值暗推；`conditional/deferred/experimental` 不计入某 claim，除非 claim profile 显式启用并完成裁决。
- `architecture_dependencies` 中每个 id 都必须在同一 ledger 定义，并写明 `relation/required_implementation_state/contract_sha256`；不允许 `C01-KERNEL` 一类不存在或粒度不明的别名。
- 架构依赖不等于“所有依赖必须同等晋级”；每个 Qualification/Milestone Profile 用 `qualification_dependencies` 冻结所需 level 和 scope。工作包规范化为 `requirements[]{required_implementation_state,required_claim}`，每个元素只代表一个精确 tuple；每条 `selection_path` 也保存一个完整 tuple 和有效 state。只对同 tuple 的多条路径取最严格 state/level，不同 tuple 禁止合并，纯 ID 闭包不得直接当工作量或资格结论。
- `qualification_claims[]` 是唯一资格事实；唯一键为 `profile_id + profile_sha256 + claim_scope + surface + provider + platform_profile`，不得出现 wildcard、缺省维度或同键多个有效 claim。每个 claim 只能由当前有效、独立签名的 Qualification Evidence Manifest 授予，不能随 `implementation_state` 自动提升，也不能把 Headless/Linux/controlled-replay 的证据外推到 VS Code/Windows/live Provider。
- 无作用域的 `qualification_level_view` 只是生成视图：对当前 applicability 要求的全部精确 claim tuple 取最低有效等级，任一 tuple 缺失/失效则为 `null/unqualified`。它不可写回 ledger，不可满足 qualification dependency，也不得用“最高已观测 level”生成。

`applicability` 必须显式列出 Surface、Provider 和平台。无法运行不等于“不适用”；`not-applicable` 必须有独立裁决记录。L5/L6 的 profile 还必须引用 [`05-黄金用户旅程与正式项目资格方案.md`](05-黄金用户旅程与正式项目资格方案.md) 的冻结 RC、自然 UI + 真实 Provider 同 run/trace、holdout 和盲评政策，不能自行发明较宽松入口。

`qualification_dependencies[].required_claim` 必须对 `profile_id/profile_sha256/claim_scope/surface/provider/platform_profile` 六个维度做全等匹配，然后才比较 `minimum_level`。聚合器还必须验证该 claim 引用的 Evidence Manifest 当前有效且其 dependency snapshot 与当前实现一致；不得用无作用域 `qualification_level_view`、另一个 Surface/Provider/平台的 claim，也不得用“更高 level 但 profile hash 不同”的 claim 替代。需要兼容多个 target 时必须在 profile 中显式列出多条依赖，不能由 reader 做模糊匹配。

### 3.3 预注册计划、Evidence Manifest 与追加式 Attempt Event

候选级预注册计划、共享前置和 case 执行必须分开，避免把共享登录检查伪装成某个 case，或通过重建 session 等到有利窗口：

```text
QualificationPlanRegistered          # 候选级；在任何 session/attempt/外部动作前
  → QualificationSessionRegistered   # 只能消费计划中的 preflight_slot_id
  → PreflightAttemptStarted
  → PreflightObserved
  → PreflightClassified
      ├─ veto → CandidateClosed
      ├─ product/connector failure
      │    ├─ RC/L0～L5 → CandidateClosed
      │    └─ L6 → SessionProductFailure → linked coverage failures recorded → next planned slot
      ├─ environment/test-infra → QualificationSessionBlocked
      │    → InfraAdjudicated → 计划内唯一 retry slot | CandidateBlocked
      └─ valid → QualificationSessionReady

AttemptRegistered                     # 引用 ready preflight 与计划中 coverage_slot_id
  → AttemptStarted
  → ExternalActionStarted
  → RunObserved* | AttemptAbandoned  # 正常观测或 watchdog 闭合的事实
  → OracleClassified
  → AttemptTerminated
```

`QualificationPreregistrationPlan` 是候选级不可变签名对象：冻结 candidate/profile/catalog/oracle/corpus/metrics，全部 preflight/case slot、顺序、seed/variant、时间窗、预算、runner/toolchain 和有效期。计划没有注册或签名无效时，任何 session/attempt 都只是调试证据。计划一旦注册不可加 slot、换顺序或改预算；必要修订会生成新 plan/candidate，旧失败仍保留。

`QualificationSession` 消费计划中唯一 preflight slot，冻结 runner、账号授权、条款/数据边界、connector 和环境身份；`PreflightAttempt` 是 session 内独立事件流并声明 `valid_until`。`PreflightClassified` 必须由 allowlisted 独立裁决者签名。DevSeek 可控 connector 缺陷属于 product failure，绝不能 infra retry/换 session：RC/L0～L5 关闭候选；L6 将该 session 和计划中绑定它的 coverage slot 记为 product failure 后继续剩余计划，最终受 connector SLO/reliability 门槛裁决。veto 在任何等级都立即关闭；只有已证明的外部 environment/test-infra 才能消费计划内唯一 retry slot。所有 failed/blocked session 都进入 wave 分母和 connector SLO，不能重建 session 消失。

`Attempt` 不是一条最后才填写 `result` 的可变记录，而是 case 事件流；每次执行生成新 `attempt_id`，先追加 `AttemptRegistered`，之后只追加事件、不回填旧事件。runner 崩溃或超时时，独立 watchdog 必须追加只描述观测事实的 `AttemptAbandoned`；它不得填写 oracle 字段。无论正常或 abandoned，独立 Oracle 先对最后观测事件追加 `OracleClassified`，再由 qualification coordinator（runner 不可用时由 watchdog）追加引用该 Oracle hash 的 `AttemptTerminated`。任一分支都不能静默消失。禁止在事件系统外读取登录状态或启动浏览器。

hash 必须按 schema 固定的 canonicalization 计算，并显式排除自引用：

- `preflight_slot_sha256 = SHA-256(canonical(preflight_slot - preflight_slot_sha256))`；
- `coverage_slot_sha256 = SHA-256(canonical(coverage_slot - coverage_slot_sha256))`，包含其完整 `attempt_windows` 与所有顺序/身份/预算字段；
- 先回填并校验所有 slot hash，再计算 `qualification_plan_sha256 = SHA-256(canonical(plan - qualification_plan_sha256 - plan_attestation.signature))`。

任一 slot 内容变化都必须同时改变 slot hash 与 plan hash，reader 不得信任对象中携带的 hash 而省略复算。注册事件签名 `campaign id + plan id + plan hash + candidate identity + created_at`。plan signer 必须命中 profile 的 plan-authority allowlist，seed reveal 必须在注册后解封并能复算 commitment；明确列出的 slot order 仍是执行权威。runner 只能消费签名 plan 中的 slot，不能在内存或 CLI 参数中现造 slot。

Plan validator 必须在注册前一次性证明：所有 id/order 唯一；每个 slot hash 可复算；`valid_from ≤ created_at ≤ scheduled_window.start < scheduled_window.end ≤ expires_at`；每个 attempt window 引用可达 preflight slot，且 slot 的 requested TTL 落在 profile 冻结范围并使窗口在计划上可行；retry 图无环且只指向更早的 slot；同一 coverage slot 的条件分支仍只产生一个 coverage；primary、adjudicated retry 与 total budget 数学一致；seed reveal 与 commitment 匹配；candidate/profile/catalog/oracle/corpus/metric/environment hash 齐全；签名 identity/key 都在 profile allowlist。任一条件失败都拒绝注册，不能让 runner 用默认值修补。

hash property test 必须证明：对象 key 重排不改变 canonical hash；任一非排除 slot 字段变化必须改变 slot hash 和 plan hash；只篡改对象自报的 slot hash 会在复算比对中失败；从其他 plan/slot 移植 hash 也必须失败。

注册前不得伪造未来 `PreflightReady.valid_until` 或实际 attempt 时间。不仅 case attempt，**preflight 自身所需的 browser launch/navigation、auth/session/cookie/credential、DNS/network/provider request 也全部是 external action**；禁止任何 adapter 在 guard 前以“health check”或“只读登录检查”为由触网。

所有这些动作共用唯一 fail-closed `QualificationExternalActionGuard`，并在**每一次** browser/auth/network 调用紧邻前执行。它是 `C0-PREREGISTRATION-PLAN / QualificationPlanRegistrationPort` 的执行组件，只强制执行已签名 plan/profile 规则，不得发明新 policy；slot reservation/receipt 通过 C0 追加式资格事件边界持久。Provider/browser adapter 不能自行判定“这次可以跳过 guard”，也不得把这个 qualification guard 混入产品 Kernel 的 `C7-EXTERNAL-EFFECT`。guard 必须满足：

1. 从不可回拨的 trusted wall-clock/time attestation 读取 `guard_now`，不信任 event 自报的 `occurred_at/recorded_at`；验证 plan 签名有效，由证据库独立签名的 `QualificationPlanRegistered` 写入 receipt 中 `trusted_recorded_at ≤ guard_now < plan.expires_at`，且当前 slot/action window 包含 `guard_now`。
2. 验证 plan/session/attempt 的已持久注册事件及 hash 链，且它们各自的独立写入 receipt 都有 `trusted_recorded_at ≤ guard_now`；preflight 动作必须有先行 `QualificationSessionRegistered`，case 动作必须有先行 `AttemptRegistered/AttemptStarted` 和精确匹配的 ready event/session/slot/hash，并满足 `ready_at ≤ guard_now < valid_until`。
3. 在同一 plan 的 preflight + coverage 全局 slot 序列上验证当前 `order`；所有必需前驱已按 profile 终结/裁决。较早的条件 retry branch 若因 primary 成功而不应执行，必须先追加签名 `SlotBranchSkipped` 并引用使 branch predicate 为 false 的精确事件 hash，不能静默跳过；不得通过新 session 或分支 runner 超序。
4. session/attempt 注册时必须对 `(qualification_plan_sha256, slot_id, attempt_role)` 执行持久化线性一致 compare-and-set 并产生 `slot_consumption_id`，guard 再验证当前 session/attempt 独占该 reservation，保证 slot/primary/retry 的唯一消费。retry 还必须精确引用计划内 retry branch 和在 `guard_now` 之前已持久的独立签名 `InfraAdjudicated`，匹配原 slot/attempt/failure event/reason/budget，且不超过 24h 裁决窗口；product/connector failure 永不可通过 retry guard。
5. guard 追加绑定 `plan/session/attempt/slot_consumption_id/action_id/action ordinal/action type/destination/guard_now/nonce/expires_at` 的一次性签名 authorization receipt；adapter 在真正发起动作时再核验并原子消费 receipt。超时、重放、改 destination/action 或 CAS 冲突均不执行动作，只追加 blocked/invalid 证据。

CI 必须用状态机/property test 覆盖时间漂移与重放：信任时钟在 window/TTL/plan-expiry 边界前后偏移，伪造早到的 `occurred_at`、延迟 `recorded_at`、plan/session/slot 注册倒序，同一或新 session 重放 slot，并发 runner 双消费，重放/篡改 authorization receipt，无裁决、超 24h、错 failure 引用和 product failure 伪装的 retry。对所有生成 trace 都必须保持前缀安全属性：若缺任一有效 plan/session/slot/order/time/unique-consumption/adjudication/receipt 前提，则 trace 中 browser/auth/network action 数必须为 `0`。

聚合器只读取事件，不写回事件：

- 配额只按签名 plan 中的 `(qualification_plan_sha256, coverage_slot_id)` 计数，一个 slot 至多贡献一个 pass。多个 attempt 全部保留；它们不会生成新 coverage。
- `AttemptRegistered` 必须精确匹配 plan 中的 slot hash、顺序、candidate/profile/case/variant/fixture/Surface/budget/runner/toolchain 身份。未计划 slot、超顺序/预算或任一身份漂移只能 invalid/形成新 candidate，不得生成新 coverage slot。CI 必须用 property test 证明“任一 attempt identity 字段变化不会增加 coverage”。
- `OracleClassified` 是 `oracle_verdict/failure_class/veto_codes` 的唯一权威事件，且只能由 allowlisted 独立 Oracle 签名；`AttemptTerminated` 只保存产品观测事实和精确的 Oracle event id/hash 引用，不得复制裁决字段。引用缺失、hash 不匹配或 actor 非独立 allowlist 时，聚合结果只能是 `unclassified`。
- `observed_run_status` 与被引用的 `oracle_verdict` 必须分离：D-G07 的正确拒绝可以观察到 `blocked` 但 case `passed`，D-G08-CANCEL 的正确取消可以观察到 `cancelled` 但 case `passed`；D-G08-RESUME 则必须从非终态 interruption 恢复，不能恢复已 cancelled run。不得把产品状态直接当评测结论，聚合器也不得缓存一份可独立修改的裁决快照。
- case 或 preflight 的 ordinary product/model/agent/connector failure 候选语义由 profile 固定：L0～L5/RC 默认 `close-candidate`；L6 将失败 session/attempt 与其绑定的 planned coverage 记为 miss，继续剩余计划，并按 [`05` 第 9.3 节](05-黄金用户旅程与正式项目资格方案.md) 执行可靠性/非劣和 connector SLO 门槛。veto 在所有等级都立即关闭。无论采用哪种策略，后续同 key 的 `passed` 都不能覆盖旧失败。
- case 与 preflight 的 `environment`/`test-infra` 失败都进入清单、wave 分母和 SLO，且不计 pass。只有独立 adjudication 证明产品尝试未开始或结果不可判定时，才可消费相同 plan 中已预留的唯一 retry slot；24 小时内未裁决保持 blocked。裁决、重试与新 session 都追加记录。DevSeek connector 的 auth/session/DOM/correlation/reconnect 缺陷属于 product failure，不能归入外环境、新建 session 或换时间窗重试。
- 修改产品、prompt、profile、case、oracle、artifact 或受影响依赖后形成新候选/新版本，按 [`05`](05-黄金用户旅程与正式项目资格方案.md) 的资格顺序重新计算，不沿用旧 pass 数。
- 报告必须同时展示覆盖数、有效尝试数、全部失败数、infra-invalid 数和 veto；禁止只展示“最后一次结果”。

`InfraAdjudicated` 也是独立事件，必须包含 actor、reason code、evidence hash 和签名；修复者不能担任该裁决者。开发机上的 Git + checksum 只能发现误改；L5/L6 事件必须由受保护 runner 对规范化事件、前序 event hash、catalog/profile/oracle hash 和 artifact identity 联合签名，并写入保留锁/WORM 或等价不可覆写存储。签名验证失败、链断裂、runner 不在 allowlist 或保留锁缺失时，该 attempt 只能作调试证据。Evidence Manifest 是事件流的签名聚合输出，不是可回写事件。敏感 raw stream/cookie/source/screenshot 进入加密限权 raw store，manifest 只保存脱敏摘要和 checksum。

事件完整性算法由 schema version 固定，避免自引用：先对事件移除 `event_sha256` 和 `runner_attestation.signature` 后做 canonical JSON，再计算 `event_sha256`；首事件的 `previous_event_sha256` 为 profile 定义的 genesis/null，后续必须等于同 stream 前一事件 hash。allowlisted runner 只签名 `schema_version + correlation_id + sequence + previous_event_sha256 + event_sha256`；artifact store 再对写入 receipt、object version/retention lock 和可信时间单独签名。任何 canonicalization、链顺序或签名算法不一致都使事件失效，而不是由 reader 猜测修复。

## 4. 两条独立状态轴

### 4.1 `implementation_state`

| 值 | 必要事实 | 资格含义 |
| --- | --- | --- |
| `proposed` | 问题、目标和边界已提出 | 无；`qualification_claims[]` 必须为空 |
| `specified` | authority port、输入输出、失败语义、指标已批准 | 最多可拥有 L0 规范证据 |
| `implemented` | 实现组件和相邻单元/契约测试存在 | 不证明真实产品入口可达 |
| `wired` | 所有声明产品入口经 authority port 可达，旧决定 owner 已封死 | 不自动证明 L2～L6 |
| `deprecated` | 有 replacement、迁移截止和禁止新增使用规则 | 不得作为新资格目标；历史证据保留 |
| `superseded` | 已被 replacement 完全替代，仅供审计 | 不参与当前资格聚合 |

状态只能按事实迁移，不以测试层命名。尤其不得再写 `surface-qualified` 作为实现状态。

### 4.2 `qualification_claims[].level`

| 等级 | 证据定义 | 不足以证明什么 |
| --- | --- | --- |
| L0 `specified` | profile、authority contract、失败语义、指标已校验 | 不证明代码存在 |
| L1 `implemented` | 实现和 unit/adjacent contract evidence 存在 | 不证明进入产品路径 |
| L2 `deterministic-qualified` | fixture、属性测试、故障注入、captured replay 通过 | 不证明真实 Surface/Provider |
| L3 `runtime-qualified` | Headless 同一 Kernel 完成端到端任务 | 不证明 IDE/CLI 适配正确 |
| L4 `surface-qualified` | VS Code 与 CLI 真实入口通过适用 conformance 和黄金旅程 | 不证明 live 模型开放任务稳定 |
| L5 `live-qualified` | 冻结 commit/artifact、预注册唯一 case、真实 Provider 同 run/trace 配额通过 | 不证明领先竞品 |
| L6 `top-tier-qualified` | holdout 上与 Codex/Claude 同题盲评无 veto，目标指标不劣 | 只对已测能力、版本和有效期成立 |

表中等级只能出现在第 3.1 节的精确作用域 claim 内。两轴相关但不可互相推导。例如 `implementation_state: wired` 可以只有某一 tuple 的 L1；也可能因当前 commit、依赖 hash 或 Provider 身份变化使原 L4 claim 失效，而接线事实仍是 `wired`。`deprecated/superseded` 条目的历史 claim 只能显示为 `historical_qualification_claims[]`，不能混入当前状态。

“存在类”“export 了服务”“有单测”“static grep 通过”至多支持 `implementation_state: implemented` 和 L1，不能支持 `wired`、L3 或更高。

## 6. Semantic authority 不是 God Service

“唯一 owner”的真实含义是一个决定只能由一个 authority contract 作出，而不是所有逻辑都塞进一个类：

```text
Agent Kernel
    → WorkspaceMutationPort          # 唯一 mutation 决策入口
        → MutationPolicy             # 范围、脏工作区、CAS 规则
        → TransactionCoordinator     # prepare/apply/rollback
        → FileSystemAdapter          # 平台 I/O
        → DiffEvidenceWriter         # 不可变 receipt

VS Code / CLI / MCP adapters
    → 只能调用 WorkspaceMutationPort
    ✕ 不得自行决定可写范围、成功或 rollback
```

治理规则：

- ledger 对一个 `semantic_authority.key` 只能存在一个 active port；多个实现组件必须列明角色和依赖方向。
- port 应围绕单一语义裁决拆分：workspace mutation、external effect、permission、verification、settlement 分别建 authority，不能合成“万能 AgentService”。
- 组件可以按性能、平台或协议多实现，但它们必须通过同一 conformance suite，且只有 composition root 可选实现。
- 文件路径不是 owner 身份。重构移动文件不改变 semantic authority；新路径试图直接作决定则属于 bypass。
- `forbidden_bypasses`、import graph、运行时 receipt 与 Surface conformance 共同证明 owner 收敛；仅 grep 到一个类名不够。

## 7. 需求—设计—代码—测试追踪与文档元数据

### 7.1 双向追踪

```text
User outcome
  ↕
Requirement / Acceptance ID
  ↕
Atomic capability id + Architecture port / ADR
  ↕
```

每个 acceptance 至少关联一个 verifier；每个 implementation component 关联一个 architecture port；每个 live case 关联原子 capability id，不能只写 `formal-simulation` 或大组 `C7`。

这里的文档维护 `owner` 可以是团队角色，但不能冒充产品 semantic authority。旧文档无需删除；必须由 migration manifest 生成醒目 banner。如果只是一部分被替代，迁移项要精确到稳定标题 selector/REQ id。

## 8. 证据继承、冻结 RC 与资格聚合

### 8.1 日常专项迭代

日常开发追求快速局部闭环，可以继承**未受影响的开发证据**，但必须由依赖 hash 自动裁决：

- 变更 capability、authority contract、实现组件、profile/case/oracle/toolchain 后，使该能力及 ledger 依赖反向闭包的旧 evidence 失效。
- 依赖快照完全相同的 unit、deterministic、captured replay 证据可标记 `reused`，但 Manifest 必须引用原 attempt，不得复制成一次新 pass。
- L4 Surface evidence 只有在 commit、构建 artifact、installed identity、Surface adapter 和 transitive dependency hashes 全部相同时才能继承；否则降级到仍有有效证据支持的层级。
- L5/L6 live/holdout 证据始终绑定候选、Provider 模式、case 隐藏变体和有效期，不得用于另一个 commit/artifact 的当前资格声明。

### 8.2 冻结 RC

冻结 RC 使用更严格规则：

1. 冻结前按 [`04`](04-分能力专项迭代与收敛路线图.md) 和 [`05`](05-黄金用户旅程与正式项目资格方案.md) 确认 C0 Gate 0 infrastructure profile 已达 wired/L2、所有适用 C1～C13 产品能力 P0/P1 的 required claim tuples 均有当前有效 L4 claim、核心自然 Surface 旅程无 veto；C14 不参与自身前置计算。
2. 固定 candidate commit、source tree、prompt/config、profile、case catalog、oracle bundle、toolchain、构建 artifact 和 installed identity，并预注册唯一 case 计划。
3. RC 的 canary、medium、live/formal 资格 attempt 必须在冻结后新采集；不得从旧 commit、旧 artifact 或另一 installed version 继承配额。
4. 任一有效 product/model/agent failure 或 veto 关闭该候选。修复形成新 commit 后，重新冻结并从 canary 开始，不能“补跑到全绿”。
5. 环境/测试基础设施失败仍追加保存，经独立裁决后可在同候选重试，但既不计 pass，也不能抹去事件。
6. 冻结后若 profile/case/oracle 改变，该候选失效；新 policy/version 必须复审并重新预注册。

因此，日常“只重跑受影响闭包”与 RC“冻结后重新收集资格配额”不是矛盾：前者优化开发反馈，后者保护发布结论。

### 8.3 架构门禁从行数升级为收敛度

现有 architecture budget 可继续保留复杂度预警，但主要硬门禁应由 ledger/graph/receipt 复算：

```text
product_coding_kernel_count = 1
run_lifecycle_authority_count = 1
settlement_authority_count = 1
tool_dispatch_authority_count = 1
workspace_mutation_bypass_count = 0
external_effect_bypass_count = 0
permission_bypass_count = 0
validation_hidden_write_count = 0
surface_business_branch_count = 0
provider_dialect_imports_in_core = 0
missing_evidence_links = 0
duplicate_active_document_ssot = 0
```

门禁实现以 import graph、AST/typed rule、dependency ledger、不可变 receipt 和 conformance test 为主；纯 grep 只能做早期辅助，不能证明运行时行为。

## 9. 旧文档机器迁移清单

### 9.1 每个旧标题/REQ 都必须有裁决

迁移不是给整份文档写一句“已过时”。每个稳定 REQ id 和受治理的 H2/H3 标题都要满足：

```text
old REQ / heading selector
  → disposition
  → replacement document + anchor + capability ids
  → generated status banner
  → CI confirms source and replacement hashes
```

规范清单示例：

```yaml
schema_version: devseek.document-migration/v1
migration_id: MIG-LEGACY-REQ-20260711
source_document:
  document_id: REQ-LEGACY-001
  path: docs/requirements/01-example.md
  source_sha256: "..."
document_banner:
  target_status: superseded
  replacement_document_id: REQ-ACTIVE-001
  marker: "<!-- generated:migration-banner:MIG-LEGACY-REQ-20260711 -->"
  text: "状态：Superseded。仅用于历史审计；当前要求以 REQ-ACTIVE-001 为准。"
items:
  - source_kind: requirement
    selector: REQ-OLD-017
    disposition: replace       # retain | revise | replace | revoke | archive
    rationale_code: COMPLETION-SELF-REPORT-UNSAFE
    replacement:
      document_id: ARCH-KERNEL-001
      anchor: settlement-decision
      capability_ids: [C1-SETTLEMENT, C9-INDEPENDENT-VERIFICATION]
    section_banner: superseded
  - source_kind: heading
    selector:
      heading_id: legacy-tool-routing
      heading_text_sha256: "..."
    disposition: revise
    rationale_code: MULTIPLE-TOOL-AUTHORITIES
    replacement:
      document_id: ARCH-KERNEL-001
      anchor: tool-dispatch
      capability_ids: [C6-TOOL-DISPATCH]
    section_banner: deprecated
effective_commit: "<commit>"
```

`retain` 也必须指向仍 active 的规范；`revoke` 必须说明不提供 replacement 的原因；`archive` 只能用于历史事实，不能让要求静默消失。标题 selector 绑定稳定 id 和文本 hash，源标题新增、删除或改名会使 CI 失败，迫使维护者补裁决。

### 9.2 少改动的迁移顺序

1. 先把本审计目录标为方向决策包，不冒充已实施的 Active Architecture。
2. 审批目标架构后创建短 Active Baseline，引用本目录 03/04/05，而不是复制全文。
3. 生成旧 `docs/requirements`、`docs/architecture` 的标题/REQ inventory；每项写入 migration manifest。
4. CI 验证裁决和 replacement 后，工具批量插入 document/section banner；正文保留审计历史。
5. 将 release reports、时间戳报告移出 quick entry，只保留当前 manifest 生成视图和历史索引。
6. 从 capability ledger 生成 `docs/README.md` 当前状态区；每次专项只更新 ledger、ADR、profile/evidence，不再手工同步十几份文档。

原需求与设计的逐项人工裁决输入见 [`07-原需求与架构设计正确性审计.md`](07-原需求与架构设计正确性审计.md)；机器清单必须把该结论落实到每个 source selector，不能只链接整份报告。

## 10. 文档与资格 CI

### 10.1 阻断级检查

**Schema 与引用完整性**

- capability、profile、preregistration plan、session/preflight/attempt event、manifest、migration、document front matter 均通过版本化 JSON Schema/YAML 校验。
- capability id 唯一；所有 `architecture_dependencies.capability_id`、`qualification_dependencies.capability_id`、acceptance、case、profile、replacement、artifact URI 都存在。
- 每条 architecture edge 必填 relation/required implementation state/contract hash；每条 qualification edge 必填 required state，且 `required_claim` 的 profile id/hash、claim scope、Surface、Provider、platform 和 minimum level 全部齐全。依赖图无环，profile 的 transitive dependency snapshot 与 ledger 复算结果一致；依赖不精确匹配当前有效 claim tuple 即失败。
- 目录每行恰好解析一个显式 priority/applicability；生成条目数与目录行数一致，任何 unmatched/ambiguous/default fallback 均失败。
- 当前 `qualification_claims[]` 只能由有效 Manifest 按精确 tuple 聚合，不允许 Markdown 或人工 ledger 字段高报；无作用域 level 必须为可重生成的最低值视图，不能用于依赖。

**Authority 与实现收敛**

- 同一 active `semantic_authority.key` 只能有一个 authority port；组件多实现不增加 authority count。
- capability 标记 `wired` 时，产品入口 reachability、composition-root 选择和 forbidden-bypass guard 必须通过。
- deprecated/superseded port 被新增 import，或 Surface/Provider adapter 绕过 authority，立即失败。

**资格真实性**

- `QualificationPlanRegistered` 必须早于任何 session/browser/auth/attempt/external action；plan signer、candidate/profile/catalog/oracle/corpus/metric/environment hash 必须匹配 allowlist 与冻结身份。每个 preflight/coverage slot hash 都必须在删除自身 hash 字段后 canonical 复算，plan hash 再包含已验证的 slot hash。
- plan 的 id/全局 order/slot hash/时间窗/retry DAG/budget/seed commitment 必须通过属性校验；每一 browser/auth/network 动作前的 fail-closed guard 必须使用 trusted actual time，验证已持久 plan/session/attempt、window/TTL/order、slot CAS 唯一消费、retry adjudication 和一次性 authorization receipt。时间漂移、伪造 event time、未计划 slot、超窗/超序/超预算、并发/重放、身份漂移、重建 session 或无有效裁决 retry 均必须保证外部动作为零且不增加 coverage。
- `PreflightClassified` 必须区分 DevSeek 可控 product/connector failure 与独立证明的 environment/test-infra；只有后者经独立签名裁决后可消费计划内 retry slot，blocked session 仍进入 wave/SLO 分母。
- attempt store 只允许新增；既有 `attempt_id` 的内容、结果、veto、artifact hash 被修改或删除即失败。
- 聚合器不读取“last result”字段；同 `(qualification_plan_sha256, coverage_slot_id)` 至多贡献一次覆盖，attempt identity 任一字段变化不得制造新 coverage，历史失败和 veto 永久可见。
- Evidence Manifest 必须通过 `devseek.qualification-evidence-manifest/v1` schema，冻结 candidate/plan/profile、所有 event-stream head、attempt/slot/retry、失败/veto/分母、逐 tuple claim 和有效期；删除自身 hash 与 attestation signature 后 canonical 复算，并由与修复者/plan/runner/watchdog/oracle/adjudicator 相互独立的 aggregator 签名。任一 head/分母/依赖/身份/时效失配都使 claims 失效。
- 当前 commit/artifact 的 stable/live claim 引用旧候选证据、缺少自然 UI + 真实 Provider 同 trace、或证据过期即失败。
- 环境失败若无独立 adjudication 被重跑或误算 pass，立即失败。
- `/tmp`、易失路径、缺 checksum artifact、source/build/installed identity 不一致均不得计入资格。

**旧文档迁移**

- active `document_id` 或 `source_of_truth_for` 冲突；active 文档无元数据；replacement 链成环或目标不存在即失败。
- inventory 中每个受治理 REQ/H2/H3 必须恰有一个 migration item；新增旧标题未裁决即失败。
- deprecated/superseded 文档或章节缺生成 banner、banner 与 manifest 不一致、历史文档仍进入 quick entry 即失败。

**生成视图与基础质量**

- 重新生成 capability/trace/qualification/migration/README 视图后 `git diff` 必须为空，防止人工编辑或漏更新。
- Markdown 本地链接、anchor、front matter、代码块和表格结构必须校验；禁止未完成占位符进入 active baseline。
- 文档中的 commit、artifact、日期、官方/本地证据链接必须可读；推断和已验证事实使用不同字段。

### 10.2 警告级检查

- active 文档或 qualification profile 超过一个 release 周期未复核。
- 代码影响 implementation component/authority contract，但 ledger、profile 或测试映射未更新。
- 新组件与既有 semantic authority 高相似，或原子 capability 粒度再次膨胀成大组。
- evidence 接近有效期、平台/Provider 覆盖低于目标但尚未触及当前适用规则。
- 新文件超过复杂度预算或单一 port 的内聚组件数量持续上升。

### 10.3 CI 输出而非手工结论

CI 只产出机器可复算结果，例如：

```text
candidate: 591a266 / artifact sha256:...
implementation: 18 wired, 12 implemented, 21 specified
qualification claims: 4 L4, 7 L3, 13 L2, 27 <=L1 (all keyed by profile/scope/surface/provider/platform)
coverage units: 11/15
attempts: 19 total, 2 failed, 1 infra-invalid, 1 veto
candidate eligibility: CLOSED (lost-user-change in attempt 01JZ...)
document migration: 438/438 selectors adjudicated, 0 banner drift
```

禁止只输出 `all passed`、`3/3` 或“Phase 完成”而不暴露分母、失败历史、候选身份和适用范围。

## 11. 每次迭代的最小治理动作

开始前：

- 选择一个原子 capability id 和唯一 semantic authority port；禁止以 C6/C7 大组直接开工。
- 锁定 acceptance、profile、golden cases、baseline metrics 和 transitive dependency snapshot。
- 记录要迁移/删除的旧决定 paths，以及受影响的旧标题/REQ migration items。

实现中：

- `implementation_state` 只随实现事实变化；`qualification_claims[]` 由证据聚合器按精确作用域独立计算，无作用域 level 只作保守生成视图。
- 新 ADR 只记录不可逆或高影响决定；运行结果自动追加 attempt/manifest。
- 一次失败关联 taxonomy、trace 和 captured replay；不得覆盖旧 attempt 或修改 oracle 迁就结果。

完成时：

- 聚合器按有效 evidence 对每个精确 claim tuple 提升、保持、降低或失效，人工不能越级或扩大作用域。
- 更新一个 capability 条目、必要的 migration items 和一个 next-work-package。
- 生成全部视图，执行 schema/dependency/authority/evidence/migration/link CI。
- 旧 semantic authority 被封死、旧文档 banner 生效且退出条件证据完整后，才关闭专项。

这样，日常维护从“多份 Markdown 复制进度”缩减为“一个原子 ledger 条目 + 必要 ADR/profile + 追加式 evidence + 机器迁移清单”。

## 12. 当前文档包的自审标准

本目录交付前也必须满足：

- Codex/Claude 只引用官方公开能力，不声称内部实现。
- 所有 DevSeek 关键判断有本地文档、代码、测试或 Git 证据。
- 明确区分“原设计错误”和“方向正确但实现偏离”。
- 目标组件、原子能力、资格 profile、黄金旅程、证据和文档迁移能双向对应。
- `implementation_state` 与带 profile/Surface/Provider/平台作用域的 `qualification_claims[]` 不混用，semantic authority 不被实现成 God Service。
- 任何 attempt 都不可覆盖；日常证据继承与冻结 RC 配额边界明确。
- 没有把六个用户示例固化成竞品的固定流程。
- 没有把 deterministic 或 DeepSeek Web 某一局部测试写成产品稳定。
- 下一迭代能直接选出一个原子 work package，而不是再次全面研究。
- Markdown link、格式、schema、dependency 和未完成占位通过自动检查，并经过一次独立反证审查。
