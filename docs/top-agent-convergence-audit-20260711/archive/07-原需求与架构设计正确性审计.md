## 1. 直接回答：原来的设计是不是错了

不是全部错误，但不能继续整体视为当前正确基线。

最准确的判断是：

> 旧文档包含正确的工程原则、适合早期 DeepSeek Web 插件 MVP 的历史方案，以及已经被事实证伪的控制架构；三者没有及时分离和退役。正确服务越加越多，旧主链路仍然活跃，最终形成多 Loop、多状态机、多完成裁判和多写入入口。

应区分四类：

| 类型 | 含义 | 代表内容 | 处置 |
| --- | --- | --- | --- |
| A 正确原则 | 对顶级编程智能体仍成立 | 宿主执行工具/权限、Headless Core、Surface 解耦、证据高于模型自述、可恢复 | 合并进新基线 |
| B 方向正确但不完整 | 概念正确，owner、运行时契约或资格缺失 | TaskContract、WorkspaceEdit、Evidence、Memory、MCP、Skills、Subagents | 重构并接入唯一 Kernel |
| C 设计本身错误 | 即使实现完全也会导致分叉、越权或假成功 | 模型 Todo/`task_complete` 直接裁决终态、未经约束归一与宿主校验的自由文本直接写盘、`.gitignore` 当安全策略、Hook 当可信根 | 废止，不做兼容 |
| D 历史目标或状态过期 | 当时可用，但不适合当前顶级目标，或“已完成”被代码证伪 | DeepSeek Web/Copilot UI MVP、Phase 完备/已落地、fake benchmark 稳定 | 归档或撤销结论 |

## 2. 设计演进为什么没有收敛

### 2.1 目标升级但旧基线未退役

2026-04/05 的需求 03/04 面向“免费 DeepSeek Web VS Code 助手”，重点是网页 Bridge、Copilot 风格 UI、Markdown/diff/代码块解析。这对 MVP 有合理性。

当目标升级为 Codex/Claude Code 级编程智能体后，新的 requirement/architecture 又增加 Headless Core、权限、Evidence、Memory、Skills、MCP、Subagents 等能力；但旧路由、解析和完成判断没有被明确标记 deprecated，也没有迁移完成条件。

结果不是“新内核替代旧内核”，而是“新抽象包在旧 Loop 外面”。

### 2.2 服务清单先行，控制内核后置

原设计分别给 Workflow、Task、Provider、History、Engineering、Surface、Repair、RunContext 建状态或结算逻辑，却没有先规定：

- 只有谁可以迁移顶层任务状态；
- 只有谁可以执行副作用；
- 只有谁可以结算完成；
- 子状态与顶层状态冲突时谁优先；
- 新 owner 接管后如何删除旧 owner。

因此“单一 Core”是口号，物理设计仍允许多个控制中心。

### 2.3 需求、设计、实施日志和审计混写

需求 03/04 各包含大量“已实现/已完成/✅”，架构文档也同时记录状态、故障复盘和 Phase 结论。一个文件既是规范又是 changelog，就无法稳定回答“现在应该怎样”和“现在实际上怎样”。

### 2.4 评测底座被安排太晚

旧路线把任务回放和系统评测排到后期，先以类、按钮、prompt、fake tool 和单路径测试判断完成。结果是到了真实项目才暴露路由、mutation、validation 和 completion 不一致，再用更多规则修样例。

### 3.1 明确错误的需求假设

#### 模型 Todo 或结束词是完成权威

需求 02 第 95 行和需求 04 第 359～369、421～437 行一度让模型 Todo、`task_complete` 或“没有工具调用”决定任务结束。这与顶级 harness 的证据原则冲突。

正确设计：Todo 是 Kernel 事件投影；模型的 `task_complete` 最多归一为低信任 `CompletionRequested` proposal，只有宿主 `CompletionDecision` 对 `acceptance → evidence` 的结算能产生终态。

#### Chat/Plan/Agent/Auto/Full Access 是同一个 mode 轴

需求 02 第 113 行、需求 05 的 IntentDecision 把用户语义、工作流阶段、工具集合、确认策略和权限混成一个枚举。这个设计会自然产生关键词分类、路由分支和附件换 Loop。

正确设计：

```text
Task mode ≠ Workflow state ≠ Tool policy ≠ Authority envelope ≠ Sandbox profile
```

五者分别建模，由 Kernel 在同一生命周期中协调。

#### `.gitignore` 等于不可读写安全边界

需求 02 第 118 行、需求 10 第 23 行把版本控制忽略和安全策略混在一起。被忽略文件可能是用户明确目标、生成产物或本地配置；真正敏感文件也不一定在 `.gitignore`。

正确设计：区分默认搜索排除、显式目标覆盖、敏感 deny、workspace boundary 和 sandbox。

#### 多格式文本 fallback 被误当成可直接写盘的工具鲁棒性

需求 03 第 503～599 行允许 JSON → diff → 代码块 → 自然语言多级解析并写盘。它看似兼容，实际让不可信模型文本通过多个旁路产生副作用，也使 Provider 方言进入 Core。

正确设计：Provider Adapter 可以按该 Provider **明确、版本化、受约束**的协议把 JSON/XML/diff 等归一为低信任 typed proposal；随后仍须 schema/path/scope/permission/transaction 全链裁决。无法可靠解析的自然语言只能触发协议修复或降级为只读建议，不能猜测后直接写盘。因此错的是“多级猜测直接产生副作用”，不是 Adapter 拥有受测 compatibility parser 本身。

## 5. 架构设计中的关键矛盾

### 5.1 “单一 Headless Core”与至少五套全局状态机

- ARCH-01 第 24～32 行、ARCH-10 第 10～18 行要求 Headless Core。
- ARCH-03 第 127～165 行给 Workflow 一套 Planning/Editing/Validating/QualityGate 状态。
- ARCH-03 第 235～257 行又给 Task 一套 Proposed/Planned/InProgress/Validating/Done。
- ARCH-07 第 75～103 行让 Provider 进入 QualityChecking。
- ARCH-09 第 81～107 行让 Engineering Context 复制规划/编辑/验证状态。
- ARCH-10 第 201～220 行又给 Surface Planning/Running/Reviewing/Verifying/Completed。

子状态并非不能存在，错误在于没有定义它们只能是 Kernel 的投影/局部状态，不能调度全局工具或裁判终态。

### 5.2 Surface 解耦却由 Surface 提供业务决定

ARCH-10 第 124～166 行的 `AgentCommand` 让 Surface 传 `intent` 和 `permissionMode`；第 169～199 行的 CLI 时序让 Workflow、Permission、Runtime 直接与 CLI 交互。这违反同文的 Application Service/Event 边界。

正确设计：Surface 提交原始输入、上下文引用和**显式用户动作**（例如选择模式、批准/拒绝某个 scope）；Kernel 产生 orientation proposal，AuthorityGate 把 policy 与该用户决定组合成授权。Surface 可以传递决定，不能自行推断最终 intent/permission 或绕过 authority。

### 5.3 RunContext owner 放在 Extension

ARCH-17 第 39～55、109～120 行把 run 创建和 owner 放在 VS Code Extension。这直接违反 Headless Core：CLI 和未来 API 无法共享同一个运行事实。

正确设计：`AgentApplicationService/AgentKernel` 创建 run，Surface 只展示 `AgentEvent`。

### 5.4 Evidence append-only 与“清理旧失败”冲突

ARCH-17 第 57～64、143～153 行讨论最终成功后的 finding 清理/结算，但没有把“UI 不再显示 active finding”与“原始失败事件永久保留”分成两个模型。若按覆盖/删除实现，会丢失 repair lineage，并可能用 completion event 反向证明 completion。

正确设计：原始失败 event 永远保留；后续追加 `FindingResolved`/新 verdict，UI 只投影当前 active finding。可以收敛显示，不得删除或改写原事件。

### 5.5 Hook 被当可信安全根

ARCH-06 第 43～51 行和 ARCH-13 第 14～30 行把 Hook 作为敏感写入阻断的一部分。Hook 是扩展点，可缺失、失败或被配置，不应拥有最终安全保证。

正确设计：Permission + platform sandbox + path/network policy + mutation transaction 是可信根；Hook 只能 veto、warning 或补 evidence。

### 5.6 “验证只读”的边界需更精确

原文档正确指出质量检查不应偷偷修改用户交付物，但“验证阶段绝对不写任何文件”过于粗。编译、测试会合法地产生 `dist`、cache、coverage 和临时二进制。

正确设计：

- Verification Service 不得修改用户源交付物；
- verifier 产物进入隔离/声明目录并被 snapshot 分类；
- 需要修源码时必须创建新的 mutation transaction；
- 完成 diff 要区分 user deliverables 与 ephemeral build artifacts。

## 9. 最终设计纠正

下一版架构必须把以下规则提升为硬约束：

1. 只有 `AgentKernel` 能迁移顶层状态。
2. 只有一个 Settlement/Completion owner 能产生终态。
3. 只有 `WorkspaceMutationTransactionService` 能以短事务提交用户交付物变更；长任务由 saga/checkpoint 协调。
4. Terminal/MCP/Git/发布副作用也经过 Authority、Sandbox 和 Evidence。
5. Provider Router 不调用 ToolExecutor；Surface 不决定 intent/permission。
6. Evidence append-only；最终 verdict 可 supersede，不删除历史失败。
7. History、UI、Todo、ReviewLedger 是 Kernel 事件投影，不是事实裁判。
8. Skills、Hooks、MCP、Subagents 经过 trust、权限、预算、取消、隔离和结果合并契约。
9. requirement、architecture、implementation status、incident 和 test report 分文档管理。
10. 新 owner 接管后必须删除旧 owner，并以 CI 禁止重新引用。

这份裁决意味着接下来的工作不是在原文档后继续追加 Phase 13，而是先确认新的 Active Baseline，再按能力轨逐项迁移和废止旁路。
