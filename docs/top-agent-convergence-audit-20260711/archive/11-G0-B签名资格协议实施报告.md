## 1. 结论先行

G0-B 已把 Golden Case Catalog、Qualification Profile、Candidate Identity、预注册 Plan、追加式事件、store/action receipt 和外部动作 guard 落成一个机器可校验的本地协议纵切。Catalog 与 Profile 已接入默认 Phase 0～12 门禁，能力状态可记为 `wired`；Plan/store/guard 已实现并通过确定性攻击测试。2026-07-12 的后续纵切又接入了 `1` 个本地 nonqualification composition root，但 `4` 个 production 入口仍 qualification-disabled，因此 Plan 的机器状态仍只能记为 `implemented`，不能写成 protected runner 已 wired。

运行时 Store 不再信任注册请求携带的自哈希 Profile/Catalog：它在构造时校验并固化批准的 governance anchor，重启后若 profile/catalog/key-registry 任一身份变化则 fail closed。Plan、event 和 receipt 在实际写入/读取边界执行与 checker 同源的严格 JSON Schema，不再只验证 factory 样例。

本轮证明的是：在当前本地实现和测试信任边界内，计划、事件、角色、slot、retry 和动作授权可以 fail closed、确定性复算，并能阻断已覆盖的篡改与竞态。它没有证明：DevSeek 已成为顶级编程智能体、真实 DeepSeek 网页资格已通过、任何 capability 已达到 L 级，或外部系统中的真实副作用恰好发生一次。

### 3.1 机器事实层

- Catalog 固定 case identity、fixture、executor entrypoint 和对应测试源文件内容 SHA-256；测试源变化但 catalog 未重生成会触发 drift failure。
- Profile 固定 required cases、最小 1000 coverage slots、最小 1000 deterministic traces、slot role、retry policy、允许动作与 qualification eligibility。
- Candidate/Plan 将 commit、source tree、artifact、prompt、runtime、connector、dependency、environment、profile 和 catalog 等 identity 纳入签名绑定。
- JSON Schema 使用严格校验；额外字段、未知版本、无效 hash、缺项或枚举外值均拒绝。

### 3.2 签名与完整性层

- plan、event 和 receipt 使用 `devseek-canonical-json/v1` 与 SHA-256，签名采用 Ed25519。
- 签名材料同时绑定 algorithm、domain、purpose、key id、signer identity、registry hash 和 payload，防止只校验公钥而混淆角色。
- 六种 purpose 使用不同 key material；重复 key material、错误 purpose、未知算法和篡改内容均 fail closed。
- event 保存 correlation、sequence、previous event hash、plan/candidate identity；store receipt 再绑定 event/hash/head 与 store 可信时间。

### 3.3 追加、顺序与重试层

- 本地 store 以不可变记录文件、hard-link compare-and-create、文件与目录 `fsync` 实现进程间 CAS；相同事件重试幂等，冲突 identity/head 拒绝。
- campaign/plan/session/correlation 和目录 identity 交叉绑定，不能把另一个 session 的合法记录复制为当前流记录。
- 全局 slot 按 plan order 消费；preflight role、reservation、branch disposition 与 coverage retry 是签名的持久状态，不依赖临时内存判断。
- infra retry 必须引用原失败 event/hash/class、独立 adjudication actor、evidence hash 和 reason；唯一 retry slot、24 小时边界和 primary/retry 分支终态均受约束。
- 成功 primary 也必须写入显式 `SlotBranchSkipped`，避免“没有 retry 文件”被误读为已关闭分支。

### 3.4 外部动作边界

- browser/auth/network 调用前必须先验证 plan、profile、slot reservation、event head、动作类型/目标与有效窗口。
- guard 先追加签名 `ExternalActionAuthorized`，动作 receipt 与该授权事件 hash 绑定；执行时原子消费动作 key，并在调用 adapter 前追加 `ExternalActionStarted`。
- 相同授权请求返回同一授权 receipt；重复执行只能有一个调用方取得 dispatch 权。
- 这实现的是本地 guard 对 callback **dispatch at-most-once**。进程在发起调用后崩溃、网络超时或远端已提交但本地未知时，真实外部 effect 仍可能是 `indeterminate`；没有远端 idempotency key、outbox/reconcile 和 provider receipt 前，不能宣称真实 effect exactly-once。

## 4. 反证与测试

主验证命令为 `npm run verify:qualification-protocol`，同时已接入 `scripts/devseek-phase0-12-verify.mjs` 的 `qualification-protocol-conformance` gate。

| 测试族 | 被阻断的缺陷类别 |
| --- | --- |
| 严格 schema conformance | runtime plan/event/receipt/key registry 与 schema 分叉、额外字段、未知格式 |
| governance trust anchor | 运行时替换自哈希 profile/catalog、profile ID 错绑、降低 coverage/required-case 约束 |
| purpose-separated Ed25519 | plan/event/store/guard/oracle/adjudicator 角色混用、未知算法、内容篡改、重复 key material |
| plan completeness | 0/999 coverage、缺 required case、重复 role；1000 边界为有效下限 |
| event verification | 断链、错误 plan/candidate/correlation、签名或 hash 不匹配 |
| durable CAS | 重复 append、head 冲突、identity 冲突、跨 session copy、临时 receipt 混入 |
| global slot order | 越序 preflight、双 reservation、未裁决 retry、伪造 retry 引用 |
| aggregate retry state | primary 与 retry 并跑、final 后再跑、失败覆盖、缺 branch disposition |
| explicit branch close | primary 成功但未写签名 branch-skip 时拒绝进入后续 slot |
| action guard | 1024 条确定性无效前缀均为 callback 0；过期、stale head、篡改 receipt 拒绝；receipt-first 崩溃窗可确定性恢复；重复授权幂等且 dispatch 只有一个 winner |
| trusted-time boundary | receipt 过期与本地 clock rollback 在 callback 前失败 |
| multi-process CAS | 12 个并发进程竞争同一 key 时只有一个 winner |

这些测试是 deterministic/local protocol-conformance evidence。它们不包含 live Provider、真实 UI、保护 runner、正式项目或 holdout 证据。

## 5. 诚实限制与未关闭风险

1. **Local-only trust**：当前 key registry 明确写入 `integrity_scope=local-protocol-conformance`、`qualification_eligible=false`；私钥/公钥是测试资产，不是组织独立的生产密钥体系。
2. **非独立可信时间**：可信时间 high-water mark 可阻断已观察到的本地回拨，但同一主机上的高权限操作者仍可删除或整体替换存储；它不是独立时间戳服务。
3. **非 WORM**：不可变文件、hard-link CAS 与 `fsync` 解决本地并发/崩溃一致性，不等于 retention lock/WORM，也不抵御拥有文件系统写权限的恶意删除。
4. **签名方不独立**：purpose separation 防角色误用，但本地 fixture keys 不满足开发者、runner、oracle、adjudicator、aggregator 的组织职责隔离。
5. **clean-tail 无外部锚**：链内篡改、断链和错误前驱可检测；删除当前流完整尾部后，仅靠流内剩余记录无法知道曾经存在更长尾部。G0-C 已实现把预期 event/run head 冻结进签名 Evidence Manifest、引用 G0-D sealed Run Evidence head 并在缺锚/head 不一致时 fail closed 的 reader；但仓库内本地 anchor 仍不是外部可信锚，因此仍不得聚合 protected claim。
6. **只有本地 runner 纵切**：`GuardedQualificationActionAdapter` 已由唯一 test-fixture composition root 走通；inventory 另含 10 个 catalog metadata、4 个 production-disabled 和 4 个 historical-disabled 条目。catalog 不是 runner，生产受保护资格执行仍未启用，因此 Plan 只能记为 `implemented`。
7. **没有任何资格 claim**：本轮三项能力的 `qualification_claims[]=[]`、`qualification_level_view=null`；Gate 0 仍为未通过，R1 不得提前开始。
8. **本地信任根与 entrypoint 证明**：audited mode 已把 profile/catalog/registry 精确 digest 固定在运行时并由 checker 反向校验，可阻断 fresh-root TOFU 替换；但它仍与代码同属本地 repo，不是外部独立信任根。Catalog 已绑定整份测试源码字节，G0-C 也已实现独立复算协议，但每个声明 entrypoint 仍缺真实 protected runner 的不可绕过执行证明；本轮不因此授予 claim。

## 6. 依赖顺序与当前检查点

G0-C 的 Manifest 必须冻结可重放的 product-run evidence head。如果先写聚合器再统一 Run Evidence Ledger，Manifest 会被迫绑定 TaskHistory、ReviewLedger、extension JSONL 等多个不等价头，随后还要重做一次 schema 和迁移。因此裁决的最短依赖顺序是 G0-D → G0-C；截至 2026-07-12，这两个本地实现纵切均已完成：

1. **G0-D（已完成产品诊断纵切）**：统一 `RunEvidenceLedgerPort` 已形成 run/command/side-effect/verifier/terminal 的 sealed head，旧记录只通过显式投影迁移为 `legacy-unverified`；它仍非 WORM/资格证据。
2. **G0-C（已完成本地确定性纵切）**：独立复算 reader 消费 G0-B 签名计划/事件和 G0-D sealed run head，生成签名 Evidence Manifest/retention lock；执行分母守恒、veto、失效和逐 tuple candidate 派生。仓库 policy 为 test-only/local 且 claim rules 为空，所以没有 claim，详见 [13](13-G0-C资格证据清单与独立聚合协议实施报告.md)。
3. **Gate 0 复核（未通过）**：只有七个 C0 节点都满足机器 profile 要求并取得有效精确 tuple claim，才可宣称 Gate 0 通过并进入 R1；当前无 live、R1 禁止。

## 7. Gate 0 交接与禁止绕过项

下一步不再是“只实现 G0-C”或重复实现本地 runner，而是按 [14](../14-未完成事项与后续整体迭代计划.md) 逐卡闭合 Active Baseline、profile executor、在线 candidate identity、五个 C0 repository wiring blocker、独立 protected trust/retention 与精确 tuple claim，再执行机器 Gate 0 复核。不得把已完成的本地协议、exact-VSIX 或用户窗口仿真包装成正式资格；以下不变量继续有效：

- 不使用旧 `3/2/1` observation、测试通过次数或生成 Markdown 产生 claim。
- 不让产品 Run Evidence Ledger 自行签发资格 verdict；产品事实与资格裁决分离。
- 不接受未注册 plan、跨 candidate/profile/catalog/event head 的证据拼接。
- 不通过重跑成功覆盖旧失败，不允许 infra 标签吞掉 connector/product failure。
- 不把 callback at-most-once 写成 external effect exactly-once。
- 不以降低 profile、人工改生成物、平行 runner 或忽略缺失证据来“通过”Gate 0。
