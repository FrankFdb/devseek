# DevSeek 决策结论与最短收敛实施方案

- 日期：2026-07-11
- 用途：下一迭代窗口的直接实施输入

## 1. 最终方向决定

DevSeek 下一阶段不再以“增加顶级能力数量”为目标，而以“让已有能力穿过一个不可绕过的 Coding Kernel”为目标。

总决策：

> 冻结 P2 功能扩张；先以简单 create/modify/repair 三条真实用户旅程建立唯一 Kernel、权限、mutation、verification、completion；再逐项把意图、需求、上下文、设计、恢复和扩展能力迁入，最后才运行未见正式项目。

这不是推倒重写。现有 Provider Runtime、Bridge、TaskContract、Evidence、RunContext、WorkspaceEdit transaction、replay 和真实插件 harness 都可作为资产；需要删除的是多主链、旁路和错误完成口径。

## 2. 少迭代的五条方针

1. **一个能力焦点**：每个专项只有一个主能力和一个 owner；依赖能力只接最小 seam，不同时宣称完成。
2. **一个纵向真路径**：每项能力必须通过真实入口→Kernel→行动→证据，而不是只增加类和 unit test。
3. **一次 live 采集，多次 replay**：网页/模型失败只采集一次，之后用捕获流定位和修复，冻结候选后再 live。
4. **迁移即删除**：新 owner 接管就删除旧分支、parser、writer 或 completion；减少后续组合测试量。
5. **状态自动生成**：只更新能力账本、ADR、evidence manifest，避免每次同步十几份文档。

目录共有 15 个领域：C0 运行证据/评测地基、C1～C13 十三个实现能力域、C14 综合资格。它们不等于 15 次大版本或 15 个 Agent；实施合并为四个收敛里程碑，但 06 中每个原子 capability 仍独立晋级，C14 不能掩盖某个原子失败。

## 3. 四个收敛里程碑

| 里程碑 | 主目标 | 纳入能力 | 必过旅程 | 完成后删除 |
| --- | --- | --- | --- | --- |
| R1 基础 Coding Kernel | 简单编程不再因入口/附件回退，副作用和完成事实唯一 | 04 Gate 0/1 root targets 的 ledger 依赖闭包 | D-G01 create、D-G02 modify、D-G03 repair、D-G04 dirty workspace | VS Code 附件选 Loop 分支、CLI 独立 writer/verifier、对应 legacy mutation/completion owner |
| R2 软件工程大脑 | 需求、上下文、探索、设计成为同一 Kernel phase | C2～C5、C8 的适用原子项 | D-G00、D-G05、D-G06、D-G09 | Intent/Router/Decomposer 的重复语义 owner、领域词特判、独立 Architect Loop |
| R3 可靠性与规模 | 中断恢复、长上下文、可控扩展、独立 review | C10～C13 的适用/conditional 原子项 | D-G07、D-G08-CANCEL、D-G08-RESUME、D-G10～D-G14 | 旧 checkpoint/recovery 分支、未接线 Skills/Hooks/Subagent 壳或旁路 |
| R4 冻结资格 | 真实用户 UI、live Provider、holdout 与竞品盲评 | C14 | 3 canary、2 medium、1 formal；随后 excellent set | 临时兼容 flag、开发用 oracle 泄漏、易失证据路径 |

里程碑内部允许多个小提交，但只进行一次候选 live 晋级。这样保留软件工程可审查性，又避免每个小修都打包、登录网页、跑 formal。

## 4. 现有实现到目标模块的迁移映射

| 现有资产 | 目标去向 | 判断 |
| --- | --- | --- |

## 5. Gate 0 通过后的工作包：R1-KERNEL-DG01-03

2026-07-12 实施检查点：G0-A 已落地 76 项 capability、138 条 typed edge、milestone profile、45 项 R1 目标 manifest 和默认漂移门禁；G0-B 已完成本地签名计划/事件/receipt/guard 协议纵切；G0-D 已把统一 Run Evidence Ledger 接入 CLI/JSONL、VS Code 与 Bridge 产品入口；G0-C 已实现本地 Evidence Manifest、独立复算 reader 与 append-only CAS retention 协议。Catalog/Profile 的实现状态为 `wired`；Capability Ledger、Plan、Run Evidence Ledger、Evidence Manifest 与 Aggregator 均保守记为 `implemented`。七项全部 `qualification_claims=[]`、`qualification_level_view=null`，本轮没有 live。当前工作是闭合真实 runner、独立 protected trust/retention、冻结 candidate 与精确 tuple 资格缺口，而不是继续“只实现 G0-C”；边界见 [13](13-G0-C资格证据清单与独立聚合协议实施报告.md) 和 [12](12-G0-D统一运行证据账本实施报告.md)。Gate 0 七项未按精确 tuple 达到 wired/L2 前，本节 R1 切片不得开始。

### 5.1 目标

在不增加新平行 Loop 的前提下，让以下自然请求走同一控制链：

- “在当前项目创建一个最小可运行程序”；
- “修改已有函数并保持原行为”；
- “根据当前失败测试修复问题并重新验证”。

三者在无附件、有附件、VS Code 和 CLI 下使用同一 TaskContract、Kernel state、mutation、verification 和 completion。

### 5.2 开始前冻结的事实

- 当前基线 commit 和 dirty state；
- `extension.ts`、两个 VS Code Loop、CLI Loop、writer、validator、completion 的 reachability map；
- D-G01～D-G03 自然 prompt、fixture、acceptance、expected diff、verifier；
- 当前失败表现和事件序列；
- 要删除的 legacy owner allowlist。

本工作包只手写 root targets：`C0-QUALIFICATION-AGGREGATOR`、`C1-SURFACE-ADAPTER-CONFORMANCE`、`C6-PROVIDER-NORMALIZATION`、`C6-DEEPSEEK-WEB-CONNECTOR`、`C7-DIRTY-WORKTREE`、`C7-PLATFORM-ADAPTER-CONFORMANCE`、`C8-INTEGRATION-CONFORMANCE`、`C9-BOUNDED-REPAIR`、`C9-REGRESSION-SELECTION`、`C10-DELIVERY-MANIFEST`。但开工 manifest 不得把 06 表的纯 ID“直接依赖”列当作全部同级工作清单；必须先在 Gate 0 实体化 typed architecture edge 和下列 `R1-MINIMAL-SEAM/v1` milestone profile，然后才能自动展开、冻结和执行：

| 节点类型 | 匹配 | 最低 implementation state | 最低 qualification | R1 含义 |
| --- | --- | --- | --- | --- |
| Gate 0 root | `C0-QUALIFICATION-AGGREGATOR` 及 typed 依赖 | wired | L2 | 计划/事件/聚合器属性测试通过 |
| Gate 1 roots | 上述 C1/C6/C7/C8/C9/C10 root targets | wired | L2 | 完成切换和 deterministic/replay 门禁，不声称 L4 |
| 工程脑 seam | 闭包中 `C2-*`、`C3-*`、`C4-*`、`C5-*` | wired | L1，profile scope=`r1-minimal-contract-v1` | 只支持 D-G01～D-G04 最小 contract/context/plan；R2 再以完整 corpus 升 L4 |
| 其他传递依赖 | typed edge 展开结果 | 取所有路径最严格值 | 至少 L1，若 profile edge 更严则从严 | 不得靠默认值或人工降级 |

manifest 每个 capability 记录必须包含 `capability_id/requirements[]{required_implementation_state,required_claim{profile_id,profile_sha256,claim_scope,surface,provider,platform_profile,minimum_level}}/work_mode(root|seam)`，并以 `architecture_requirements[]` 保留每条 `required_by/relation/required_implementation_state/contract_sha256`；relation 不可相互排序，不能压成一个字符串。`required_implementation_state_view` 仅供浏览，不参与裁决。多路径只对同一精确 claim tuple 的 state/level 取最严要求，不同 Surface/Provider/平台必须保留为不同 `requirements[]` 元素；每条 `selection_path` 仍保存一个完整 tuple 和有效 state，禁止合并、覆盖或丢失。同时保留所有依赖理由，并冻结整份 manifest hash。当前种子中 Gate 0+1 纯拓扑闭包是 45/76 项；这只说明依赖可达，不表示 R1 要把 45 项全部做到 L4。任一 edge 未类型化、profile 缺失、priority/applicability 未决议或生成闭包与冻结 hash 不同，都不开始重构。一条 development live canary 只是线路观测，不构成 Connector L5、任一原子 L4 或产品 stable claim。

没有这份 baseline，不开始重构，避免完成后无法证明 owner 真的减少。

### 5.3 实施切片

**原子 cutover 硬约束**：Slice A～D 只允许在同一个未发布迁移候选中递进。A～C 之间明确不执行面向日常用户的 package/install/release，也不把局部新路径作为产品版本交付；仓库默认 release loop 延后到 Slice D 全入口 cutover 后只执行一次。临时 legacy adapter 只能是无业务语义 delegator，不得写盘、双写、产生终态或按任务 fallback。rollback 只能重新部署/安装上一份已签名完整 artifact/version；当前 artifact 不得包含旧 Kernel 或 runtime dual flag，禁止新旧 Kernel 按 case/附件并存。发布前，VS Code/CLI/声明命令等所有产品入口必须一次性通过 reachability/conformance，旧 semantic owner `=0`。

#### Slice A：控制 seam 与真实 D-G01

1. 定义最小 `TaskContract`、`AgentCommand/Event`、Kernel state、terminal decision。
2. 在未发布迁移候选中让 D-G01 经 `AgentApplicationService`；VS Code/CLI 只适配命令和事件。
3. 附件作为 `ContextRef[]` 输入，不参与 runtime/loop 选择。
4. 从现有通用循环提取逻辑，不再新建 `simple-file-task` 或 fallback。
5. D-G01 所有写入经 workspace transaction，执行 readback 和适用编译/运行。

Slice A 只达到纵向可运行，不宣称 C1/C7/C9 全部完成。

#### Slice B：D-G02 mutation 完整性

1. 把 edit/delete/mkdir/move/undo 和 CLI 写入接到同一 mutation port。
2. 捕获 baseline、CAS conflict、commit token、readback、rollback。
3. 加入脏工作区、用户并发修改、权限拒绝和 resume fault injection。
4. 删除已迁移 legacy writer；CI 禁止再次 import。

#### Slice C：D-G03 验证与完成唯一化

1. Engineering Context 只接最小 build/test discovery seam。
2. 合并 verifier plan/result；无 verifier 不返回 passed。
3. 失败 evidence 进入 diagnosis→execution→reverify，不由固定两轮控制。
4. Settlement 逐项对账 acceptance；`waiting-user` 保持可恢复，只有 completed/failed/blocked/cancelled 是终态。
5. 删除旧 validator/repair/completion owner 和错误 `agent-run-completed` 事件用法。

#### Slice D：Surface 收口与里程碑证据

1. Headless conformance 全绿后，VS Code/CLI 跑同一 D-G01～D-G03 cases。
2. 更新 VSIX，验证 installed identity。
3. 运行一个真实自然 UI canary；失败先捕获 replay，不立刻扩 live。
4. 达到退出指标后更新 ledger 的实现状态和由证据推导的等级；只记录 R1 milestone pass，不人工写 L4，然后才开始 R2。

### 5.4 明确不在范围内

- 不实现真实 Subagents、Skills、Hooks、Git PR、自动发布。
- 不增加新的 formal/UAV/license/Markdown 规则。
- 不全面重写 Memory 或 Engineering Context。
- 不用“保留 fallback 更安全”为理由长期保留旧 owner。
- 不运行正式项目 holdout。

### 5.5 必跑测试

| 层 | 用例 |
| --- | --- |
| unit/property | state transition、TaskContract revision、permission、CAS、idempotency、completion mapping |
| captured replay | valid/invalid/duplicate/partial DeepSeek tool stream；Provider disconnect |
| Headless | D-G01～D-G04，附件 metamorphic variant，权限拒绝，验证失败 |
| Surface conformance | VS Code、CLI 同 fixture、同领域事件、同 terminal decision |
| architecture | Kernel/owner/dispatcher/mutation/completion 数量；forbidden imports |
| candidate live | 冻结 commit 的 D-G01 natural UI 一次；不使用 strict tool-call prompt |

### 5.6 R1 退出指标

```text
D-G01/D-G02/D-G03 same-semantic result across attachment variants = 100%
product task entry owner = 1
D-G01-D-G03 mutation bypass = 0
D-G01-D-G03 permission bypass = 0
validation rewrites user deliverables = 0
success without acceptance evidence = 0
lost user changes = 0
duplicate side effects after resume = 0
all declared product entrypoints reach unified Kernel = 100%
legacy semantic owners reachable from declared product entrypoints = 0
Headless + VS Code + CLI conformance = passed
R1 conformance profile = smoke-only; L4 claim = false
```

若任一硬指标不满足，R1 不能通过；不能用 prompt 特判或新增 fallback 降低失败率。

## 6. 每项能力如何真正“对标极致”

对每个 C2～C13 后续专项，使用相同模板：

1. 选一个公开可观察的 Codex/Claude 优秀行为和 5～20 个最小 fixture。
2. 测 DevSeek 当前基线，列出全部语义 owner 和旁路。
3. 只定义一个目标 owner、contract 和独立 oracle。
4. 微测试通过后接入一个真实纵切，不新建 Loop。
5. 删除旧 owner，运行全部既有黄金旅程。
6. 取得 L4 Surface 资格后，冻结 wave 做少量 live。
7. 最终 holdout 用自然需求盲评正确性、安全、证据和效率。

“极致”不按功能开关数量定义，而按硬结果定义：更少用户干预、更少上下文/工具浪费、无安全旁路、无假成功、无回归、失败可恢复、证据可复算。

## 7. 决策门禁

进入 R1 前还需确认三件事：

1. 接受 `AgentKernel` 为唯一顶层控制 owner；
2. 接受迁移后删除旧 Loop/owner，不长期双轨；
3. 接受正式项目延后到 P0/P1 Surface 资格完成，但小型黄金旅程从第一天持续运行。

当前下一窗口不重做方向研究，也不重做已完成的 G0-A/B/C/D 本地纵切；它只处理 [13 第 8 节](13-G0-C资格证据清单与独立聚合协议实施报告.md#8-gate-0-交接不是-r1-开工许可) 已列出的 Gate 0 资格缺口与机器复核。本地协议、产品诊断账本和 35/35 聚合攻击测试都不等于 wired/L2 claim。只有 Gate 0 已通过且上述三项成立，才执行 R1-KERNEL-DG01-03，并以本文件的退出指标结束该里程碑；在此之前无 live、R1 禁止。
