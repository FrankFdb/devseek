## 3. 动态基线、提交与制品身份

### 3.1 先解析包含接管文档的提交

一次 Git 提交不能在自身内容中嵌入自己的最终 hash；VSIX 又必须在提交后构建，因此 tracked Markdown 不保存会自我失效的 hash。以包含本文的最近提交作为本轮 source handoff identity：

```bash
HANDOFF_DOC=docs/top-agent-convergence-audit-20260711/15-新窗口与跨模型接管手册.md
HANDOFF_COMMIT=$(git log -1 --format=%H -- "$HANDOFF_DOC")
printf '%s\n' "$HANDOFF_COMMIT"
git show --stat --oneline "$HANDOFF_COMMIT"
git status --short --branch
git diff --name-status
git diff --cached --name-status
git diff --check
```

已提交历史锚点：

| 身份 | 事实 |
| --- | --- |
| `fd7b4f0` | G0-A 机器能力收敛门禁 |
| `de896a6` | G0-B 签名资格协议 |
| `$HANDOFF_COMMIT` | 包含 G0-C/G0-D、产品接线、测试、生成物和 12～16 的统一 source integration；必须动态解析，不猜 hash |

若 `HANDOFF_COMMIT` 不可解析、本文只存在于未提交工作树、或出现未解释的 tracked dirty/staged 内容，停止后续修改，先恢复真实接管边界；禁止 reset、clean、stash、rebase、amend 或覆盖用户改动。

### 3.2 动态复核 Phase 与 VSIX

```bash
REPORT_DIR=docs/testing/phase0-12-verification-reports
find "$REPORT_DIR" -maxdepth 1 -type f -printf '%T@ %p\n' 2>/dev/null | sort -nr | head -5

VSIX=devseek-netai-latest.vsix
sha256sum "$VSIX"
unzip -p "$VSIX" extension/package.json | \
  node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const p=JSON.parse(s);console.log(JSON.stringify({version:p.version,devseekBuild:p.devseekBuild},null,2))})"
npm run verify:packaged-bridge -- "$VSIX"

find "$HOME/.vscode/extensions" -maxdepth 2 -path '*/devseek-netai.devseek-netai-*/package.json' -print
```

Phase 报告必须对应 `$HANDOFF_COMMIT`；VSIX 内 `devseekBuild.gitCommit` 必须等于它；已安装扩展的 version/buildId/gitCommit 必须与 VSIX 一致。忽略目录中的报告或 VSIX 若不存在，不代表 source 任务回退：先确认 clean checkout 指向 `$HANDOFF_COMMIT`，再按 AGENTS 从该 commit 重建、验证和安装，不修改源码或文档。

## 5. 集成身份成立后的唯一原子任务：`G0-RUNNER-WIRING`

### 5.1 用户结果

任一被声明为 qualification runner 的入口，在执行任何 slot/case/Provider/Surface 动作前，必须消费同一个已验签 plan/session/attempt 注册与 guard；运行后必须产生完整 event/receipt，并只由 G0-C independent reader 聚合。缺任一前置时外部动作数量必须为零。

### 5.2 Authority 与边界

- G0-B 是 plan、event、receipt、guard 的协议 authority；
- G0-C 是 Manifest、retention 和 independent aggregation authority；
- G0-D 仅提供非资格产品诊断，不能替代或签发 claim；
- runner composition root 只负责接线，不得重写验证、资格或 settlement 语义；
- CLI、VS Code、脚本、Surface adapter 不能各自实现第二套 guard/reader。

### 5.3 最小实施顺序

1. 从 11/13 与实际 composition roots 建**声明 runner 入口清单**，区分 production、test fixture、historical/disabled；不先全仓重构。
2. 为每个 production/declared entry 画 reachability：entry → plan verify → session/slot register → guard → external action → signed event/receipt → G0-C reader。
3. 先固化旁路反例：缺 plan、错误 session/attempt、未注册 slot、过期/revoked key、receipt 缺失、直接调用 adapter 时，callback/Provider/Surface 动作均为 0。
4. 只在 composition root/统一 runner port 接线；重复入口改为无语义委托或删除。
5. 添加静态 import/reachability guard，禁止新入口直接绕过 G0-B/C。
6. focused → package full → independent review → Phase 0～12；行为影响 Extension/Bridge 时执行默认本地 release loop。

### 5.4 退出门

```text
declared_runner_inventory_coverage = 100%
guard_and_reader_reachability = 100%
known_bypass_count = 0
unregistered_external_action_count = 0
missing_receipt_or_attempt_silently_passed = 0
independent_review = P0 0 / P1 0
qualification_claims = []
gate_0 = NOT_PASSED
r1 = NOT_STARTED
```

完成 runner wiring 仍只能写 `implemented/wired locally but unqualified`。缺外部 trust plane 时下一步是 blocked/并行申请 authority，不是伪造 policy、key、retention 或 claim。

## 6. 固定工程作业顺序

1. 先写本轮作业卡：atomic ID、用户结果、authority、contract、sibling、删除项、focused/full gates、停止条件。
2. 保存 branch/HEAD/dirty/installed baseline；所有既有 dirty 内容视为用户资产。
3. 构造最小失败证据，再修改唯一 authority；同类失败必须提高 abstraction/Schema/static guard。
4. 检查 sibling entrypoint、state、persistence、recovery、protocol、UI 和 legacy path。
5. 从便宜到昂贵验证：focused → affected package → architecture/generated drift → independent review → Phase 0～12。
6. 在统一 source commit 前完成 12～16、README 与机器 SSOT，再由集成 owner 审计 staged diff 并提交；子代理不得 commit/package/install。
7. 从该 commit 重跑 Phase；行为变化按 AGENTS 执行 compile → package exact VSIX → packaged Bridge verify → SHA-256 → local install → installed identity。
8. 安装后只产生动态回执、Phase 报告和最终交付身份；不为回填 commit/VSIX hash 创建第二个混合 Markdown 提交。

完整 DoD、Skills 晋级和停止规则以 16 为准。

## 7. 权限、外部动作与禁止重复

无需新增授权：本地只读发现、代码/测试修改、deterministic/replay、compile、local commit、package、packaged Bridge verify、local install。

必须另获明确用户授权或外部 authority：

- DeepSeek Web/真实 Provider、浏览器登录、network live、natural UI、canary/medium/formal、holdout；
- Codex/Claude 账号调用或可能消耗配额、触发条款/数据出境的动作；
- protected policy、生产密钥、WORM/retention、trusted time、独立 signer/评审职责；
- push、PR、marketplace 发布或修改远端/共享基础设施。

禁止重复：重做 G0-A/B/C/D、重做 01～09 全仓审计、按 ARCH-18 旧顺序进入 P0-MUTATION、用补跑覆盖失败、人工编辑生成物、降低 profile/分母、把 product diagnostics 当 qualification、建立 parallel owner 或 runtime dual-track。

## 8. 异常处理

| 情况 | 必须处理 | 禁止处理 |
| --- | --- | --- |
| dirty/staged 与快照不同 | 重新读取 diff，识别当前任务边界 | reset、clean、覆盖或假定是垃圾 |
| focused/full 失败 | 保存命令、首个根因和最小 replay，回唯一 authority | 弱化断言、跳 suite、标 flaky 后继续 |
| Phase 失败 | 不提交/不打包，按 gate 回 focused | 用旧报告或别的 commit 顶替 |
| package/installed identity 不一致 | 停止，重建精确 commit 并核对包内 metadata | 修改文档假装一致、混用旧 VSIX |
| 文档与机器 SSOT 冲突 | 机器 ledger/schema/实际证据优先，登记 superseding fact | 用 Markdown 提升状态或 claim |
| 外部 authority 缺失 | 标记 `blocked-by-external-authority` | 用本机 fixture 自签、自批 |
| P2 在当前任务中被触发 | 若复现 P0/P1，升级并收口 defect class；否则留在 14 | 无范围顺手重构或删除 backlog |

## 9. 永久资格边界

```text

gate_0: NOT_PASSED

```

`canary 3/3、medium 2/2、formal 1/1` 是旧 development observation/未来 RC smoke 口径，不是 Gate 0、stable 或 top-tier 资格。G0-D 永远是 `product-run-diagnostics`，不能自行签发资格 verdict。

## 10. 跨模型执行与输出契约

任何模型都必须：

1. 区分 repository fact、test evidence、inference 和 proposal；竞品变化事实只用官方公开来源。
2. 每次只认领一个 atomic capability/defect class，先说明 authority、范围、非目标、sibling 和退出门。
3. 报告实际命令、精确计数、未运行项与环境限制；不沿用旧聊天数字替代本轮结果。
4. 不因模型更换重写设计、清理 dirty worktree、重复 live 或改变 qualification state。
5. 最终交付顺序固定为：结果 → 改动 → 验证/独立复审 → commit/artifact identity → 未运行/风险 → 资格边界 → 下一原子任务/暂停。
