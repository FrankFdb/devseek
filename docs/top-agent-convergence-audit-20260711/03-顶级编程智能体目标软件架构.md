# DevSeek 顶级编程智能体目标软件架构

- 日期：2026-07-11
- 架构代号：Converged Coding Kernel
- 适用 Surface：Headless、VS Code、CLI、后续 API/CI
- 接管定位：candidate 目标架构；组件和契约存在不等于 active/wired/qualified，实际执行使用 14 的 atomic leaf

## 1. 目标与非目标

### 1.1 目标

建立一个面向真实软件工程任务的统一内核，使简单创建、局部修复、跨文件功能、正式项目交付都共享：

- 一个任务契约；
- 一个状态机；
- 一个权限策略点；
- 一个工具执行协议；
- 一个 workspace-mutation semantic authority，以多个短事务组成可恢复 saga；
- 一个验证与修复闭环；
- 一个完成事实；
- 一个 checkpoint、trace 和 replay 模型。

### 1.2 非目标

- 不复制或声称知道 Codex、Claude Code 的闭源内部架构。
- 不要求每个简单任务生成完整需求、设计和发布文档。
- 不以增加更多平行 Agent Loop 实现“专业分工”。
- 不在基础 Coding Kernel 稳定前扩张无人使用的高级功能壳。
- 不把模型文本、自报成功、mock 通过或 static grep 当成宿主事实。

## 2. 十条架构原则

1. **单一内核**：所有 Surface 调用同一个 `AgentKernel`，不能自行编排编码循环。
2. **Context 不选引擎**：附件、选中文本、打开文件只增加上下文，不改变权限、mutation、验证和完成内核。
3. **模型提议，宿主裁决**：模型可提出计划和工具调用，宿主负责策略、执行、观察和终态。
4. **契约先于完成**：目标、交付物、约束、非目标和验收方式必须进入 `TaskContract`。
5. **分类后的单一副作用边界**：write/edit/delete/mkdir/move/undo 只通过 `WorkspaceMutationTransactionService`；terminal/network/MCP/Git/release 只通过 `ExternalEffectService`，两者共享 Authority/Evidence。
6. **证据先于声明**：无适用 verifier 时必须报告 `unverified`，不能默认 `passed`。
7. **失败向上游路由**：验证失败回到诊断/实现，权限缺失回到 authority，需求不清回到 contracting。
8. **可暂停、可恢复、幂等**：每个副作用前后都有 checkpoint 和幂等键，恢复不重复执行已提交动作。
9. **扩展不替代内核**：Skills、Hooks、MCP、Subagents 只能通过注册接口扩展同一内核。
10. **迁移即删除旧 owner**：每迁移一个纵切，必须删除或封死等价旧入口，并由静态门禁阻止回流。

依赖只能向下。Surface 不得引用 Loop、Workspace 写入实现或 Provider 方言；Adapter 不得宣布任务完成；Extension 不得建立自己的任务状态机。

### 3.1 物理部署、composition root 与信任边界

R1 目标不先引入新 daemon：`AgentApplicationService/AgentKernel` 作为同一 `packages/shared` 进程内 library，分别由 VS Code Extension Host 和 CLI composition root 装配。两个 Surface 只能选择 platform adapter，不能替换内核、状态转移或 Settlement。Bridge 保持为独立本地进程，与 Extension/CLI 使用短期认证、请求 correlation id 和有界重连；DeepSeek Web 是外部低信任系统。

```text
Untrusted VS Code Webview
    │ validated message schema + nonce
    ▼
VS Code Extension Host composition root ──┐
                                      ├── shared in-process AgentApplicationService/Kernel
CLI composition root ───────────────┘       │
                                                   ├─ durable Run Store + WAL/Outbox/Event Cursor
                                                   ├─ Workspace Lease + sandboxed Tool/Effect adapters
                                                   └─ Evidence Store (redacted index / restricted raw)

Extension/CLI ─ authenticated local protocol ─► Bridge process ─► External DeepSeek Web
Kernel ─ authorized mutation ─► User workspace / Git / build outputs
```

信任和一致性规则：

- Webview、Provider 输出、MCP/网页内容都是 untrusted input；只能转为 typed proposal，不得直接产生权限、副作用或终态。
- 同一 workspace 允许多个只读 run，但只允许一个持有 mutation lease 的 run；VS Code/CLI 跨进程争用时等待或 blocked，不得各自写盘。lease 只给准备/提交阶段，不跨长时间模型思考持有。
- 内部命令、状态、effect intent/outbox 和可展示事件在本地 durable transaction 中提交；外部世界不能与数据库原子提交。worker 以 at-least-once 方式执行外部 effect，依靠 idempotency key/reconciliation 防重，再以第二个短事务追加 receipt 和状态。系统不承诺数据库 + 网络/Git/发布的 exactly-once；进程崩溃后从 WAL/checkpoint 恢复，消费者用 cursor 去重。
- 证据索引与脱敏 replay 可供日常读取；原始 prompt/source/stream/screenshot 进限权加密存储，按 retention/secret-scan 政策处理。
- 若未来需要 daemon/cloud offload，只能新增实现同一 ports 的运输/远程 adapter，并先通过同一 conformance suite，不改变本文语义 owner。

## 4. 六个横向平面

“平面”不是六个任务步骤，而是贯穿整个生命周期的架构责任。

| 平面 | 责任 | 唯一 owner |
| --- | --- | --- |
| Control Plane | 状态转换、预算、中断、恢复、重试和终止 | `AgentKernel` |
| Semantic Plane | 意图、需求、设计、计划、完成契约 | Task/Requirement/Design services |
| Action Plane | 计划动作编排、工具注册、结构化调用与结果归一 | `ExecutionOrchestrator` 唯一负责批准后动作序列/分派；`ToolExecutor` 唯一负责下层 typed 调用/结果归一，二者不得跨层反向调用 |
| Authority Plane | 政策/沙箱计算，审批请求/用户决定，风险和副作用授权 | `PermissionPolicyEngine` 负责纯政策决策；`AuthorityGate` 负责 preflight、请求与 decision receipt |
| Evidence Plane | 事实、artifact、验证、review、trace、replay | `EvidenceStore` |
| Extension Plane | Skills、Hooks、MCP、Subagents、Provider/Platform 适配 | typed extension registries |

任何能力只有同时进入 Control 和 Evidence 平面，并且在 Authority 平面得到显式 policy decision（纯只读能力可是可审计 `no-effect/no-approval-required`），才算“接入”，否则只是旁路实现。

## 5. 核心组件与职责

| 组件 | 唯一职责 | 禁止承担 |
| --- | --- | --- |
| `SurfaceAdapter` | UI/CLI 输入转命令，事件转展示 | 任务路由、文件写入、验证、完成判断 |
| `AgentApplicationService` | 会话命令和事件入口 | Provider 专用业务分支、独立 Coding Loop |
| `AgentKernel` | 驱动状态机、选择下一阶段、管理预算 | 直接解析某 Provider 文本、直接写磁盘 |
| `TaskContractService` | 维护目标、范围、约束、交付物、验收和授权 | 直接执行工具 |
| `ContextBroker` | 汇聚指令、会话、附件、工程事实、外部来源并控制预算 | 根据附件替换内核 |
| `EngineeringOrientationService` | 识别仓库结构、语言、构建/测试、平台和风险 | 修改工作区 |
| `RequirementsService` | 将目标和证据转成可追踪需求、非目标和验收 | 用领域正则代替通用模型 |
| `DesignPlanner` | 影响分析、设计决策、计划、可逆性和风险 | 自己执行 mutation |
| `PermissionPolicyEngine` | 根据任务、工具、effect facets 和环境计算 allow/deny/ask 及 sandbox 约束 | 显示 UI、代替用户同意、执行工具 |
| `AuthorityGate` | 消费 `PermissionPolicyDecision`，收集显式用户批准/拒绝，执行 preflight，并产生 authority receipt | 重新计算一套 policy、隐式放行未知副作用 |
| `ExecutionOrchestrator` | 将计划转成结构化动作，消费 approved plan 并调用 mutation/external/read-only application service | 维护第二套完成语义、绕过服务直接选 adapter |
| `WorkspaceMutationTransactionService` | 消费已批准的 workspace facet，组织 baseline、CAS、隔离 staging、原子提交、readback、rollback和 receipt；仅通过下层 typed mutation port 执行 | 网络/MCP/发布等外部 effect，任务理解和 UI 文案 |
| `ExternalEffectService` | 消费已批准的 terminal/network/MCP/Git/release facet，组织 sandbox、幂等键、补偿和 effect receipt；仅通过下层 typed tool port 执行 | 重新审批、绕过工作区 transaction 修改用户交付物 |
| `ToolRegistry` / `ToolExecutionPort` / `ToolExecutor` | 解析 typed operation，并在上层已决定的 sandbox/scope 内调用底层 adapter，返回原始 typed result | 分类高层 effect、请求审批、反向调用 Kernel service、构造 transaction/effect/completion receipt |
| `BuildService` | 从工程上下文选择构建/打包动作，产生 typed plan 和证据要求，交由 `ExecutionOrchestrator` 执行 | 持有 ToolPort/shell adapter、自己执行动作、没有证据时返回成功 |
| `VerificationService` | 建立 verifier plan、收集结果、输出验证事实 | 修复文件或隐式 mutation |
| `DiagnosisRepairService` | 根据失败证据生成修复假设并回到执行 | 固定假定两轮足够 |
| `IndependentReviewGate` | 从 diff、契约、验证和风险独立判断是否可交付 | 重用执行者的自报结论 |
| `SettlementService` | 只从 TaskContract、append-only Evidence 和 review verdict 构造唯一 `CompletionDecision` | 执行工具、修改证据、用模型自报完成 |
| `DeliveryReleaseService` | 交付摘要；按授权处理 Git/CI/release/rollback | 未经授权提交或发布 |
| `SessionRecoveryService` | checkpoint、resume、cancel、幂等恢复 | 只恢复聊天文本而丢失动作事实 |

## 6. 统一领域契约

以下为概念 schema，用于约束实现边界，并非要求一次性采用完全相同的 TypeScript 名称。

```ts
interface AgentApplicationService {
  start(request: TaskRequest): Promise<RunRef>;
  dispatch(runId: string, command: AgentCommand): Promise<CommandReceipt>;
  events(runId: string, afterCursor?: EventCursor): AsyncIterable<AgentEventEnvelope>;
}

interface TaskContract {
  taskId: string;
  goal: string;
  mode: "explain" | "review" | "change" | "release";
  scope: { include: string[]; exclude: string[] };
  deliverables: Deliverable[];
  requirements: Requirement[];
  nonGoals: string[];
  constraints: Constraint[];
  acceptance: AcceptanceCriterion[];
  authority: AuthorityEnvelope;
  risk: RiskProfile;
  provenance: EvidenceRef[];
  revision: number;
}

interface AgentRun {
  runId: string;
  version: number;
  task?: TaskContractRef;
  phase: KernelPhase;
  status: RunStatus;
  contextSnapshot: ContextSnapshotRef;
  plan?: PlanRevisionRef;
  suspendedAtPhase?: KernelPhase;
  pendingWorkspacePlans: WorkspaceMutationPlanRef[];
  workspaceMutations: WorkspaceMutationReceiptRef[];
  externalEffects: ExternalEffectReceiptRef[];
  evidence: EvidenceRef[];
  pendingDecision?: DecisionRequest;
  cancellation?: CancellationStateRef; // request receipt/version + frozen in-flight effect refs
  checkpoint: CheckpointRef;
  completion?: CompletionDecision;
}

type RunStatus =
  | "active"
  | "paused"
  | "waiting-user"
  | "interrupted"
  | "cancelling"
  | TerminalStatus;

type TerminalStatus =
  | "completed"
  | "failed"
  | "blocked"
  | "cancelled";
```

`TaskContract` 不是调用者必须先构造好的一次性参数。`start` 接收原始 `TaskRequest`，内核在 orientation/contracting 中建立第一个 revision；审批、澄清、steer、resume 和 cancel 都经 `dispatch` 作为 typed command 重入同一 run。`dispatch` 只在命令持久化后返回 `CommandReceipt`；Surface 以 durable `EventCursor` 调用 `events` 可恢复订阅，断线后从 cursor 继续，不依赖一个短命 `AsyncIterable` 刚好存活。`AgentKernel` 是 event/reducer 语义 owner，不是一个不可中断的长方法。

`AgentRun` 的可选字段受 phase invariant 约束，而不是用空对象凑 schema：RECEIVED/ORIENTING 可没有 `task`；离开 CONTRACTING 后必须有 `TaskContractRef`；进入 AWAITING_AUTHORITY/EXECUTING 前必须有适用的 `PlanRevisionRef`；`status=cancelling` 时 `cancellation` 必填且 request version/in-flight refs 冻结，终态保留该历史引用；terminal 时必须同时 `phase=CLOSED` 且有唯一 `completion`。CI 对 reducer 的每个 transition 做 invariant/property test。

`phase` 表示当前工程阶段，`status` 表示运行/等待/取消/终止属性，两者不得混用。`(phase, status, version)` 是一次 CAS 更新的 aggregate；paused/waiting-user/interrupted/cancelling 不推进工程 phase，`suspendedAtPhase` 保存恢复位置。长任务是 saga/process manager，可有多个短 workspace transaction 和多个 external-effect receipt，不是一个跨全生命周期的 ACID 大事务。`phase=CLOSED` 必须与 terminal `status` 和唯一 `completion` 同时存在；终态以 run version CAS 幂等写入，一旦成功不可再迁移。

`cancelling` 是持久化的非终态控制状态，不是一条瞬时内存标志。首次有效 `Cancel` 必须以 run-version CAS 原子写入 `status=cancelling`、冻结新 action/effect dispatch、记录 `CancellationRequested` receipt 和当时的 in-flight effect 集；重复 `Cancel` 返回同一 receipt。此后只允许 reconcile、等待、补偿和 `SettlementService` 的取消结算命令，其他用户/模型命令幂等拒绝。进程崩溃后 `SessionRecoveryService` 只能恢复这条 cancellation saga，不能恢复普通执行；全部 in-flight effect 已结算/补偿后才写 `cancelled`，不可安全结算时按证据写 `failed` 或 `blocked`，不得假装取消成功。

还必须统一以下契约：

- `ToolCall` / `ToolResult`：Provider Adapter 之外不得出现 XML、自由文本 diff 或厂商字段。
- `WorkspaceMutationPlan` / `WorkspaceMutationReceipt`：所有用户工作区变更包含 baseline、幂等键、变更集、readback 和 rollback 信息。
- `ExternalEffectPlan` / `ExternalEffectReceipt`：terminal、network、MCP、Git、release 记录目标、风险、授权、sandbox、幂等键、结果和补偿/回退；不得假装成文件 transaction。
- `VerificationPlan` / `VerificationResult`：明确 verifier 来源、命令、范围、退出码、输出摘要和覆盖的验收条件。
- `CompletionDecision`：逐项关联 acceptance → evidence，不允许仅存一段“已完成”文本。
- `AgentEvent`：事件名和状态一致，不能用 `completed` 事件承载 failed/cancelled。
- `Checkpoint`：保存状态、契约 revision、已提交动作、未决审批和恢复令牌。

## 7. 状态机

```text
KernelPhase:
RECEIVED
  → ORIENTING
  → CONTRACTING
  → DISCOVERING
  → SPECIFYING
  → DESIGNING
  → AWAITING_AUTHORITY
  → EXECUTING
  → BUILDING
  → VERIFYING
  → REVIEWING
  → DELIVERY_READY
  → [AWAITING_AUTHORITY → DELIVERING_EFFECTS]
  → SETTLING
  → CLOSED

任意执行 phase → DIAGNOSING → EXECUTING | CONTRACTING | DESIGNING

RunStatus（与 phase 正交）:
active ⇄ paused | waiting-user | interrupted
active | paused | waiting-user | interrupted → cancelling
cancelling → cancelled | failed | blocked
非 cancelling 的非终态 status → completed | failed | blocked
terminal transition 原子地设置 phase=CLOSED + terminal status + completion
```

状态跳转必须由 typed transition 触发，并通过同一 WAL/outbox transaction 写入 `(phase,status,version)`、checkpoint 与事件日志。pause/wait/interrupted 只改 status 并保留恢复 phase，不能通过调用另一个 Loop 隐式改变 phase。只有 `SettlementService` 可从非终态以 run-version CAS 原子写入 `phase=CLOSED`、terminal `status` 和唯一 `CompletionDecision`；终态对后续 command 只返回幂等拒绝，不再迁移。结果展示不是 `KernelPhase`：Surface 只对 `CLOSED` durable event 做幂等 projection/ack，失败时从 cursor 重放，不回滚产品终态。

核心 command 与 status 约束：

| Command | 允许的前置 | 结果 |
| --- | --- | --- |
| `ProvideClarification` / `Approve` / `Deny` | `waiting-user` 且 decision id/version 匹配 | 恢复 active 或安全 blocked；旧 decision 幂等拒绝 |
| `Steer` | active/paused/waiting-user/interrupted | 新 TaskContract/plan revision，已提交 receipt 不回写；cancelling 时拒绝 |
| `Pause` / `Resume` | active / paused/interrupted | 保存 checkpoint；resume 先验证 workspace lease/baseline/receipts |
| `Cancel` | active/paused/waiting-user/interrupted；或已在 cancelling | 首次 CAS 写 `cancelling`、冻结新 action/effect、持久化 in-flight 集与 receipt；重复调用返回同一 receipt |
| `ReconcileEffect` / `CompensateEffect` / `SettleCancellation`（内部） | `cancelling` 且命令引用冻结的 cancellation receipt/version | 只结算既有 effect；全部安全闭合后由 Settlement 写 cancelled，不可安全闭合则写 failed/blocked |
| 其他 command | `cancelling` | 不改状态、不启动 effect，返回同一 cancellation-in-progress receipt |
| 任意 command | terminal | 不改状态，返回 terminal receipt |

## 8. 完整软件工程阶段

| 阶段 | 核心动作 | 强制产物/证据 | 退出条件 |
| --- | --- | --- | --- |
| S0 会话与工作区基线 | 建立/恢复 session，确认 repo、branch、dirty state、规则作用域 | workspace snapshot、instruction chain、run id | 工作区身份和已有用户改动可区分 |
| S1 意图与任务模式 | 判断 explain/review/change/release、风险和是否需要澄清 | intent decision + provenance | 任务模式确定，歧义被标记 |
| S2 任务契约 | 固化目标、非目标、范围、交付物、验收、授权边界 | `TaskContract` revision | 每个交付物有可验证条件；关键歧义已解决或显式假设 |
| S3 工程与外部边界 | 读取项目指令、构建/测试、依赖、接口、法规/文档等外部事实 | engineering context、source refs | 足以选择探索和 verifier；来源可追踪 |
| S4 探索与需求 | 搜索代码、诊断依赖、建立影响图和需求追踪 | evidence graph、requirements | 关键实现位置、调用者和风险边界已识别 |
| S5 设计与计划 | 设计责任边界、备选方案、影响集、步骤和回退 | design decision、plan revision | 方案符合仓库原则，副作用和验证可执行 |
| S6 权限与 preflight | 计算文件/命令/网络/MCP 权限，捕获 workspace baseline，规划外部 effect | authority decision、transaction baseline、effect plan | 所需权限已授予，拒绝路径可安全停止 |
| S7 实现与工具执行 | 小步结构化动作，观察结果，必要时重规划 | tool results、workspace mutation/external effect receipts | 计划变更已提交、外部 effect 已结算或安全回滚/补偿 |
| S8 构建与产物 | 编译、类型检查、打包或启动项目 | build evidence、artifact identity | 适用构建成功；不适用有理由 |
| S9 验证与修复 | 运行测试、静态检查、行为检查；失败回到诊断/执行 | verification results、repair lineage | 验收项有通过/未验证/失败状态，无伪通过 |
| S10 独立审查 | 审查 diff、范围、回归、安全、证据充分度 | review decision、risk ledger | 无 veto 缺陷；残余风险显式化 |
| S11 交付 readiness 与授权 effect | review 后先生成可交付判断；必要时请求 commit/CI/release 授权并执行 | delivery-readiness decision、可选 Git/CI/release/rollback receipts | 所有授权 effect 已结算或安全失败，不提前对 UI 宣布完成 |
| S12 最终完成裁决 | `SettlementService` 逐项对账契约、append-only evidence、review 和 S11 receipts，以 CAS 写 terminal decision | completion decision、handoff | terminal status 与证据一致，构造点唯一 |
| S13 终态投影与接管（非 KernelPhase） | Surface 从 durable event cursor 幂等展示终态、diff、验证和残余风险 | rendered terminal receipt/ack | UI 内容可追溯到 S12，不自行重新判断；投影失败只重试，不改写或回滚 S12 终态 |

### 8.1 失败路由

| 失败类型 | 返回阶段 |
| --- | --- |
| 目标或验收条件不清 | S2 契约 |
| 新发现的外部接口约束 | S3/S4 边界与需求 |
| 设计无法满足约束 | S5 设计 |
| 权限拒绝或风险升高 | S6 authority，必要时 `waiting-user` |
| 工具协议/平台问题 | Runtime Adapter，不允许在业务 Loop 内打补丁 |
| 写入冲突或 baseline 过期 | S6 重新 capture；不得覆盖用户修改 |
| 构建/测试失败 | Diagnosis → S7 修复 → S8/S9 重验 |
| review 发现范围或架构缺陷 | S2/S5/S7，按缺陷来源回退 |

## 9. 简单、复杂和正式任务如何共用内核

| 任务类型 | 可折叠内容 | 绝不能省略 |
| --- | --- | --- |
| 只读解释 | S5 计划可内联；S6/S7 mutation 不适用 | 指令/上下文、证据来源、诚实完成 |
| 简单文件创建 | S2/S4/S5 可形成紧凑内部契约和单步计划 | 权限、事务写入、readback、适用语法/测试验证、完成对账 |
| 局部 bugfix | 需求和设计可简化 | 根因证据、影响面、测试失败→修复→重验 |
| 跨文件功能 | 显式需求、影响图和计划审阅 | 所有统一边界 |
| 正式项目 | 所有阶段显式化，增加 release/运维策略 | 同一 Kernel，不切换到“Formal 专用 Agent” |

折叠只能减少展示和预算，不能生成另一套代码路径。例如简单创建可在一个 transition 中完成 `CONTRACTING → SPECIFYING → DESIGNING`，但仍产生相同 schema 的最小工件。

## 10. 权限、workspace mutation、外部 effect 与验证协议

```text
Kernel proposes action
  → ToolRegistry resolves typed operation schema
  → Effect classifier declares one or more facets
      [read] [process] [network] [workspace-mutation] [git] [release]
  → PermissionPolicyEngine evaluates every facet/scope/risk
  → AuthorityGate requests approval if needed
  → AuthorityGate emits immutable ApprovedActionPlan / receipt
  → ExecutionOrchestrator dispatches by approved facet
      ├─ read-only facet → read-only ToolExecutionPort → adapter result
      ├─ process/network/git/release facet
      │    → ExternalEffectService → ToolExecutionPort → adapter
      │    → idempotency/reconcile/effect receipt
      └─ workspace-mutation facet
           → WorkspaceMutationTransactionService → typed mutation port → adapter
           → staged overlay/worktree + baseline/CAS/commit/readback receipt
  → append-only evidence is recorded
  → verifier observes committed state without editing user deliverables
  → success continues; failure routes to diagnosis or rollback
```

强制规则：

- workspace mount 分三类：用户交付物/persistent source 只能经 `WorkspaceMutationTransactionService`；cache/coverage/temp 等 ephemeral build output 只能写 sandbox overlay 或声明 output mount，任务结束按策略清理且不进入用户 diff；需长期交付的 artifact 由授权 export 经 `ExternalEffectService` 生成 identity/receipt。`VerificationService` 不得直接修改用户源码；需要修复时创建新的 mutation plan。
- Build、Verification、Review、Skill、Hook 等领域服务只能产生 typed plan，由 `ExecutionOrchestrator` 在 Authority 后调用 application service；它们不得直接持有 `ToolPort` 或 shell/filesystem/network adapter。`ToolExecutor` 位于服务下层，不得反向调用 Kernel/application service。
- 无 verifier 不等于成功，应标记 `unverified` 并由 review 判断是否允许交付。
- 分类不是工具三选一，而是 effect facets。例如 formatter/generator 同时含 process 和 workspace-mutation：进程由 `ExternalEffectService` 在 staging 执行，其产生的 diff 再由 `WorkspaceMutationTransactionService` 提交，两个 receipt 组成同一 saga action。网络只读仍是 external effect，不因“不写文件”免权限。
- MCP、terminal、Git、Web/release 与文件系统共享统一 Authority 语言，但使用适合自身的 effect receipt，不强行伪装成文件 transaction。
- terminal 默认以只读 workspace mount 执行；formatter/generator 等可能改源码的命令在 staging overlay/worktree 中运行，其 diff 必须经 `WorkspaceMutationTransactionService` 提交。任意 shell 不能直接绕过 CAS 修改用户工作区。
- workspace mutation receipt 或适用的 external effect receipt 是 completion 的必要证据，模型文本不是。
- commit token 对一次计划唯一；resume 先查询 receipt，再决定是否重放。

## 11. Skills、Hooks、MCP 与 Subagents

### Skills

Skill 是对内核阶段的可复用说明、资源和脚本包。它只能声明适用条件、所需权限、输入输出和验证方式；不能直接获得绕过 ToolExecutor 的写权限。

### Hooks

Hook 绑定 typed lifecycle event，例如 `beforeMutation`、`afterMutation`、`beforeCompletion`。Hook 的命令也经过 PermissionPolicyEngine/AuthorityGate，失败语义必须明确为 veto、warning 或 evidence。

### MCP

MCP tool 先转为统一 `ToolDescriptor`，再进入 registry、权限、审计和 evidence 流。Server 自报只用于元数据，不能替代本地风险策略。

### Subagents

Subagent 是内核调度的隔离任务，不是新的产品内核：

- 有独立 context budget、tool scope、authority envelope 和 task contract；
- 默认用于只读探索、独立 review、测试分诊等低冲突工作；
- 写任务必须显式划分不重叠 mutation scope，或使用独立 worktree；
- 结果通过 typed summary/evidence 合并，主 Kernel 保留最终 completion 权限。

### Plugins 与供应链

如果 DevSeek 提供可安装 Plugin bundle，Plugin 只是 Skills/Hooks/MCP/adapter 的受治理包装，不是新的信任域。manifest 必须声明来源、版本、签名、内容 hash、权限、兼容 Kernel 版本和卸载/撤销入口；安装、更新、禁用和删除均产生 audit receipt。未签名、来源撤销、权限扩大或版本不兼容默认拒绝，Extension Plane 不得因为“本地目录存在”而加载执行代码。

### 条件能力：peer teams、automation、visual computer use、headless/cloud

- parent-child Subagent 是默认协调模型；peer/agent-team 另建 experimental profile，不能共享隐式写权限或绕过主 Kernel settlement。
- 定时任务、routine/goal/background work 只向同一 `AgentApplicationService` 投递版本化 `AgentCommand`，复用 checkpoint、cancel、authority 和 evidence；scheduler 不是第二 Kernel。
- browser/desktop visual tool 经 ToolRegistry → Permission/Authority → `ExternalEffectService`，screen/DOM 是低信任 observation；截图/视觉判断只能补充，不替代代码、构建和行为 oracle。
- Headless SDK、remote API 或 cloud offload 只能实现同一 command/event/receipt ports，并先通过 Surface conformance；适用范围、数据出境和凭据边界必须由独立 profile 声明。

## 12. 依赖与防漂移规则

CI 至少强制检查：

1. 产品可执行 Coding Kernel 数量必须为 1。
2. Surface 层不能 import mutation、validation、Provider parser 或 Loop 实现。
3. 所有 persistent source/用户交付物写入 API 只能由 `WorkspaceMutationTransactionService` 调用；可改源码的命令必须在 staging 中产生 diff 后走同一提交边界。ephemeral output mount 不得回写 source，artifact export 必须有 `ExternalEffectService` receipt。
4. 所有外部副作用必须由 `ExternalEffectService` 执行，并可追溯到 `PermissionDecision`、幂等键和 receipt。
5. Provider dialect 类型不能越过 Provider Adapter 包。
6. `CompletionDecision` 的构造点只能有 1 个领域 owner。
7. 新增千行热点、重复分支或 semantic owner 时 gate 失败，而不只是提示。
8. 每个核心状态至少有一个黄金旅程覆盖，跨 Surface 共享同一 conformance suite。
9. cancellation property suite 必须证明：首次 Cancel 后新 effect 数为 0、重复 Cancel receipt 相同、crash/resume 只继续结算、未闭合 in-flight effect 时不能进入 cancelled。
10. 文档能力状态从可执行账本生成，不允许手写“完成”覆盖证据。

## 13. 目标架构的完成定义

只有满足以下条件，Converged Coding Kernel 才算成立：

- VS Code、CLI、Headless 使用同一 TaskContract、Kernel、ToolExecutor、mutation、verification、completion。
- 删除或封死 `runAgenticLoop`、`runAgentLoop`、CLI Coding Loop 作为独立产品内核的能力。
- 附件、任务大小和 Provider 只改变输入、预算或 Adapter，不改变核心语义。
- 简单 create/modify/repair 在真实 VS Code 和 CLI 产生等价领域事件与文件结果。
- 权限拒绝、验证失败、中断、恢复、CAS 冲突均有真实路径测试。
- 架构门禁能够阻止旧 owner、旁路和第二内核重新出现。

实现顺序和每项能力的晋级规则见 [`04-分能力专项迭代与收敛路线图.md`](04-分能力专项迭代与收敛路线图.md)。
