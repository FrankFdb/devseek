## 1. 为什么第一轮先做 G0-A

审计已经证明，DevSeek 当前最危险的问题不是“少一个功能”，而是实现状态、资格等级、测试次数和发布结论没有同一份机器事实源。若直接进入 Kernel 重构，会继续出现以下问题：

1. 依赖范围靠人工抄表，漏项和隐式扩项无法阻断。
2. deterministic PASS、development live observation 和产品资格容易被混为一谈。
3. 不同 Surface、Provider、平台的证据会被无作用域等级错误外推。
4. 同一能力的 relation、authority contract 和 required state 在工作清单中可能丢失。
5. 文档与代码漂移后，后续迭代无法判断究竟是实现退化还是验收口径变化。

因此本轮只建设最小可计算治理纵切：机器能力图、精确资格目标、R1 依赖闭包、生成物防漂移和 Phase 0～12 门禁。它为后续实现提供可执行边界，但不伪装成完整 Gate 0。

## 2. 本轮目标与非目标

### 2.1 目标

- 将 C0～C14 的 76 个原子 capability 和 138 条 architecture edge 落为 JSON SSOT。
- 对 priority/applicability 使用有优先级且必须唯一命中的规则，禁止隐式默认。
- 每个能力保存唯一 semantic authority、版本化 contract 和 contract hash。
- 每个 authority 的本地 `source_ref` 必须指向仓库内真实文件与稳定显式 anchor；断链 fail closed。
- architecture dependency 保存 relation、required implementation state 和目标 contract hash。
- edge 上的 required claim 必须与注册 claim profile 六维精确匹配，未知 profile 或 hash/作用域漂移 fail closed。
- 资格事实采用 `qualification_claims[]` 精确 tuple；无作用域字段只能是保守生成视图。
- 以 milestone profile 自动生成 R1 最小工作 manifest，以 `requirements[]{required_implementation_state,required_claim}` 保留精确 tuple，并保留 root、路径、relation 和 contract。
- 把 schema、语义校验、生成物一致性和负例属性测试接入默认 Phase 0～12 门禁。
- 将旧 `canary 3/3、medium 2/2、formal 1/1` 逻辑降为 development observation，永远不能授予 candidate/stable。

### 2.2 非目标

- 不实现 Qualification Plan、Session、Preflight、Attempt event store。
- 不实现签名 Qualification Evidence Manifest 或独立 aggregator。
- 不宣称 `C0-RUN-EVIDENCE-LEDGER` 已统一接入全部产品入口。
- 不修改 VS Code、CLI、Bridge 或 Coding Kernel 行为。
- 不运行 DeepSeek live、正式项目、VSIX 打包安装或发布。
- 不把 R1 manifest 中的 `minimum_level` 当作当前成绩。

## 3. 已实现架构

```text
06 能力目录种子
       │ 一次迁移
       ▼
devseek-capability-ledger.json ── ledger SHA-256
       │
       ├── JSON Schema（结构）
       ├── semantic validator（引用/唯一性/环/hash/状态）
       └── milestone profiles（精确 required_claim tuple）
                         │
                         ▼
              R1 target work manifest
              ├── 45/76 dependency closure
              ├── 10 root targets
              ├── selection_paths[]
              ├── architecture_requirements[]
              └── requirements[]{state, required_claim}
                         │
                         ▼
            generated-file drift gate
                         │
                         ▼
              Phase 0～12 default gate
```

边界规则：

- `docs/process/devseek-capability-ledger.json` 是能力图机器 SSOT；生成 Markdown 只读。
- milestone manifest 的 `manifest_kind=target-work-requirements` 且 `asserts_current_qualification=false`。
- `implementation_state` 与 `qualification_claims[]` 是两条轴；`wired` 不自动产生 L 级。
- claim 唯一键是 `profile_id + profile_sha256 + claim_scope + surface + provider + platform_profile`。
- `qualification_level_view` 不参与依赖匹配；本轮无签名 manifest，因此全部为 `null`。
- 不同 claim tuple 不合并；每条 selection path 保存自己的 `required_claim`。
- `required_implementation_state_view` 只是非权威汇总；同一精确 tuple 合并时 state/level 取最严，不同 tuple 永不交叉外推。
- ledger、claim profile、milestone profile 和 work manifest 均显式声明 `sha256 + devseek-canonical-json/v1`；未知算法或规范化版本 fail closed，固定 golden vector 防止实现与测试一起漂移。
- `devseek-canonical-json/v1` 固定为：数组保持顺序、对象键按 JavaScript UTF-16 code unit 升序递归排列、只接受 JSON primitive/array/plain object、拒绝 `undefined` 与非有限数、`-0` 规范化为 `0`；键和 primitive 采用 `JSON.stringify` 的转义/数值表示并直接组装紧凑 JSON，再对 UTF-8 字节计算 SHA-256。

## 6. 能力状态更新规则

G0-A 的当前机器 ledger 将 `C0-CAPABILITY-LEDGER-SCHEMA` 保守记为 `implemented`。G0-B 完成后，`C0-CASE-CATALOG` 与 `C0-QUALIFICATION-PROFILE-SCHEMA` 的 schema、机器源、校验器、测试和默认 gate 已形成可达纵切，因此标为 `wired`；`C0-PREREGISTRATION-PLAN` 已有签名 plan/event/receipt、store、CAS、retry 状态机与 external-action guard，但尚未接真实 qualification runner，因此保守标为 `implemented`。G0-D 完成后，`C0-RUN-EVIDENCE-LEDGER` 已由 Shared authority 接入 CLI/JSONL、VS Code 和 Bridge 的产品入口，但因入口完整性、细粒度事实与诊断 fail-soft 边界尚未形成不可绕过的资格纵切，保守记为 `implemented`；其 integrity scope 仍严格限定为 product diagnostics。G0-C 完成后，`C0-QUALIFICATION-EVIDENCE-MANIFEST` 与 `C0-QUALIFICATION-AGGREGATOR` 已有 Schema、独立复算 reader、本地 CAS retention、policy/checker 和攻击测试，但没有 protected trust root、真实 runner 或外部 WORM，因此也只记为 `implemented`。

Gate 0 七项仍全部没有正式 `qualification_claims[]`，`qualification_level_view` 均为 `null`。其他 capability 继续保持其机器 ledger 当前事实。特别是：

- R1 manifest 要求某节点未来达到 wired/L1 或 wired/L2，不代表当前已经达到。
- Markdown 中出现目标等级，不得回写成当前 claim。
- 旧 extension JSONL、TaskHistory 或 ReviewLedger 只能显式投影为 `legacy-unverified`，不能代替新 ledger 的原生事实或资格证据。

## 7. 最少迭代的后续顺序

### G0-B：签名计划与 append-only 事件协议（已完成本地纵切）

目标能力：`C0-CASE-CATALOG`、`C0-QUALIFICATION-PROFILE-SCHEMA`、`C0-PREREGISTRATION-PLAN`。

必须交付：

1. Golden Case Catalog 与 Qualification Profile machine schema。
2. Candidate identity、Preregistration Plan、Session、Preflight、Attempt 的版本化事件。
3. plan/slot/event canonical hash 和 append-only hash chain。
4. 在任何 browser/auth/network 动作前执行 fail-closed runtime guard。
5. trusted store time、全局 slot 顺序、CAS 唯一消费、retry adjudication、一次性 receipt。
6. 时间漂移、跨 session 重放、并发双消费、receipt 篡改等属性测试。

退出结果：计划和事件可以确定性复算，Catalog/Profile 已接默认 gate，Plan/store/guard 已实现；仍不授予 capability qualification claim。完整证据与限制见 [11](11-G0-B签名资格协议实施报告.md)。

### G0-D：统一 Run Evidence Ledger 与旧状态迁移（已完成产品诊断纵切）

目标能力：`C0-RUN-EVIDENCE-LEDGER`。

必须交付：

1. Shared authority、VS Code、CLI/JSONL 与 Bridge 共用的 append-only `RunEvidenceLedgerPort`。
2. run/command/event/side effect/verifier/terminal evidence 的统一 identity。
3. TaskHistory、ReviewLedger、diagnostic JSONL 的只读迁移或降级 manifest。
4. 崩溃恢复、重复 event、截断链、不同 Surface replay 的测试。

退出结果：已生成可由 G0-C 冻结引用的 sealed run head/expected anchor，产品 ledger 只记录事实且不能自行签发资格 verdict。VS Code 细粒度事件、真实 Bridge live E2E、WORM/外部 anchor 和 fail-soft 缺口不在本轮完成口径内，详见 [12](12-G0-D统一运行证据账本实施报告.md)。

### G0-C：Evidence Manifest 与独立聚合（已完成本地确定性纵切）

目标能力：`C0-QUALIFICATION-EVIDENCE-MANIFEST`、`C0-QUALIFICATION-AGGREGATOR`。

必须交付：

1. `devseek.qualification-evidence-manifest/v1` machine schema。
2. 冻结 candidate/plan/profile/event-stream head/全部 slot 与 attempt。
3. 分母守恒、失败、veto、排除项和逐 tuple claim 派生。
4. canonical manifest hash、独立 signer allowlist、签名验证和 retention lock。
5. candidate、dependency、Provider、Surface、platform、event head、过期等失效规则。
6. 伪造签名、漏记失败、补跑覆盖、跨 tuple 外推的负例测试。

退出结果：Manifest、retention lock、独立复算、分母/失败/veto/失效规则和本地 CAS store 已实现，定向测试 `35/35`；仓库 policy 仍为 test-only/local、`claim_rules=[]`、`qualification_eligible=false`，所以输出零 claim。只有有效 protected Manifest 可以产生 `qualification_claims[]`；旧 observation 和测试中的 `claim_candidates` 不能迁移为 claim。Gate 0 七个节点全部按精确 claim profile 达到 wired/L2 后，才允许把 Gate 0 标为通过。完整证据与限制见 [13](13-G0-C资格证据清单与独立聚合协议实施报告.md)。
