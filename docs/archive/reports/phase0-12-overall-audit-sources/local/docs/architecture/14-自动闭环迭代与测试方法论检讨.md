# DevSeek 自动闭环迭代与测试方法论检讨

## 1. 本次问题结论

本次 `shape_manager` X11 图形任务反复失败，不是单点 bug，而是 DevSeek 的自动闭环方法还没有达到顶级编程智能体要求。

截图现象：

1. 同一任务在“继续上次对话”和“新对话”中都退化为 1 个 `run_terminal` 验证任务。
2. 任务直接显示失败：`使用 run_terminal 执行 cmake 编译并运行程序验证 X11 图形显示`。
3. 用户实际看到过图形窗口，但 DevSeek 仍把运行验证标记为失败或回滚待确认文件。
4. reload window 后历史摘要和执行时状态不一致。

根本判断：

1. DevSeek 把“可观察的 GUI/交互式程序运行”当成普通终端成功/失败处理，缺少一等公民状态：`manual_review_required`。
2. 当前修复多次只覆盖了局部路径，例如最终 QualityGate、部分 standalone analyze 分支，但没有把“验证任务”提升为统一运行时领域对象。
3. 自动测试覆盖了纯函数和局部分支，没有覆盖完整用户路径：任务规划、工具执行、Todo settle、ReviewLedger、QualityGate、WebView 展示、history reload、继续执行。
4. 手动截图发现的问题没有自动进入 replay fixture，导致每次修复依赖人工再次试错。

## 2. 为什么自动测试没有发现

现有测试主要验证“代码点”而不是“用户任务闭环”。

| 缺口 | 现有情况 | 造成的问题 |
| --- | --- | --- |
| 缺少端到端 Agent replay | 单测验证 `shouldRequestManualReviewForRun` 等纯函数 | 真实任务中失败发生在规划/settle/UI 之前，纯函数通过也无效 |
| 缺少截图级状态断言 | Extension host harness 偏 UI 事件回放，但未覆盖 X11/GUI 验证失败场景 | 用户看到的红色失败、Todo 数量、reload 历史不一致无法被测试发现 |
| 缺少历史回放断言 | 手工 case 没有固化为 `AgentReplayCase` | “继续上次对话”和“新对话”分支没有自动回归 |
| 缺少负向场景矩阵 | 只测 timeout 转人工确认，未测 build-only、GUI launched、cannot open display、binary not found 的差异 | 容易把硬失败和需要人工确认混在一起 |
| 缺少设计边界测试 | 没有测试任务类型、证据类型、UI 状态之间的契约 | 补丁落在 `agent-loop.ts` 某个分支后，其他分支继续漏掉 |

自动测试仍然有意义，但必须从“函数覆盖”升级为“行为闭环覆盖”。顶级编程智能体的测试重点不是只证明某个 helper 返回 true，而是证明在真实任务生命周期中不会对用户撒谎、不会误回滚、不会错误续作。

## 3. 为什么多次无法一次修正

多次修复失败的直接原因是每次都沿着当前失败截图去补局部分支。

设计层原因：

1. `run_terminal` 输出被直接转换成 `TerminalEvidence`，证据模型只有 `ok / failed`，没有 `blocked / needs_human_review / launched` 等中间态。
2. `analyze`、`explore`、最终 `runValidation`、本地执行、历史恢复分别处理验证失败，状态机分叉。
3. Todo settle 直接调用 `findBlockingTerminalFailureEvidence`，只要看到失败 terminal evidence 就失败，无法表达“命令已启动但结果需要人工观察”。
4. 任务规划器把“编译并运行验证”表达为普通 `analyze` 任务，而不是 `validation` 或 `run` 领域任务，导致运行时不知道这是一个可特殊处理的验证节点。
5. UI 只消费已归一的状态事件，无法区分“真实失败”和“等待人工验收”，所以展示上总是红色失败。
6. 历史恢复基于任务摘要和 checkpoint，不是基于稳定的事件溯源状态，因此 reload 后和实时画面容易不一致。

过程层原因：

1. 每轮没有先写“失败复现测试”，而是先改代码再靠用户截图验收。
2. 没有把截图中的用户旅程转换为可自动运行的 replay case。
3. 没有先画清楚完整状态机，导致修复点不断漂移。
4. 没有为“同一类问题”设立横向矩阵，导致 final validation、standalone analyze、resume、new session、reload 分支逐个漏。

## 4. 对标 Claude Code / Codex 的方法

本节基于官方公开资料和产品可观察行为抽象原则，不声称复刻其内部私有实现。

优秀编程智能体的共同点：

1. **规划和执行分离。** 复杂任务先计划，计划只读，执行前用户可确认。Codex 文档强调复杂任务使用 Plan mode，并把 Goal、Context、Constraints、Done when 写清楚。
2. **工具边界硬执行。** Claude Code 通过 `PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`Stop` 等生命周期 hook 在工具调用前后做确定性控制；Codex 通过 sandbox、approval、review 控制动作边界。
3. **证据高于模型自述。** 代码生成后必须运行测试、lint、typecheck、review diff；不能靠模型说“完成”。
4. **人工确认是一等状态。** 对视觉、GUI、交互、外部系统结果，顶级 Agent 不会伪装成自动通过，也不会误报失败，而是保留变更并请求用户确认。
5. **可恢复和可回放。** session、checkpoint、worktree、transcript、event log 支撑 resume/fork/compact/review，续作不是盲目重放旧命令。
6. **反复错误进入持久规则或 fixture。** Codex 官方最佳实践明确建议：当 Codex 重复犯同一错误时，做 retrospective 并更新 `AGENTS.md` 或技能；同理 DevSeek 应更新实施原则、测试 fixture 和设计边界。

DevSeek 要吸收的不是某个按钮，而是这种工程闭环：

```text
用户目标
  -> 任务语义分类
  -> 计划审查
  -> 权限与工具策略
  -> 工具执行事件
  -> 结构化证据
  -> QualityGate/ManualReviewGate
  -> ReviewLedger
  -> 历史事件溯源
  -> replay case
  -> 下次自动回归
```

## 5. 新的自动闭环迭代方法

后续每个用户截图问题必须按以下流程处理。

### 5.1 先复现，再修复

每个缺陷必须先落成一种可运行复现：

1. **Domain unit**：纯领域函数，例如视觉运行分类、路径解析、权限判定。
2. **Runtime replay**：模拟模型输出、工具输出、terminal evidence、任务 settle，验证 `AgentEvent` 序列。
3. **Surface harness**：WebView/Extension host 展示断言，验证用户看到的 Todo、红绿状态、继续按钮、历史 reload。
4. **Manual case**：真实 DeepSeek 网页不可控时，只保留为最终手工验收，不作为唯一验收依据。

没有至少一个自动 replay case 的修复，不能认为完成。

### 5.2 每个截图转为 Replay Case

新增 `AgentEvalReplayStore` 的实际接入规则：

1. 从截图和日志提取：用户 prompt、任务计划、工具调用、终端输出、文件变更、checkpoint、UI 事件。
2. 脱敏后保存为 fixture。
3. fixture 必须断言最终事件，不只断言函数返回值。
4. 每次手工测试失败后，先补 fixture，再修代码。

推荐 fixture 维度：

| Fixture | 覆盖 |
| --- | --- |
| `x11-manual-review-new-session` | 新对话中 GUI 程序启动后进入人工确认，不红色失败 |
| `x11-manual-review-resume` | 继续上次对话时不重放错误状态 |
| `x11-history-reload-consistency` | reload 后历史与实时事件一致 |
| `x11-hard-compile-failure` | 编译错误仍然红色失败 |
| `x11-cannot-open-display` | 环境错误清晰提示，不当成人工确认 |
| `x11-build-only-missing-run` | 只构建未运行时提示缺少运行证据 |

### 5.3 建立 Evidence State Machine

把 `TerminalEvidence.ok` 二值模型升级为明确状态：

```text
not_started
running
passed
failed
blocked
manual_review_required
cancelled
```

规则：

1. `passed` 只来自确定性证据，例如退出码 0 且完成条件满足。
2. `failed` 只来自确定性失败，例如编译错误、二进制不存在、崩溃、权限拒绝。
3. `manual_review_required` 用于 GUI/视觉/交互式任务已启动但自动系统无法判断结果。
4. `blocked` 用于缺少权限、缺少环境、Provider 登录、需要用户输入。
5. `TodoLedger`、`QualityGate`、`ReviewLedger`、`History` 只能消费这个统一状态，不能各自解释终端字符串。

### 5.4 区分三种验证

DevSeek 必须把验证拆成三个领域对象：

1. **BuildValidation**：编译、类型检查、lint。
2. **RuntimeValidation**：CLI/服务/API/非交互程序运行，能用退出码和输出判断。
3. **VisualReviewValidation**：GUI、图形、截图、浏览器、交互式程序，需要人工或视觉模型确认。

这三类不能再都塞进 `analyze` 任务和 `run_terminal` 字符串。

### 5.5 测试金字塔调整

新的测试金字塔：

| 层级 | 目的 | 必须覆盖 |
| --- | --- | --- |
| Pure unit | 快速验证领域规则 | 证据分类、权限、路径、任务语义 |
| Runtime replay | 验证 Agent Core 行为 | 工具事件、任务状态、QualityGate、ReviewLedger |
| Surface replay | 验证用户看到的结果 | WebView Todo、banner、reload history |
| Real provider smoke | 验证 DeepSeek Web/API 接入可用 | 登录、流式、恢复，不验证每个逻辑分支 |
| Manual acceptance | 验证真实视觉/交互效果 | X11 窗口、截图、人眼确认 |

真实 DeepSeek 网页测试不能替代自动测试，因为 Provider 输出不稳定、网络/登录不可控、成本高、不可重复。它应该用于 smoke 和最终验收；逻辑正确性必须由 replay/eval 保障。

## 6. 针对当前问题的设计修正方向

这次 X11 问题后续修复不应再继续补 `if timeout then review`。

必须做的重构：

1. 新增 `ValidationStateService` 或同等领域服务，统一把工具结果归一为 `ValidationState`。
2. 新增 `VisualReviewGate`，从 Prompt、任务类型、命令、源码特征、终端行为判断是否进入人工确认。
3. `AgentTask` 增加 `validationKind` 或引入独立 `ValidationTask`，不要把运行验证伪装成普通 `analyze`。
4. `TaskTodoLedger` 不再直接查询 `findBlockingTerminalFailureEvidence`，而是消费 `TaskEvidenceState`。
5. `QualityGateService` 明确支持 `pass / fail / blocked / manual_review_required`。
6. `AgenticHistory` 存储事件溯源状态，reload 不重新推断。
7. `WebView` 对 `manual_review_required` 使用黄色/蓝色“等待人工确认”，不得红色失败；保留文件改动，不自动接受。
8. 每个修复必须新增 runtime replay 和 surface replay，覆盖 new session、resume、reload 三条路径。

## 7. 一次修正问题的工作法

后续遇到同类问题，执行顺序固定为：

1. **Freeze**：冻结当前用户截图和日志，记录现象。
2. **Trace**：画出事件链路，定位是 planner、tool、evidence、ledger、gate、surface、history 哪一层错。
3. **Matrix**：列出同类横向分支，不只看当前截图。
4. **Replay first**：先写失败 replay，确认能稳定失败。
5. **Design fix**：改领域边界，而不是在出错分支补条件。
6. **Cross-layer test**：至少跑 unit + runtime replay；涉及 UI 跑 surface replay。
7. **Release loop**：extension/bridge 行为变更必须 compile/package/install。
8. **Retrofit docs**：重复错误进入实施原则、AGENTS.md 或专题设计。

验收标准：

1. 同类矩阵全部有测试。
2. reload/history 与实时事件一致。
3. 手工测试只验证真实 Provider 和视觉效果，不再承担逻辑回归职责。
4. 代码变更落在正确领域服务，不让 `agent-loop.ts` 和 `extension.ts` 继续吞职责。

## 8. 对 DevSeek 的长期迭代策略

DevSeek 要成为顶级编程智能体，核心不是“多补几个规则”，而是建立可进化系统：

1. **把每次失败变成资产。** 手工截图、Provider 异常、用户反馈都进入 replay store。
2. **用设计边界吸收复杂性。** 权限、工具、证据、验证、审查、历史、UI 都有自己的服务和事件契约。
3. **让测试贴近真实用户旅程。** 不是只测 helper，而是测 Agent 从 prompt 到最终 UI 状态的完整行为。
4. **保持模型可替换。** DeepSeek Web、API、CLI mock 都走同一个 Agent Core；Provider 只负责生成事件，不拥有工具和质量门禁。
5. **把人工确认正规化。** 顶级 Agent 不会把不可自动判断的视觉结果伪装成成功，也不会误报失败；它会保留证据、请求用户确认、可继续迭代。
6. **把重复错误写进规则。** 两次以上出现的问题必须沉淀到实施原则、测试 fixture、架构守卫或技能，而不是靠记忆提醒。

## 9. 下一步落地清单

P0：

1. 建立 `AgentRuntimeReplay` 测试工具，输入任务计划、模型工具调用、终端输出，断言 `AgentEvent`、Todo、QualityGate。
2. 为当前 X11 问题补 `new-session`、`resume`、`reload` 三个 fixture。
3. 引入统一 `ValidationState`，让 Todo、QualityGate、History 共享状态。
4. 把 VisualReview 从 `manual-review-validation.ts` helper 升级为 `VisualReviewGate`。

P1：

1. Extension host harness 增加截图问题回放断言。
2. History reload 使用事件溯源而不是摘要重建。
3. ReviewLedger 绑定 `manual_review_required`，文件保留为待确认。
4. CLI 增加 `devseek replay <case>`，支持在不打开 VS Code 的情况下跑完整 Agent Core。

P2：

1. 引入视觉模型或截图比对作为可选验证，但不能替代人工确认。
2. 把常见 GUI/浏览器/服务启动任务抽成 Skills。
3. 建立失败趋势 dashboard：重复失败指纹、未覆盖 fixture、手工测试转自动测试比例。

## 10. 本文档约束

后续 DevSeek 修复若涉及 Agent 执行、工具、验证、Todo、历史或 UI 展示，必须回答：

1. 这个问题是否已被转成 replay fixture？
2. 这个修复是否覆盖 new session、resume、reload？
3. 这个状态是否有统一 Evidence/ValidationState 表达？
4. 这个判断是否在领域服务内，而不是 UI 或 `agent-loop.ts` 分支里？
5. 这个场景在 Claude Code/Codex 类优秀智能体中会如何通过权限、hook、evidence、review、resume 处理？

如果答案是否定的，本次迭代不能视为完成。
