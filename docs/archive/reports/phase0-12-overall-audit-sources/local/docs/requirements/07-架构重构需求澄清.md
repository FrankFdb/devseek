# DevSeek 架构重构需求澄清

文档编号：REQ-07
最后更新：2026-06-18
状态：进入架构设计前的需求确认
用途：把 `02-顶级编程智能体需求基线.md` 和 `06-记忆体需求.md` 中需要优先进入设计重构的需求收敛成可执行边界。

## 1. 本轮重构目标

本轮重构不是直接新增更多 Agent 功能，而是先把 DevSeek 的核心编程智能体能力重构到可持续演进的架构边界里。

目标是让后续 P0/P1 能力有清晰承载位置：

1. Plan Mode、Inspect Mode、Edit Mode、Run Mode 有统一工作流入口。
2. 工具调用从文本伪工具逐步收口到工具注册、权限判定、执行器和审计事件。
3. 权限、安全、写盘、终端、MCP、网络访问由统一策略控制。
4. 会话、任务摘要、recent files、项目规则、AI 记忆进入可治理状态模型。
5. WebView 只展示协议事件，不继续承载业务判断。
6. 历史任务可以保存、显示、打开和继续工作，且恢复过程可审计、可回退。
7. DeepSeek Web 作为默认模型 Provider，其他大模型通过 API Provider 直连接入同一 Agent Runtime。
8. VS Code、CLI、非交互脚本、桌面/本地 Web 必须通过 Surface Adapter 接入同一 Agent Core。
9. 多入口重构与既有实现差异很大，建议在 `devseek-multi` 分支推进，main 只接收阶段完成的稳定合并。
10. 多目标构建必须说清楚 shared/core、bridge、VS Code extension、CLI TUI、CLI JSONL、future desktop/local web 的 build/test/package/release profile。
11. `extension.ts` 和 `agent-loop.ts` 不再作为所有功能的默认堆叠位置。

## 3. 暂不覆盖范围

| 暂不做 | 原因 |
| --- | --- |
| 云端任务委派 | 需要远端执行环境、安全边界和账号体系，当前先本地优先 |
| 插件市场/团队分发包 | 依赖 skills、hooks、MCP 治理成型后再做 |
| 向量数据库代码索引 | 第一阶段先做来源可解释的轻量上下文装配，避免引入重依赖 |
| 完整 PR 云端生命周期 | 先做本地 Git diff、code review、commit/PR 文案 |
| 全权限无人值守自动驾驶 | 权限、沙箱、回退、审计完成前不开放 |

## 4. 当前代码现状约束

| 现状 | 设计影响 |
| --- | --- |
| `packages/vscode-extension/src/extension.ts` 约 5500 行，仍承担 UI 路由、会话、Agent、Provider、Pending Edit、终端确认等多职责 | 必须逐步迁出到 `app/*`、`ui/*`、`workspace/*`，不再往主入口堆新业务 |
| `packages/vscode-extension/src/agent-loop.ts` 约 3600 行，混合 prompt、工具解析、工具执行、验证、UI 事件 | 必须拆出 Agent runtime、tool dispatch、completion/evidence、prompt assembly |
| `app/chat-controller.ts`、`workflow-service.ts`、`session-service.ts`、`permission-service.ts` 已存在但偏薄 | 本轮不是重建抽象，而是把真实职责迁入已有边界 |
| `SessionService` 已能保存历史对话 meta/history/summary/files，但任务事实、验证证据、change set 和 checkpoint 仍分散 | 需要新增 `TaskHistoryStore`，让聊天历史和任务历史分层关联 |
| `agent/tool-registry.ts`、`agent/tool-executor.ts` 已有工具元数据雏形 | 结构化工具协议应沿现有注册表扩展，不另起一套 |
| `llm/*` 已有 ProviderRouter、DeepSeek API、OpenAI-compatible、Bridge 包装雏形 | 需要统一 Provider 配置、默认选择、capabilities、health、fallback 和输出规范化，不能让不同 Provider 分叉 Agent 主流程 |
| 当前上下文主要依赖文本搜索、recent files 和人工附件 | 需要补 repository map、符号导航、工程环境识别和内容排除，避免大型仓库中读取错误或污染上下文 |
| 当前文件写入主要依赖应用前后快照和 pending edit | 需要写入前版本检查和用户并发修改冲突策略，不能静默覆盖用户工作 |
| 当前产品入口主要围绕 VS Code 插件和 WebView | 需要把 Agent Core 从显示层剥离出来，CLI、JSONL、桌面/本地 Web 不能复制业务逻辑 |
| 当前终端、路径、浏览器桥接和存储差异未形成跨平台边界 | 需要 PlatformRuntimeAdapter 统一 Linux/macOS/Windows native/WSL 行为 |
| 当前编译发布主要服务 VS Code 插件和 Bridge | 需要明确多目标构建矩阵，确保 CLI/JSONL/未来 Desktop 不破坏既有 VSIX release loop |
| `.devseek/memory.md` 读取、写入、注入分散在 `project-rules.ts`、`extension.ts`、`agent-loop.ts` | 必须收口到 `MemoryService` |
| 测试已有 intent、workflow、permission、tool、session、pending-edit、workspace-applier 等单测 | 重构测试应优先扩展现有单测，而不是只做字符串 grep |

## 5. 六大设计原则约束

本轮设计必须显式符合软件六大设计原则：

| 原则 | DevSeek 约束 |
| --- | --- |
| 单一职责原则 | 一个服务只拥有一个变化原因；例如 `MemoryService` 管记忆，`PermissionService` 管权限，`WorkflowService` 管模式选择 |
| 开闭原则 | 新增工具、Provider、workflow、memory type 时优先注册扩展，不修改主流程分支 |
| 里氏替换原则 | Provider、Tool、Repository、Storage 的实现必须能被替换，调用方依赖统一契约 |
| 接口隔离原则 | UI、Agent、Workspace、Memory、Permission 不共享臃肿接口；按调用方需要拆小接口 |
| 依赖倒置原则 | 高层 workflow 依赖抽象服务接口，不直接依赖 VS Code API、fs、Bridge DOM 细节 |
| 迪米特法则 | 模块只和直接协作者通信；WebView 不知道 Memory 存储细节，Agent 不直接操作 UI DOM 或 storage key |
