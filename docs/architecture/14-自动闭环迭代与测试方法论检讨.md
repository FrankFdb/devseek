# DevSeek 自动闭环迭代与测试方法论检讨

文档编号：ARCH-14
最后更新：2026-07-17
状态：活跃方法论与测试架构约束
关联文档：[05-代码重构实施计划.md](05-代码重构实施计划.md)、[06-竞品实现方式对标审计与设计修正.md](06-竞品实现方式对标审计与设计修正.md)、[12-Agentic修复运行时专题设计.md](12-Agentic修复运行时专题设计.md)、[13-工程完整性与顶级增强核心设计.md](13-工程完整性与顶级增强核心设计.md)、[17-顶层RunContext与执行事实治理专题设计.md](17-顶层RunContext与执行事实治理专题设计.md)

## 1. 本次问题结论

本次 `shape_manager` X11 图形任务反复失败，不是单点 bug，而是 DevSeek 的自动闭环方法还没有达到顶级编程智能体要求。

截图现象：

1. 同一任务在“继续上次对话”和“新对话”中都退化为 1 个 `run_terminal` 验证任务。
2. 任务直接显示失败：`使用 run_terminal 执行 cmake 编译并运行程序验证 X11 图形显示`。
3. 用户实际看到过图形窗口，但 DevSeek 仍把运行验证标记为失败或回滚待确认文件。
4. reload window 后历史摘要和执行时状态不一致。

根本判断：

1. DevSeek 把“可观察的 GUI/交互式程序运行”当成普通终端成功/失败处理，缺少一等公民状态：`manual_review_required`。
2. 当前修复多次只覆盖了局部路径，例如最终 QualityGate、部分 standalone analyze 分支，但没有把“验证任务”提升为统一运行时领域对象。
3. 自动测试覆盖了纯函数和局部分支，没有覆盖完整用户路径：任务规划、工具执行、Todo settle、ReviewLedger、QualityGate、WebView 展示、history reload、继续执行。
4. 手动截图发现的问题没有自动进入 replay fixture，导致每次修复依赖人工再次试错。

## 2. 为什么自动测试没有发现

现有测试主要验证“代码点”而不是“用户任务闭环”。

| 缺口 | 现有情况 | 造成的问题 |
| --- | --- | --- |
| 缺少端到端 Agent replay | 单测验证 `shouldRequestManualReviewForRun` 等纯函数 | 真实任务中失败发生在规划/settle/UI 之前，纯函数通过也无效 |
| 缺少截图级状态断言 | Extension host harness 偏 UI 事件回放，但未覆盖 X11/GUI 验证失败场景 | 用户看到的红色失败、Todo 数量、reload 历史不一致无法被测试发现 |
| 缺少历史回放断言 | 手工 case 没有固化为 `AgentReplayCase` | “继续上次对话”和“新对话”分支没有自动回归 |
| 缺少负向场景矩阵 | 只测 timeout 转人工确认，未测 build-only、GUI launched、cannot open display、binary not found 的差异 | 容易把硬失败和需要人工确认混在一起 |
| 缺少设计边界测试 | 没有测试任务类型、证据类型、UI 状态之间的契约 | 补丁落在 `agent-loop.ts` 某个分支后，其他分支继续漏掉 |

自动测试仍然有意义，但必须从“函数覆盖”升级为“行为闭环覆盖”。顶级编程智能体的测试重点不是只证明某个 helper 返回 true，而是证明在真实任务生命周期中不会对用户撒谎、不会误回滚、不会错误续作。

## 3. 为什么多次无法一次修正

多次修复失败的直接原因是每次都沿着当前失败截图去补局部分支。

设计层原因：

1. `run_terminal` 输出被直接转换成 `TerminalEvidence`，证据模型只有 `ok / failed`，没有 `blocked / needs_human_review / launched` 等中间态。
2. `analyze`、`explore`、最终 `runValidation`、本地执行、历史恢复分别处理验证失败，状态机分叉。
3. Todo settle 直接调用 `findBlockingTerminalFailureEvidence`，只要看到失败 terminal evidence 就失败，无法表达“命令已启动但结果需要人工观察”。
4. 任务规划器把“编译并运行验证”表达为普通 `analyze` 任务，而不是 `validation` 或 `run` 领域任务，导致运行时不知道这是一个可特殊处理的验证节点。
5. UI 只消费已归一的状态事件，无法区分“真实失败”和“等待人工验收”，所以展示上总是红色失败。
6. 历史恢复基于任务摘要和 checkpoint，不是基于稳定的事件溯源状态，因此 reload 后和实时画面容易不一致。

过程层原因：

1. 每轮没有先写“失败复现测试”，而是先改代码再靠用户截图验收。
2. 没有把截图中的用户旅程转换为可自动运行的 replay case。
3. 没有先画清楚完整状态机，导致修复点不断漂移。
4. 没有为“同一类问题”设立横向矩阵，导致 final validation、standalone analyze、resume、new session、reload 分支逐个漏。

## 4. 对标 Claude Code / Codex 的方法

本节基于官方公开资料和产品可观察行为抽象原则，不声称复刻其内部私有实现。

优秀编程智能体的共同点：

1. **规划和执行分离。** 复杂任务先计划，计划只读，执行前用户可确认。Codex 文档强调复杂任务使用 Plan mode，并把 Goal、Context、Constraints、Done when 写清楚。
2. **工具边界硬执行。** Claude Code 通过 `PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`Stop` 等生命周期 hook 在工具调用前后做确定性控制；Codex 通过 sandbox、approval、review 控制动作边界。
3. **证据高于模型自述。** 代码生成后必须运行测试、lint、typecheck、review diff；不能靠模型说“完成”。
4. **人工确认是一等状态。** 对视觉、GUI、交互、外部系统结果，顶级 Agent 不会伪装成自动通过，也不会误报失败，而是保留变更并请求用户确认。
5. **可恢复和可回放。** session、checkpoint、worktree、transcript、event log 支撑 resume/fork/compact/review，续作不是盲目重放旧命令。
6. **反复错误进入持久规则或 fixture。** Codex 官方最佳实践明确建议：当 Codex 重复犯同一错误时，做 retrospective 并更新 `AGENTS.md` 或技能；同理 DevSeek 应更新实施原则、测试 fixture 和设计边界。
7. **无进展循环必须由运行时阻断。** Claude Code/Codex 类 Agent 不会只靠“请继续”无限喂给模型；它们会用工具事件、文件变更、验证结果等证据判断是否取得进展。DevSeek 后续必须把重复同一工具/同一反馈但没有写入、补丁或完成证据的情况视为运行时收敛问题。

DevSeek 要吸收的不是某个按钮，而是这种工程闭环：

```text
用户目标
  -> 任务语义分类
  -> 计划审查
  -> 权限与工具策略
  -> 工具执行事件
  -> 结构化证据
  -> QualityGate/ManualReviewGate
  -> ReviewLedger
  -> 历史事件溯源
  -> replay case
  -> 下次自动回归
```

## 5. 新的自动闭环迭代方法

后续每个用户截图问题必须按以下流程处理。

### 5.1 先复现，再修复

每个缺陷必须先落成一种可运行复现：

1. **Domain unit**：纯领域函数，例如视觉运行分类、路径解析、权限判定。
2. **Runtime replay**：模拟模型输出、工具输出、terminal evidence、任务 settle，验证 `AgentEvent` 序列。
3. **Surface harness**：WebView/Extension host 展示断言，验证用户看到的 Todo、红绿状态、继续按钮、历史 reload。
4. **Manual case**：真实 DeepSeek 网页不可控时，只保留为最终手工验收，不作为唯一验收依据。
5. **Real provider protocol smoke**：当截图显示模型输出新工具方言时，用真实 DeepSeek Web 发送最小提示，确认网页端确实能返回该格式，再把样本降级为可重复 parser/sanitizer/replay 测试。

没有至少一个自动 replay case 的修复，不能认为完成。

### 5.2 每个截图转为 Replay Case

新增 `AgentEvalReplayStore` 的实际接入规则：

1. 从截图和日志提取：用户 prompt、任务计划、工具调用、终端输出、文件变更、checkpoint、UI 事件。
2. 脱敏后保存为 fixture。
3. fixture 必须断言最终事件，不只断言函数返回值。
4. 每次手工测试失败后，先补 fixture，再修代码。
5. 如果截图出现 `Calling:`、`AFILE:...RESET`、DOM 按钮文案或 checkpoint/继续按钮异常，必须同时补 parser、sanitizer、runtime replay 和 surface 显示断言；不能只把它当成 UI 文本清洗问题。

推荐 fixture 维度：

| Fixture | 覆盖 |
| --- | --- |
| `x11-manual-review-new-session` | 新对话中 GUI 程序启动后进入人工确认，不红色失败 |
| `x11-manual-review-resume` | 继续上次对话时不重放错误状态 |
| `x11-history-reload-consistency` | reload 后历史与实时事件一致 |
| `x11-hard-compile-failure` | 编译错误仍然红色失败 |
| `x11-cannot-open-display` | 环境错误清晰提示，不当成人工确认 |
| `x11-build-only-missing-run` | 只构建未运行时提示缺少运行证据 |

### 5.3 建立 Evidence State Machine

把 `TerminalEvidence.ok` 二值模型升级为明确状态：

```text
not_started
running
passed
failed
blocked
manual_review_required
cancelled
```

规则：

1. `passed` 只来自确定性证据，例如退出码 0 且完成条件满足。
2. `failed` 只来自确定性失败，例如编译错误、二进制不存在、崩溃、权限拒绝。
3. `manual_review_required` 用于 GUI/视觉/交互式任务已启动但自动系统无法判断结果。
4. `blocked` 用于缺少权限、缺少环境、Provider 登录、需要用户输入。
5. `TodoLedger`、`QualityGate`、`ReviewLedger`、`History` 只能消费这个统一状态，不能各自解释终端字符串。

### 5.4 区分三种验证

DevSeek 必须把验证拆成三个领域对象：

1. **BuildValidation**：编译、类型检查、lint。
2. **RuntimeValidation**：CLI/服务/API/非交互程序运行，能用退出码和输出判断。
3. **VisualReviewValidation**：GUI、图形、截图、浏览器、交互式程序，需要人工或视觉模型确认。

这三类不能再都塞进 `analyze` 任务和 `run_terminal` 字符串。

### 5.5 测试金字塔调整

新的测试金字塔：

| 层级 | 目的 | 必须覆盖 |
| --- | --- | --- |
| Pure unit | 快速验证领域规则 | 证据分类、权限、路径、任务语义 |
| Runtime replay | 验证 Agent Core 行为 | 工具事件、任务状态、QualityGate、ReviewLedger |
| Surface replay | 验证用户看到的结果 | WebView Todo、banner、reload history |
| Real provider smoke | 验证 DeepSeek Web/API 接入可用 | 登录、流式、恢复，不验证每个逻辑分支 |
| Manual acceptance | 验证真实视觉/交互效果 | X11 窗口、截图、人眼确认 |

真实 DeepSeek 网页测试不能替代自动测试，因为 Provider 输出不稳定、网络/登录不可控、成本高、不可重复。它应该用于 smoke 和最终验收；逻辑正确性必须由 replay/eval 保障。

### 5.6 分布式子闭环测试

DevSeek 后续不能把“真实 DeepSeek 网页能跑一次”当成智能体能力证明。正确方式是把一个大闭环拆成多个可独立运行、可独立定位的子闭环，逐层晋级。

子闭环分层：

| 层级 | 子闭环 | Provider | 验收重点 | 提交级 |
| --- | --- | --- | --- | --- |
| L0 | Agent Core protocol replay | 本地 fake provider | `AgentCommand` 输入、`AgentEvent` 输出、history/usage 边界 | 必跑 |
| L1 | CLI JSONL mock | CLI mock provider | stdout 机器可读、事件顺序、退出码 | 必跑 |
| L2 | CLI fake Bridge SSE | 本地 fake Bridge | CLI 到 Bridge 的 SSE、等待提示、stdout/stderr 分离 | 必跑 |
| L3 | CLI fake Bridge programming | 本地 fake Bridge | 通过 CLI 得到代码工件、本地写入、编译、运行 | 必跑 |
| L3b | CLI loose tool JSON recovery | 本地 fake Bridge | 复现真实 DeepSeek 非严格工具 JSON，恢复代码工件、编译、运行，并保留协议缺口信号 | 必跑 |
| L4 | CLI real DeepSeek programming | 真实 Bridge + DeepSeek Web | 登录态、真实模型协议遵循、JSONL 最终响应中的编程输出可编译运行 | 手工/冒烟 |
| L5 | VS Code surface replay | Extension host/WebView harness | 用户看到的 Todo、File Changes、QualityGate、reload | 按变更必跑 |
| L6 | Long-run eval/canary | 定时任务 | 多轮、恢复、Provider fallback、性能和稳定性趋势 | 定时 |

新增脚本：

```bash
npm run verify:agent-loop-eval
npm run verify:agent-loop-eval:real
npm run verify:programming-agent-benchmark
```

其中 `verify:agent-loop-eval` 只跑 L0-L3b 的确定性子闭环，并生成 `artifacts/agent-loop-eval/<run-id>/report.json`；`verify:agent-loop-eval:real` 显式加入 L4，要求本地 Bridge 与 DeepSeek Web 登录态可用。L4 失败不能直接证明业务逻辑错，必须先归类为登录、限流、DOM、网络、模型协议遵循或本地评测失败。

`verify:agent-loop-eval` 只能证明管道、协议、工件解析和局部编译链路，不等于证明 DevSeek 已经是优秀编程智能体。真正对标 Claude Code/Codex 的能力门禁是 `verify:programming-agent-benchmark`，它必须测试 DevSeek 是否能在工作区内真实完成：

1. 读取/理解任务。
2. 应用结构化文件改动，而不是只把工具调用打印到 stdout。
3. 修改既有代码并保留旧行为。
4. 运行验证命令。
5. 根据失败证据进行修复并重跑验证。
6. 输出 file changes、validation、quality gate 等可审查事件。
7. 在用户追加需求时，把相关既有源码作为上下文传给模型，避免模型凭空猜测。
8. 对需要 stdin 的交互式程序，使用 `devseek.verify.json` 之类的显式验证配置完成编译、执行、输入和输出断言。

该 benchmark 的被测代码工作区固定在 `code/devseek-programming-agent-benchmark/<run-id>/`。`code/` 是 DevSeek 编程能力测试沙箱，可以读取既有样例，也可以生成新测试工程；被测智能体不得修改 DevSeek 项目自身的 `packages/`、`scripts/`、`docs/` 等源码和文档。真实 CLI/DeepSeek 冒烟若需要 cwd，也必须使用 `code/agent-loop-eval/<run-id>/` 之类的沙箱目录。

同时，每次执行必须在 `docs/testing/agent-loop-eval-reports/<run-id>/` 或 `docs/testing/programming-agent-benchmark-reports/<run-id>/` 下沉淀测试报告，并更新对应 `latest.md`。`artifacts` 保存原始运行证据，`docs/testing` 保存可评审、可复盘、可继续迭代的测试结论。

报告必须包含：

1. 本轮是否发现 DevSeek 缺陷。
2. 若失败，归因是 DevSeek 逻辑、真实 Provider 环境、模型协议、生成代码、测试前置条件，还是测试用例设计问题。
3. 若通过但使用了恢复路径，例如 `tool-json-recovered`，必须记录为“通过但暴露协议缺口”，不能当作完全健康。
4. 若真实 Provider 流式显示会改写或重发片段，编程产物 oracle 必须读取 JSONL `chat.completed.response`，不能直接从流式 stdout 抽取代码。
5. 若没有发现问题，必须说明当前 case 没有压到哪些能力边界，并给出下一轮要新增的更尖锐 case。
6. 每个 finding 必须给出下一步：修 DevSeek、补 replay、调整 prompt/tool contract、修测试前置，或重写不合理 case。

子闭环迭代顺序：

1. 运行当前层级测试，形成 `docs/testing` 报告。
2. 阅读 findings 和 case-design review，确认问题属于 DevSeek 还是测试本身。
3. 若是 DevSeek 问题，先把失败样本降级成可重复 L0-L3 replay，再修代码。
4. 若是测试 case 不合理，先重写 case 的目标和 oracle，再用它做门禁。
5. 修复后重跑同一命令，比较新旧报告，直到 finding 关闭或降级为明确的后续工作。
6. 只有低层子闭环稳定后，才进入更高层真实 Provider 或 VS Code Surface 验证。

2026-07-06 复盘补充：真实日志 `20260706-152846` 显示 DeepSeek 网页最后只输出“接下来将生成分析报告”，DevSeek 正确不应结算成功；但 UI 暴露了 `Calling: list_dirtex复制下载`、`AFILE:...RESET` 等内部协议文本，并显示无恢复证据的“继续执行”。本类问题必须按 Claude Code/Codex 的边界处理：工具协议只进入工具事件和 EvidenceRef，Provider 短意图进入完整性门禁，checkpoint banner 只有登录/限流/响应损坏等恢复证据时才显示。

每个新能力必须先回答：

1. 它属于哪一层子闭环？
2. 低一层是否已有确定性 replay？
3. 是否会污染 stdout/JSONL 或把进度文本混入机器事件？
4. 是否能把 DeepSeek 输出转成结构化工件并验证？
5. 若真实 Provider 失败，是否能用假 Provider 稳定复现同一逻辑？

### 5.7 无进展循环的复盘规则

当 Agent 连续重复同一工具、同一提示词或同一错误时，不能继续叠加 prompt。必须按以下步骤收敛：

1. 判断重复发生在哪一层：Provider 输出协议、工具解析、工具执行、证据归类、任务状态、UI 展示或上下文注入。
2. 将重复样本归一为结构化 fixture，例如工具文本、工具结果、terminal evidence、written file evidence。
3. 在运行时接入共享收敛守卫：第二次重复给模型换策略提示，第三次仍无进展则停止任务并给出阻塞原因。
4. 如果停止后发现用户需求其实可解决，必须修补权威边界或补齐工具方言，而不是让用户再次输入同义提示。
5. 修复完成后同时跑真实 provider smoke 和可重复单测；真实 smoke 只证明样本存在，逻辑正确性由单测和 replay 证明。

### 5.8 从基本编程智能体到优秀编程智能体

迭代路线按能力台阶推进，不跳级。

| 台阶 | 能力目标 | 自动验收 |
| --- | --- | --- |
| A0 Chat | 能通过 CLI/JSONL 完成一次请求响应 | L0/L1 事件顺序和退出码 |
| A1 Code artifact | 能产出结构化文件工件 | L3 解析 `[TOOL:create_file]` 或代码块 |
| A2 Build/run | 能把代码写入临时工作区并编译运行 | L3 本地 `g++` 编译运行通过 |
| A3 Modify existing | 能保留旧行为并添加功能 | replay fixture 对比旧输出和新输出 |
| A4 Repair | 能根据失败证据修复并重跑原命令 | runtime replay 必须包含失败证据和二次验证 |
| A5 Multi-file | 能维护多文件项目结构 | fixture 覆盖 include/path/build command |
| A6 Review/QualityGate | 完成态绑定 diff、命令、退出码和风险 | QualityGate/ReviewLedger 事件断言 |
| A7 Resume/reload | 续作不盲目重放副作用，reload 状态一致 | new session/resume/reload 三 fixture |
| A8 Real provider | 真实 DeepSeek Web/API 与假 Provider 共享同一 Agent Core | L4/L6 smoke 只验证接入和模型协议 |
| A9 Top agent | 能处理长任务、并发、hooks/skills/subagents/MCP、worktree | benchmark、canary、趋势报告 |

Claude Code / Codex 的优秀实践给 DevSeek 的启发是：CLI、IDE、非交互、hooks、skills、MCP、subagents、checkpoint、worktree 和 review 都必须围绕同一 agent loop，而不是每个入口复制业务逻辑。因此 DevSeek 的每个台阶都必须先强化 Agent Core，再扩展 Surface。

## 6. 针对当前问题的设计修正方向

这次 X11 问题后续修复不应再继续补 `if timeout then review`。

必须做的重构：

1. 新增 `ValidationStateService` 或同等领域服务，统一把工具结果归一为 `ValidationState`。
2. 新增 `VisualReviewGate`，从 Prompt、任务类型、命令、源码特征、终端行为判断是否进入人工确认。
3. `AgentTask` 增加 `validationKind` 或引入独立 `ValidationTask`，不要把运行验证伪装成普通 `analyze`。
4. `TaskTodoLedger` 不再直接查询 `findBlockingTerminalFailureEvidence`，而是消费 `TaskEvidenceState`。
5. `QualityGateService` 明确支持 `pass / fail / blocked / manual_review_required`。
6. `AgenticHistory` 存储事件溯源状态，reload 不重新推断。
7. `WebView` 对 `manual_review_required` 使用黄色/蓝色“等待人工确认”，不得红色失败；保留文件改动，不自动接受。
8. 每个修复必须新增 runtime replay 和 surface replay，覆盖 new session、resume、reload 三条路径。

## 7. 一次修正问题的工作法

后续遇到同类问题，执行顺序固定为：

1. **Freeze**：冻结当前用户截图和日志，记录现象。
2. **Trace**：画出事件链路，定位是 planner、tool、evidence、ledger、gate、surface、history 哪一层错。
3. **Matrix**：列出同类横向分支，不只看当前截图。
4. **Replay first**：先写失败 replay，确认能稳定失败。
5. **Design fix**：改领域边界，而不是在出错分支补条件。
6. **Cross-layer test**：至少跑 unit + runtime replay；涉及 UI 跑 surface replay。
7. **Release loop**：extension/bridge 行为变更必须 compile/package/install。
8. **Retrofit docs**：重复错误进入实施原则、AGENTS.md 或专题设计。

验收标准：

1. 同类矩阵全部有测试。
2. reload/history 与实时事件一致。
3. 手工测试只验证真实 Provider 和视觉效果，不再承担逻辑回归职责。
4. 代码变更落在正确领域服务，不让 `agent-loop.ts` 和 `extension.ts` 继续吞职责。

## 8. 对 DevSeek 的长期迭代策略

DevSeek 要成为顶级编程智能体，核心不是“多补几个规则”，而是建立可进化系统：

1. **把每次失败变成资产。** 手工截图、Provider 异常、用户反馈都进入 replay store。
2. **用设计边界吸收复杂性。** 权限、工具、证据、验证、审查、历史、UI 都有自己的服务和事件契约。
3. **让测试贴近真实用户旅程。** 不是只测 helper，而是测 Agent 从 prompt 到最终 UI 状态的完整行为。
4. **保持模型可替换。** DeepSeek Web、API、CLI mock 都走同一个 Agent Core；Provider 只负责生成事件，不拥有工具和质量门禁。
5. **把人工确认正规化。** 顶级 Agent 不会把不可自动判断的视觉结果伪装成成功，也不会误报失败；它会保留证据、请求用户确认、可继续迭代。
6. **把重复错误写进规则。** 两次以上出现的问题必须沉淀到实施原则、测试 fixture、架构守卫或技能，而不是靠记忆提醒。

## 10. 诊断日志基线

DevSeek 需要保留真实执行证据链，避免继续依赖截图猜测根因。日志实现必须与 DevSeek 项目代码同级，作为共享基础设施被 Extension、Bridge、Agent、工具执行器共同调用，而不是散落在具体功能内部。

默认落盘位置：

```text
<被操作项目根目录>/.devseek/runs/<YYYYMMDD-HHMMSS>.log
```

默认文件数量保持克制：一次顶层执行只生成一个 JSONL 日志文件，事件、payload、版本、工具、UI、验证都按写入顺序进入同一文件。

```text
<YYYYMMDD-HHMMSS>.log
```

关键原则：

1. 时序以 `.devseek/runs/<runId>.log` 为准，每行是 JSON，必须包含毫秒级 `ts`、单调 `seq`、`source`、`tag`、`phase`、`event`、`runId`。
2. prompt、response、DOM 片段等大文本也写入同一个文件，事件名使用 `payload-recorded`，并带 `length` 与 `sha256`，避免人类排查时跨文件拼时序。
3. 文件名使用 `runId`，时间写在日志文件名和每条事件的 `ts` 中；`runId` 精确到秒，不追加随机串。
4. Extension 在一次顶层 Agent 执行开始时生成 `runId`，所有模型调用、工具调用、验证、UI 事件都复用这个 `runId`。底层 Provider/HTTP/Bridge 不允许自建“会话事实”。
5. `<runId>.log` 第一条记录必须是 `run-started`，写入 DevSeek 版本号、build channel、build id、git commit、workspaceRoot、logPath 和进程 pid；后续各参与者可写入 `participant-started`。
6. 日志等级分为 `off/error/info/debug/trace`。测试版默认 `debug`，发布版默认 `info`。
7. token、cookie、authorization、password、secret、api key、session、credential 等字段必须脱敏。
8. 后续 replay 测试从 `.devseek/runs/<runId>.log` 生成，不再依赖手工截图复现。

版本规则：

1. Release 版本使用标准语义化版本：`MAJOR.MINOR.PATCH`，例如 `1.0.1`。
2. Debug 版本使用同一个 release 基线加预发布号：`MAJOR.MINOR.PATCH-debug.YYYYMMDD.tHHMMSS.g<commit>`，例如 `1.0.1-debug.20260702.t184501.g343b2f5`。
3. Debug 包可高频生成，每次打包都应产生不同版本号，避免 VS Code 安装后无法确认当前运行的是哪一次构建。
4. VSIX 同时输出 `devseek-netai-latest.vsix` 和 `devseek-netai-<version>.vsix`；测试安装用 latest，问题复盘用 versioned 文件。
