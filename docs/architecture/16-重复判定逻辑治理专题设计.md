## 1. 问题结论

本轮 `shape_manager` 连续测试暴露的根因不是某一个函数写错，而是 DevSeek 在多个阶段存在“相同语义、多份实现”的结构性问题：

1. A 处已经把 DeepSeek 网页输出识别为工具调用，B 处仍把同样文本当普通回复显示。
2. A 处已经把图形/交互程序超时判定为需要人工确认，B 处仍按终端失败触发修复。
3. A 处已经过滤无关历史，B 处仍把旧 session 摘要注入请求。
4. A 处已经稳定使用项目 `build/`，B 处仍从另一路径执行或展示旧路径。
5. A 处已经把验证完成显示为成功结论，B 处仍显示内部执行标签或红色失败。

这些问题共同指向一个架构缺陷：同一类事实在不同层被重复解释，缺少单一事实源和统一状态机。

## 2. 治理目标

本专题的目标是让 DevSeek 全部代码逐步满足以下约束：

1. 同一业务判断只能有一个权威归属者。
2. 工具协议、执行结果、上下文范围、任务状态、UI 文案不得各自解析原始字符串。
3. 下游模块只能消费结构化结果，不能重复实现正则、关键字、状态码或路径推断。
4. 每个权威判断必须有 contract test 和至少一个跨阶段 replay test。
5. 每次修复问题必须修缺陷类别，审计兄弟入口，避免“当前截图修了、另一路径仍旧”。

最终状态：DevSeek 的 Agent Core 像 Claude Code / Codex 一样，以清晰的 command/event、tool result、execution outcome、surface adapter 边界流转事实，而不是让多个文件各自猜测模型输出和运行结果。

## 3. 高风险重复区域

| 区域 | 重复表现 | 目标归属 |
| --- | --- | --- |
| 工具协议 | `read_file`、`grep_search`、`search_content`、DSML、XML、Calling 格式在 parser、webview sanitizer、response checker 中各自维护 | `ToolProtocolRegistry` + `ToolCallNormalizer` |
| 响应完整性 | Bridge、provider recovery、webview 清理分别判断 incomplete tool block、继续生成、响应损坏 | `ResponseIntegrityService` + `ProviderRecoveryService` |
| 本地执行 | `execution-planner`、`local-execution`、`terminal tool`、`validation-service` 各自解释 timeout、exitCode、GUI 程序 | `ExecutionOutcomeClassifier` |
| 验证任务 | Build、Runtime、VisualReview 混在 `analyze`、`run_terminal`、QualityGate 中 | `ValidationOrchestrator` |
| Todo 状态 | Todo、TaskLedger、ReviewLedger、QualityGate、history reload 分别 settle 成功/失败 | `TaskStateMachine` |
| 上下文选择 | 当前 prompt、session history、memory、active editor、changed files 多处拼装 | `ContextScopeResolver` |
| UI 展示 | 后端 title、webview activity、final summary、pending edit notice 各自生成文案 | `AgentDisplayPresenter` |
| 文件读写 | 大文件读取、范围读取、候选文件、写盘结果、diff 展示分别处理路径和截断 | `FileContextService` + `WorkspaceEditService` |
| 构建目录 | CMake build 路径由多个执行分支生成 | `BuildLayoutResolver` |
| 工作区路径与意图 | 文件路径、目录路径、计划请求、实现请求在 intent、workflow、interaction 中各自用不同正则判断 | `workspace/path-patterns` + `IntentClassifier` |

## 4. 设计原则

### 4.1 单一事实源

每类判断必须收敛到一个领域服务：

```text
Raw provider output
  -> ToolProtocolRegistry / ToolCallNormalizer
  -> AgentCommand
  -> ToolExecutor
  -> ToolResult / Evidence
  -> ExecutionOutcomeClassifier / TaskStateMachine
  -> AgentEvent
  -> AgentDisplayPresenter / SurfaceAdapter
```

禁止下游绕过结构化对象直接重新解释原始文本。

### 4.2 状态机优先于布尔值

避免 `ok=true/false` 承载过多语义。执行和验证至少需要这些状态：

```text
not_started
running
passed
failed
blocked
manual_review_required
cancelled
corrupted
```

规则：

1. `passed` 只来自确定性成功证据。
2. `failed` 只来自确定性失败证据。
3. `manual_review_required` 用于 GUI、图形、浏览器、交互式程序已启动但自动系统无法判断内容。
4. `blocked` 用于权限、登录、环境、用户输入等外部阻塞。
5. `corrupted` 用于 provider 输出损坏或未完整生成。

### 4.3 展示层不能拥有业务判断

WebView 只负责把 `AgentEvent` 渲染成人类可读界面。它可以有展示格式化函数，但不能独立决定：

1. 工具是否应该执行。
2. 任务是否成功。
3. 是否需要自动修复。
4. 是否应该重试 provider。
5. 是否应该读取历史上下文。

### 4.4 修复即审计

任何 bugfix 必须回答：

1. 这个问题属于哪个缺陷类别？
2. 同类判断还有哪些入口？
3. 当前修改是否进入权威归属服务？
4. 下游是否还有重复判断？
5. 是否新增了 contract test 或 replay test？

没有完成这些问题的修复，不能算闭环。

## 5. 目标组件

### 5.1 ToolProtocolRegistry

职责：

1. canonical tool name。
2. provider/model 输出别名。
3. 参数别名。
4. 风险等级和权限类别。
5. webview sanitizer 所需的工具词典生成源。

验收：

1. `fake-tool-parser`、`tool-call-normalizer`、webview sanitizer 不再手写不同工具列表。
2. 新增工具别名时，只改 registry 和对应测试。

### 5.2 ExecutionOutcomeClassifier

职责：

1. 统一解释 exitCode、timeout、stderr/stdout、known build errors、GUI launch evidence。
2. 输出 `ExecutionOutcome`，而不是散落的 `ok/reviewRequired/reason`。
3. 区分 BuildValidation、RuntimeValidation、VisualReviewValidation。

验收：

1. `execution-planner`、`local-execution`、terminal tool、validation service 共用分类器。
2. 图形窗口启动后关闭，不再被误判成需要自动修复。
3. 编译错误仍保持硬失败并提供具体文件证据。

### 5.3 TaskStateMachine

职责：

1. 统一消费 ToolResult、ExecutionOutcome、QualityGate、ReviewLedger。
2. 输出任务状态和可展示摘要。
3. 保证实时执行、reload history、checkpoint resume 使用同一状态规则。

验收：

1. Todo 不能靠字符串包含 `失败`、`执行完成` 推断状态。
2. 继续执行和新对话对同一证据得到同一状态。

### 5.4 ContextScopeResolver

职责：

1. 决定当前请求相关的 project/session/history/memory/files。
2. 过滤无关旧 session。
3. 输出结构化 `ContextScope`，供 Prompt Builder 使用。

验收：

1. 当前项目只带当前项目相关历史。
2. 用户后续追问不重新扫描整个 workspace。
3. memory 注入只基于当前 prompt 和明确路径锚点。

### 5.5 AgentDisplayPresenter

职责：

1. 将 AgentEvent 转为用户可读标题、详情、按钮、摘要。
2. 隐藏内部命令、冗长路径、原始日志，必要时放入详情。
3. 保持 Working、Todo、final summary、pending edit notice 文案一致。

验收：

1. 不再出现同一事实一处绿、一处红。
2. 不再把内部动作如 `运行 main.cpp` 当最终结论。
3. 用户看到的是“编译通过、运行需人工确认、修改已保留、下一步可继续测试”。

### 5.6 BuildLayoutResolver

职责：

1. 统一 C/C++/CMake 项目的 build 目录和可执行文件发现规则。
2. 生成稳定构建路径，例如项目内 `build/`。
3. 禁止不同路径分支各自产物。

验收：

1. 同一项目多次编译不再产生 `.devseek-build`、`build`、临时目录混用。
2. run-only、compile-run、repeat run 共用同一 resolver。

## 6. 全面重构路线

### Phase 0：重复判定盘点与守卫

目标：先找出全部重复判断点，禁止继续扩大。

动作：

1. 建立重复逻辑 inventory：工具名、状态名、exitCode、timeout、build path、history scope、UI title。
2. 对高风险关键字建立静态守卫：例如 `search_content`、`执行完成`、`reviewRequired`、`自动验证按失败处理`。
3. 在 `workflow-compliance.test.mjs` 中增加“不得绕过权威服务”的 architecture guard。
4. 输出第一版治理清单，标记每个重复点的 owner 和迁移优先级。

完成标准：

1. 新增逻辑不能绕过已有 owner。
2. 重复点清单可持续更新。

### Phase 1：工具协议收敛

目标：杜绝“模型输出像工具但 DevSeek 不执行/前端显示出来”的问题。

动作：

1. `ToolProtocolRegistry` 成为工具名和别名唯一来源。
2. WebView 工具过滤词典改为构建期生成或测试强同步。
3. Parser、normalizer、integrity checker 使用同一工具别名策略。
4. 建立 DeepSeek Web 输出样本库，覆盖 DSML、XML、Calling、function-style、Markdown-bold Calling。
5. 用同一批样本同时回放 `fake-tool-parser` 和 WebView sanitizer，确保后端能执行的伪工具文本不会在前端泄漏。

完成标准：

1. 新增工具别名只需改一处 registry。
2. 同一 provider 响应在 parser、executor、webview sanitizer 中结果一致。
3. sanitizer 不再维护手写工具名或别名白名单，只消费由 `ToolProtocolRegistry` 生成的 WebView manifest。

进展：

1. 已新增 `ModelToolProtocolAdapter` 作为模型工具方言适配层，`parse`、`findStart`、`strip` 统一从 dialect registry 进入，避免 parser、执行器、UI 各自维护格式分支。
2. 已将 `[TOOL:]`、`Calling`、`Tool Arguments`、DSML、XML、`<TOOL_CALL>`、function-style、JSON 工具数组、ReAct `Action / Action Input` 纳入同一适配入口。
3. WebView outbound sanitizer、final summary 清理、terminal guard 均复用 `stripToolCallBlocks` / `containsFakeToolCallProtocol` 的统一判定结果。
4. 已补充 ReAct split streaming 回归：模型先输出 `Action: read_file`、后输出 `Action Input: {...}` 时，UI 不泄漏协议文本，执行器也不会把协议文本送入 shell。
5. 已补充真实 DeepSeek Web 烟测样本：网页端会返回 `Action: read_fileAction Input: {...}` 这种黏连 ReAct 方言；`ModelToolProtocolAdapter` 必须能解析、定位、剥离该格式，不能要求 `Action Input` 前有换行或词边界。
6. 已新增工具结果边界隔离：模型响应里夹带 `[工具执行结果]`、`[工具返回]` 或 `[read_file:]` 等 provider-authored transcript 时，`ModelToolProtocolAdapter` 只允许 `parse`、`findStart`、`strip` 处理边界之前的工具请求区，边界之后的旧工具标记、命令和代码块不再进入执行链。
7. `run-log-replay` 已同步使用同一隔离规则：污染响应保留为诊断 warning，legacy build path、malformed tool block、run_terminal 统计只基于工具请求区，避免 replay 本身成为第二套协议判断。
8. 2026-07-03 补充真实日志回归：当用户请求包含明确工作区目录、代码实现、编译或验证时，`IntentClassifier` 必须进入 edit/run 路径；如果 Provider 只返回源码代码块而没有写盘、工具或终端证据，`run-log-replay` 必须诊断为 `source-output-without-application`。

### Phase 2：执行和验证状态收敛

目标：杜绝“实际运行成功/需人工确认，但 DevSeek 判定失败”的问题。

动作：

1. 新建 `ExecutionOutcomeClassifier`，统一 `cp.exec` 的 timeout、exitCode、硬失败、图形/交互人工确认分类。
2. 把 `execution-planner`、`local-execution`、terminal tool、validation service 的 timeout/exitCode/build error 分类迁入分类器。
3. 将 `reviewRequired`、`reason`、`exitCode` 收敛为 `ExecutionOutcome`。
4. QualityGate、repair loop、Todo settle 只消费 `ExecutionOutcome`。

完成标准：

1. GUI/图形/交互程序进入 `manual_review_required`。
2. build failure 进入 `failed`。
3. provider/login/environment 进入 `blocked`。

进展：

1. `execution-planner`、`local-execution`、`validation-service` 已消费 `ExecutionOutcomeClassifier`。
2. `terminal tool` 的长运行人工确认、timeout、exitCode 语义已迁入 `ExecutionOutcomeClassifier`，不再本地维护 `exitCode=-1` 或独立人工确认文案。
3. `agent/tool-loop` 解析终端人工确认 marker 和不确定执行证据时改为消费分类器 helper，避免写端和读端各自维护规则。
4. `agent/tool-loop` 对格式化终端输出中的退出码、未执行、人工确认 marker 的解释已迁入 `ExecutionOutcomeClassifier`，自身仅保留终端证据适配、命令分类和产物路径校验。

### Phase 3：任务状态和历史收敛

目标：实时执行、继续执行、reload window、历史记录显示一致。

动作：

1. 新建或强化 `TaskStateMachine`。
2. Todo、checkpoint、history、ReviewLedger、QualityGate 都消费同一状态。
3. 禁止各模块通过文本标题推断成功/失败。
4. 建立 replay fixture：新对话、续作、reload、失败重试、安全重试。

完成标准：

1. 同一证据在所有 surface 中状态一致。
2. reload 后不出现旧失败覆盖当前成功。

进展：

1. `agentic-loop` 的验证失败 Todo 更新已改为调用 `task-todo-ledger` 的 `settleValidationFailureTodos`，不再在 evidence recovery 侧维护独立规则。
2. `evidence-recovery.markValidationFailureTodos` 保留为兼容入口，但只转发到 `task-todo-ledger`，避免 agentic-loop 与两阶段 agent-loop 对 QualityGate 失败使用不同 Todo 状态规则。
3. `task-todo-ledger` 已承接 Agentic 初始 Todo、缺证据 Todo 重开、线性任务 Todo 完成/失败/推进、QualityGate Todo 追加等通用状态规则；`simple-file-task` 和 `agentic-loop` 不再直接手写这些状态迁移。
4. `evidence-recovery` 保留旧函数名作为兼容入口，但状态计算只转发到 `task-todo-ledger`。

### Phase 4：上下文和记忆收敛

目标：杜绝无关历史污染当前请求。

动作：

1. `ContextScopeResolver` 统一选择当前 session、project memory、changed files、active editor。
2. Prompt builder 只能消费 `ContextScope`。
3. 旧 session 摘要必须经过项目路径和当前 prompt 相关性过滤。
4. 对 follow-up 请求建立独立 replay case。

完成标准：

1. 当前项目之外的历史不会进入 DeepSeek 请求。
2. 简短追问不会重新触发全仓探索。

进展：

1. 2026-07-03 将显式工作区目标识别从“只认文件路径”扩展为统一 `hasExplicitWorkspacePath()`，目录路径如 `/home/ff/work/devseek_netai/code/shape_manager` 不再被普通聊天或模糊请求逻辑降级。
2. “规划方案，并通过代码实现/编译/验证”不再按只读 plan 处理；只要同一句请求明确要求落地或验证，就按执行型代码任务进入 Agent 路径。

### Phase 5：展示层收敛

目标：杜绝“底层事实正确，但 UI 提示吓人或互相矛盾”。

动作：

1. 建立 `AgentDisplayPresenter`。
2. WebView 的 Working、Todo、final summary、pending edit notice 使用同一 display model。
3. 后端 status title 只传语义码和结构化 detail，展示层负责友好文案。
4. 长日志默认折叠，正文只展示结论。

完成标准：

1. 用户看到的每条状态都能回答“发生了什么、是否需要我做什么”。
2. 内部命令、路径、原始日志不会挤占主反馈。

### Phase 6：大文件和胖函数拆分

目标：让后续 AI 和人工维护都能局部修改，不再因大文件导致读不全、修不全。

动作：

1. 对 `extension.ts`、`agent-loop.ts`、`webview.js` 做职责切片。
2. 每次迁移必须先建立公共接口，再迁移调用方。
3. 不为了低于 100 行而机械拆文件；小文件必须有明确领域职责。
4. 优先拆业务、数据、类型和规则；渲染细节可以保留在 webview，但不能承载业务判断。

目标阈值：

1. 新增生产文件优先 `100-800` 行。
2. 生产文件超过 `1024` 行必须审计职责。
3. 超过 `2048` 行必须制定拆分计划。
4. 普通函数优先 `<=100` 行。
5. 编排函数硬上限 `300` 行。

### Phase 7：Replay 与发布闸门

目标：以后不靠用户反复截图发现同类问题。

动作：

1. 每个线上截图问题转为 replay fixture。
2. 每个权威服务都有 contract test。
3. 每个跨阶段问题都有 surface replay。
4. 修改 extension/bridge 行为后仍执行 compile、package、verify packaged bridge、install VSIX。

完成标准：

1. 不能只靠真实 DeepSeek Web smoke 证明逻辑正确。
2. 真实网页测试用于最终验收，核心逻辑由可重复测试保障。

### Phase 8：Agent 自净化与无进展循环治理

目标：杜绝“重复同一工具、重复同一提示词、重复同一错误”的死循环。

动作：

1. 新建 `TaskConvergenceGuard`，由编辑循环和分析循环共同消费。
2. 以结构化证据判断进展：文件写入、可应用补丁、完成信号、不同工具证据，而不是模型自述。
3. 同一工具/同一反馈连续重复时，第二次向模型注入收敛提醒，要求改变策略或直接产出可应用修改。
4. 第三次仍无进展时停止当前任务，给用户展示“停止重复执行”的明确原因，保留已有变更和证据。
5. 该逻辑必须在运行时集中实现，不能在不同工具执行器、UI 卡片或 prompt builder 中各写一份。

完成标准：

1. 简单修改请求不能因为模型重复 `read_file`、`search_content` 或原始协议文本而进入长循环。
2. 无进展重复被阻断时，DevSeek 给出可理解的阻塞原因和下一步，而不是继续刷新相同任务卡片。
3. 新增循环入口必须接入同一个收敛守卫或等价状态机。

## 7. 变更闸门

后续任何 bugfix、功能添加、重构都必须满足：

1. 先定位缺陷类别，不只定位当前截图。
2. 先找 owner，没有 owner 就先建立 owner。
3. 禁止在第二个地方复制同一判断。
4. 如果必须暂时保留兼容入口，必须标注迁移目标和删除条件。

## 10. 成功标准

本专题完成后，DevSeek 应达到：

1. 任一工具别名新增不会出现后端能识别、前端不能过滤的分裂。

3. 任一任务状态只由状态机 settle，不再由 UI 或 history 文本反推。
4. 任一上下文注入只由 ContextScopeResolver 决定。
5. 任一用户可见文案只由 display/presenter 层格式化。
6. 关键路径都有 contract test、replay test、workflow compliance guard。

这才算真正解决“A 处修了，B 处仍按旧规则走”的根因。
