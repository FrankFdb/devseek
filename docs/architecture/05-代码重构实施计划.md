## 1. 实施原则

1. **修改前竞品对标第一原则：任何实现、优化、缺陷修复或重构落代码前，必须先把 DevSeek 当前做法与 Claude Code/Codex 对同类问题的最佳工程行为对标，确认 DevSeek 方案是当前架构下的最优解。** 对标结论必须落到任务理解、工作目录、工具边界、权限审计、证据闭环、失败恢复、历史可追溯和 UI 交付策略；不能只写口号，也不能在未完成对标时直接堆局部补丁。
2. **架构优先修改原则：所有代码修改都必须先从架构边界、职责归属和长期演进角度判断，禁止不定时、补丁式、只修当前截图的局部修改。** 如果现有架构、状态机、职责边界、工具协议、权限审计、验证闭环、恢复路径或 UI 交付边界不合理，必须先重构到同类问题的最优方式，再落具体功能或修复；凡触达旧代码，即同步审计并收敛不合理实现，不得在错误位置继续堆逻辑。
3. **任务形态识别与既有工程集成原则。** 落代码前必须先判断当前任务属于既有大项目/正式项目内实现、独立编程任务、只读分析/设计/文档、验证修复续作或其他类型；如果是既有工程内新增功能，设计阶段必须先收集与原主控/平台/遥控器等整体架构的关系、职责边界、主入口、线程/事件模型、消息协议、数据结构、构建测试入口和可复用方法，再在这个背景下实现。Planner 不能按固定文档数量或固定模板驱动正式项目任务，必须按“项目级事实调查 → 设计/接口/修改清单 → 代码实现 → 编译/测试/验证”的工程阶段动态规划；模型生成的参考模块、通讯链路、接口边界等 explore/analyze 任务属于实现证据，后续规范化不能当作噪音清理掉。涉及“参考既有通讯模块方式”的任务，必须从参考模块反向追踪项目级真实通讯链路，扩大到全项目通讯入口/出口、`uart*_tx/rx_main` 或等价通道、`TunnelTransport`/分片组装、MAVLink tunnel、publisher/subscriber、topic/payload_type/命令号、路由调度和主流程调用点，并把这些证据写入设计、接口和修改清单；禁止只在用户给出的目录内自洽实现。禁止把正式项目需求做成与主流程脱节的独立小模块、样例 `main` 或孤立测试程序；只有明确是独立任务、原型或练习时，才允许自建入口和自洽目录。
4. **顶级编程智能体目标必须持续校准。** 每次迭代都要推动 DevSeek 在任务理解、工具边界、证据闭环、历史可追溯和用户可控性上追平甚至超越 Claude Code/Codex；不得用局部补丁掩盖错误边界。
5. **先建立边界，再迁移职责，最后增强能力。** 不做“大爆炸重写”，但目标态必须是革命性的 Headless Agent Core / Agent Runtime；每一阶段都必须能独立测试、独立回退，多入口重构在 `devseek-multi` 分支推进，main 只接收阶段完成、测试通过、可回退的合并。
6. **入口和 Surface 只能做适配。** `extension.ts`、CLI main、Desktop main 等入口只能注册 surface、注入依赖、启动服务和做生命周期清理；VS Code WebView、命令、Inline Chat、CLI TUI、JSONL、Desktop/local Web 都只能把用户输入转换为 `AgentCommand`，把 `AgentEvent` 渲染为界面；同一任务事实必须由 Headless Agent Core 产生，不能复制 Agent 业务判断。
7. **权限、审计和证据闭环是新增路径准入条件。** 任何写盘、终端、网络、MCP、VS Code command 的新增路径，都必须先接入权限、审计、EvidenceRef、Checkpoint、ReviewLedger 和 QualityGate；模型 prose、UI 状态或半截 Provider 输出不能绕过事实层结算任务。
8. **同类型问题必须系统性修复。** 任何 bugfix、优化或重构都不能只修当前复现路径；必须审计同类入口、状态流、消息/工具/权限/验证边界和历史恢复路径。若存在重复逻辑或多处相同判断，必须收敛为单一抽象、单一出口或单一领域服务，并补上覆盖同类路径的测试与静态守卫；除非有明确架构差异，完全一样的逻辑在项目中原则上只能有一份。
9. **弱工具通道兼容层负责协议污染修复，Agent 状态机负责重复失败收敛。** DeepSeek Web 等非原生 function-calling 通道把源码、JSON、工具块通过网页文本传输时，转义污染、DOM 文案污染、截断和旧 bridge 串线都必须在 Provider/Tool 兼容层归一为可信 ToolCall/EvidenceRef，不能把协议污染原样交给业务层或用户。模型同一工具、同一路径、同一原因连续失败时，必须作为一等运行事实进入 Agent 状态机，先要求改变策略或写入粒度，超过阈值必须失败结算并保留原因；不得靠继续提示模型、UI completed 或 task_complete 覆盖无进展事实。
10. **六大设计原则是修复准入条件。** 每次修改前后都要用单一职责、开闭、里氏替换、接口隔离、依赖倒置和迪米特法则自检；发现复制逻辑、跨层调用、UI/Provider/Agent/Workspace 互相知道过多、或业务层依赖具体基础设施时，应先重构边界再落修复，不得把局部补丁当成最终方案。
11. **代码规模必须服务 AI 可维护性。** 行数阈值只是审计触发器，不是重构目标：生产代码文件超过 1024 行必须审计职责，复杂生产模块超过 2048 行必须制定拆分计划，超过 3000 行必须作为重构优先级处理；普通函数控制在 100 行以内，复杂编排函数控制在 300 行以内。拆分必须让职责更单一、依赖方向更正确、后续 Claude Code/Codex 类能力更容易接入。
12. **文件上下文和工具协议必须词典化治理。** 大文件读取不得隐式截断；必须通过统一文件上下文服务返回总行数、返回范围、截断状态和续读方式。工具名、工具别名、参数别名、权限分类、执行路径和 UI 清理必须以 `tool-registry` 为单一事实源，并用测试守卫前后端镜像同步，避免模型输出新别名时只显示不执行。
13. **修改 Extension 或 Bridge 行为后必须执行本地发布闭环。** 按仓库要求完成 compile、package、install VSIX，并确认 VS Code 当前运行版本与本次构建一致。
14. **分层闭环测试准入原则：用户插件实测不能作为主要缺陷发现手段。** 任何 Agent/Provider/工具/文件交付修复都必须先建立 `unit 测试 -> run-log replay 测试 -> 仿真 DevSeek Surface + DeepSeek Web 交互测试 -> 真实 DevSeek 插件 + 真实 DeepSeek Web live 抽查` 的分层门禁；unit 守纯策略和边界，replay 固化真实失败日志，仿真交互守同一用户场景下的 Provider 往返、工具证据、文件落盘、QualityGate 和最终交付。真实插件 live 测试因依赖账号、网页和人工登录，只能作为显式 opt-in 发布/回归抽查，但凡改动 VS Code Extension、Bridge、Provider 网页交互、文件交付或状态结算，必须至少提供可运行的 live harness，并在需要真实网页确认时执行；live 失败必须先沉淀为 replay 或仿真 fixture，再修复和回归，避免把人工插件截图测试变成反复试错主流程。
15. **上下文层级与同会话复用原则。** 固定不变的 Agent 行为规则、项目规则、工具协议、工程原则和 Provider 约束必须作为稳定会话基线管理，不能在同一个 DeepSeek Web/Provider 会话的每轮交互中重复塞入用户消息；后续轮次只发送新增用户纠偏、工具结果、恢复指令、验证证据和必要摘要，并显式说明沿用上一轮规则。若 Provider 支持 system/developer/user 分层，应使用原生层级；若 Web bridge 只能发送单一文本，必须在 bridge 边界用会话指纹、traceRunId 和增量 prompt 模拟该分层。任何 prompt 压缩都不能丢失本轮任务目标、真实工具证据、写盘/验证结果和失败事实；省 token 不能以牺牲证据闭环为代价。
16. **阶段成果物质量验收原则：日志成功不是交付成功。** 每次正式项目或编程任务测试，除了确认 Provider、工具、状态机和 run-log 事件外，必须逐阶段验收实际成果物是否达到编程智能体标准：需求/原项目事实调查是否具体可追溯，设计/接口文档是否可交给对端实现，原代码修改清单是否明确文件/函数/风险/验证方式，代码是否无协议污染并符合项目边界，编译/单测/自闭环验证是否有证据，最终交付是否给出路径、结论和下一步。任一阶段成果物不达标，不能因为 `completed`、文件存在或 UI 正常而结算成功。
17. **同任务参考实施与质量对标原则。** 每次正式项目能力测试必须允许用同一用户任务生成一份 Codex/Claude Code 风格的参考实施或参考分析，再把 DevSeek 产物与参考产物逐项对比：原项目调查深度、具体常量/数值/协议字段、接口文档完整度、原代码修改清单、代码集成边界、验证证据和用户可读性。对标结论必须进入测试报告，不能只看 `completed` 或文件存在。
18. **测试产物隔离原则。** 真实项目测试不得把仿真文档和代码散落到正式源码目录；每次测试必须在目标模块下创建到分钟级时间戳目录，例如 `202607101055/`，其下固定分为 `docs/` 和 `src/`，文件名使用正式业务命名，不添加 `selfloop`、`codex`、`verify` 等临时后缀。需要修改正式原代码时，测试产物先在文档中列出“原有代码修改清单”，明确文件、函数/类、改动内容、原因、风险和验证方式。

### 1.1 代码规模治理执行策略

1. **阈值分级。** 生产代码文件 800 行进入关注清单，1024 行必须说明职责边界，2048 行禁止继续承载新职责并必须拆分计划，3000 行以上列为优先偿还对象；普通函数建议 80 行以内，超过 120 行必须解释，复杂编排函数 300 行为硬上限。
2. **增量守卫。** 新增或修改代码不得让已超限文件继续膨胀同一职责；确需触达超限文件时，本次改动必须同时迁出一个可复用纯函数、服务或 adapter，或者在任务报告中说明为什么本次只能先补测试并登记后续拆分。
3. **重复逻辑归一。** 协议解析、工具调用清洗、权限判断、路径解析、构建验证、Provider 恢复、UI 事件翻译等跨入口逻辑必须集中到单一模块；WebView 兜底逻辑只能作为显示防线，不能成为业务事实来源。
4. **测试守门。** 每次修复缺陷类必须补至少一个“同类变体”测试，而不是只覆盖截图文本；涉及重复逻辑迁移时，优先加纯函数单测，再加 UI/集成回归。
5. **滚动偿还。** 旧大文件采用分阶段瘦身：先抽纯函数和协议模块，再抽应用服务，最后让入口文件只保留组合装配。不得为了行数而切出错误抽象。
6. **避免微文件化。** 少于 100 行的生产逻辑模块必须有明确职责边界、复用入口或依赖方向收益；不得为了降低行数把连续业务流程切成难以导航的碎片。小型配置或 manifest 只有在消除跨入口重复事实源时才允许独立存在，例如生产 HTML、打包脚本、测试 harness 需要共享同一运行清单。
7. **WebView 拆分先迁出非描画事实。** WebView 层可以保留 DOM 描画、样式注入和交互渲染；优先迁出工具协议、策略表、生成内容识别、路径/上下文规则、状态判定等无 DOM 的业务事实和纯函数。不得为了降低 `webview.js` 行数先拆 CSS/HTML 字符串，除非该渲染模块本身已经形成独立 Surface Adapter。

### 2.1 Phase 9 后滚动审计结论（2026-06-21）

Phase 0 到 Phase 9 已经把 DevSeek 从“DeepSeek Web 包装器 + 大入口文件”推进到“有权限、工具、Provider、恢复、质量门禁和 UI 协议边界的 Agent 插件”。但按顶级编程智能体目标审计，当前真正的瓶颈不是某个文件多几十行，而是 **Headless Agent Core 尚未成为唯一业务事实来源**。

当前已达成：

1. Provider Runtime 已统一 DeepSeek Web 文本工具、API/native tool calling、fallback 和 secret redaction。
2. Task checkpoint、provider recovery、response corruption safe retry、QualityGate、ValidationEvidence 已能阻断“模型说完成但事实失败”。
3. WebView HTML、artifact UI、pending diff、task history UI、view provider、VS Code command registration 已从 `extension.ts` 迁出到 `ui/*` 或 `app/*`。
4. 架构守卫能发现 `app/*` 反向依赖 UI、legacy 入口继续膨胀、领域边界缺公共出口等问题。

仍需修正的根本差距：

1. `runChat` 仍在 VS Code 入口文件中承担 Agent 应用编排，导致 CLI/JSONL/Desktop 复用困难。
2. `routeChat` 仍绑定 extension session state，Provider 调用、历史追踪和错误恢复需要迁入应用层 runtime。
3. VS Code Surface 与 Agent Core 之间还不是完整 `AgentCommand` / `AgentEvent` 协议，当前仍有一部分 direct callback。
4. ReviewLedger 还没有达到 Codex/Copilot 类 review pane 的 per file/per hunk/stage/revert/inline feedback 完整能力。
5. Skills/hooks/subagents/worktrees 仍是设计扩展点，尚未成为可注册、可权限控制、可审计的运行时能力。

Phase 10 因此必须优先做“应用内核抽离”，而不是继续做零散 UI 修补。

### 2.2 P0/P1 状态机与运行账本收口（2026-07-06）

按实施原则先对标 Claude Code/Codex：顶级编程智能体会把模型输出完整性、工具意图、工具执行、证据、验证、checkpoint 和 UI delivery 串成同一条事实链；任何一段失败都不能被后续短答、todo 或 UI completed 覆盖。

本轮已落地：

1. `AgentRuntimeStateMachine` 成为运行时结算门，显式覆盖 `needs_context / tool_requested / tool_executed / evidence_collected / verified / delivered / failed`。
2. `ProviderOutputIntegrity` 成为 DeepSeek Web 响应完整性分类门禁，BridgeProvider、read-only recovery、Runtime Replay 复用同一分类事实。
3. `run-log-replay` 固化工具意图未执行、工具后短答、Provider 断线/截断、旧 bridge、缺少结论、UI 假完成等样例。
4. ToolLoop 返回 `EvidenceRef[]`，ToolCall/EvidenceRef 开始成为业务事实层输入；fake-tool-parser 仅作为 provider 兼容解析来源。
5. `AgentRuntimeLedger` 连接 TaskHistory、Checkpoint、IdempotencyGuard，建立可恢复、可回放、可审计的任务账本核心。
6. 收敛确认不必要的兼容/重复判断：只读无工具恢复并入 `AgentRuntimeTurnPolicy`，删除独立 `read-only-task-recovery` 模块；`TaskTodoLedger` 不再把 `task_complete` 当只读完成证据，而是消费 `AgentRuntimeStateMachine` 结算；`TaskConvergenceGuard` 改为接收统一 `ToolCall`，不再依赖 fake-tool 兼容类型。
7. 状态机进一步区分只读回答证据与写盘任务证据：`modify/create/delete` 等非只读任务不能靠“已完成”文字或 `task_complete` 自证完成，必须有写盘、终端或验证事实。
8. Provider 完整性门禁收敛为统一控制面分类：登录、验证码、人机验证、限流和错误页必须按 Provider 页面/协议形态识别，不能裸匹配“验证码”“请求失败”等业务词；Runtime、Replay、Recovery 复用同一分类规则，避免 DeepSeek 已返回完整分析但 UI 展示前被误拦截。
9. Surface 协议泄漏进入同一门禁：真实日志中 Provider 工具调用被 WebView/DOM 污染成 `Calling: list_dirtex复制下载`，并混入 `AFILE:...RESET` 路由标记；parser/sanitizer 必须按注册工具名前缀识别污染工具名，`Call/Calling` 必须有英文词尾边界以免误伤 `tool_calls`，无恢复证据的 checkpoint 不得显示“继续执行”。

后续 Phase 10/11 的重点调整为：继续把 `runChat`、edit/run 兼容路径、ReviewLedger/QualityGate 事件化迁入 Headless Agent Core，VS Code 入口只保留 Surface Adapter 和 composition root。
