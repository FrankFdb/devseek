## 1. “100% 优秀”的可验证定义

“100%”不是声称能够解决世界上所有未知编程任务，而是指 DevSeek 在约定发布范围内的所有硬性资格门禁均通过，不存在已知 P0 缺陷，也不通过假成功、弱 oracle 或人工挑选日志提高分数。

达到 100% 发布资格必须同时满足：

1. **任务理解正确**：正确识别既有工程实现、独立项目、只读分析、文档交付、验证修复、续作和破坏性操作；约束只作用于对应对象，不能把“不要修改源码”扩大成“不要创建报告”。
2. **事实完全可追溯**：源代码数值、接口、依赖、命令结果和生成文件均引用可审计 `EvidenceRef`；最终产物中的强事实与证据逐项一致，禁止臆造。
3. **软件工程闭环完整**：调查、需求澄清、设计、实现、验证、审阅、交付按任务需要执行；不固定文档数量，也不为简单任务制造无关文档。
4. **状态结算唯一且诚实**：所有入口统一经过 Agent 状态机；任何中途 Provider、工具、写盘、验证或 Replay 失败都保留为失败事实，不能被后续文本覆盖。
5. **工具和副作用可靠**：文本工具、native function calling、MCP 都归一为 `ToolCall`；写盘、终端和 MCP 副作用具备 checkpoint、幂等与恢复边界。
6. **验证与用户要求一致**：自动选择 build/test/lint/run/read-back；无法自动验证时进入 `waiting_user` 或 `manual_review_required`，不能伪造通过。
7. **Provider 可替换**：DeepSeek Web 只是 Provider Adapter；Headless Agent Core、工具、证据、状态、验证和 UI 结算不依赖网页 DOM 或特定模型话术。
8. **用户体验清楚**：用户看到连续保留的阶段总结；具体读文件、搜索和命令折叠展示；能明确知道当前完成了什么、为什么阻塞、下一步是什么。
9. **架构债务收敛**：职责持续从超大编排文件外移，架构预算只能下降；迁移完成后删除不合理或无用旧代码，不保留无业务价值的兼容分支。
10. **真实资格达标**：同一干净提交通过本文第 8 节规定的确定性、仿真、真实任务和竞品对标门禁。

任何一项硬门禁失败，完成度都不能记为 100%。

## 4. 目标架构

### 4.1 TaskContract 是任务语义唯一来源

新增或收敛为一个 Provider 无关的 `TaskContract`，至少包含：

- `taskShape`：existing-project、standalone、inspection、documentation、verification、repair、resume、destructive。
- `objectives`：用户真正要求完成的结果。
- `inputs`：指定文件、目录、会话事实和用户提供资料。
- `deliverables`：文件、代码变更、文档、命令结果或只读结论，不固定数量。
- `constraints`：禁止修改的对象、允许写入的目录、语言、兼容和安全约束。
- `evidenceRequirements`：哪些结论必须由源码、命令、测试或用户确认支持。
- `verificationContract`：每个交付物的可执行验收条件。
- `completionPolicy`：什么情况下 delivered、failed、blocked 或 waiting_user。

意图分类器只负责构造或补充 `TaskContract`，不能直接决定“已完成”。计划、工具权限、QualityGate、Replay、UI 和恢复都消费同一个契约。

### 4.2 EvidenceRef 是事实唯一来源

所有工具结果归一成不可变 `EvidenceRef`：

- `evidenceId`、`operationId`、工具类型、工作区和运行版本。
- 源文件真实路径、行区间、内容哈希和读取时间。
- 命令、cwd、退出码、stdout/stderr 摘要和原始 payload 引用。
- 写盘前后哈希、diff、read-back 结果。
- 验证类型、状态、失败原因和是否需要人工确认。

模型可以总结 Evidence，但不能覆盖 Evidence。恢复、续作和最终回答都从 EvidenceStore 重建，不依赖网页聊天文本。

### 4.3 ArtifactClaim 连接证据和交付物

交付物中的可验证强事实必须转换成 `ArtifactClaim`：

- claim 内容和规范化值。
- 来源 `EvidenceRef`。
- 目标文件和位置。
- validator 类型，例如 exact、numeric、path-exists、symbol-definition、command-exit、schema。
- 验证状态和差异。

如果任务明确要求提取六个常量，六项都必须建立 claim 并与源码一致。只检查 `kMavTunnelCmdLicense` 关键词存在属于弱 oracle，必须禁止。

### 4.4 QualityPolicy 由任务契约组合

删除“所有正式项目都需要协议数值、遥控器接口和修改清单”这类领域硬编码。由 `TaskContract` 组合通用策略：

- 文档任务检查标题、结构、请求覆盖、事实 claim、路径和 read-back。
- 既有项目功能检查 repo 调查、集成点、修改范围、构建和回归。
- 协议任务仅在用户请求或代码证据表明存在协议时检查 schema、request/response、数值和兼容。
- 纯常量报告不生成实现方案、接口文档或修改清单。
- 独立项目不强制引用不存在的主控链路。

迁移完成后直接删除被新策略替代的领域专用判断和兼容分支，不同时保留两套完成判定。

### 4.5 单一 Headless Agent Core

统一状态至少覆盖：

```text
needs_context
  -> tool_requested
  -> tool_executed
  -> evidence_collected
  -> change_prepared
  -> change_applied
  -> verified
  -> delivered

任意阶段 -> failed / blocked / waiting_user / manual_review_required
```

规则：

1. Analyze/Edit/Run、自由 Agent、Markdown 快路径、恢复和历史续作不能自己结算。
2. 失败是粘性的，只有新的有效证据和显式恢复迁移可以解除。
3. 每轮必须取得新 Evidence、状态推进或明确终态，否则计为 no-progress。
4. 达到恢复预算、相同工具重复预算或相同 Provider 输出预算后直接失败，不能无限“继续生成”。
5. VS Code、CLI 和未来 API 入口只做 Surface Adapter。

### 4.6 Provider 和 UI 边界

- DeepSeek Web、DeepSeek API、OpenAI-compatible API 和其他模型只实现 Provider Adapter。
- native function calling 优先使用结构化 schema；Web 文本工具协议仅是兼容层。
- Provider 输出完整性必须分类为 complete、tool-call、short-intent、truncated、error-page、auth-failed、empty。
- UI 只渲染 append-only 的领域事件，不覆盖前一条阶段总结。
- 用户可见总结说明“完成什么、发现什么、下一步什么”；文件和命令折叠展示，不重复刷屏。

5. 既有项目实现必须说明与主流程的关系，独立任务不得强行寻找主控链路。

### P1-B：代码实现与验证规划

目标：从“模型给代码”升级为宿主可验证的软件工程变更。

实施：

1. 变更前建立目标文件、符号、调用关系和项目规则证据。
2. 由 WorkspaceEdit/ChangeSet 统一写盘，保留 diff、checkpoint 和幂等 operationId。
3. 根据项目自动选择最小有效验证，再扩展到模块测试和项目构建。
4. 编译失败进入 repair contract；GUI/交互式验证进入人工验收，不伪装 exit 0。
5. 最终交付列出文件、关键改动、验证命令、结果和未验证风险。

### P2：架构债务收敛和 Provider 扩展

目标：让能力增长不再依赖超大文件和 DeepSeek Web 特例。

实施：

1. 按架构预算从 `extension.ts`、`agent-loop.ts`、`agentic-loop.ts`、`tool-loop.ts`、`fake-tool-parser.ts`、`deepseek-agent.ts`、`webview.js` 外移职责。

5. 在有可用账号/配置时增加第二 Provider 的真实小任务，但不把 Provider 差异写入 Agent Core。

## 6. 每轮固定迭代算法

每轮只处理一个失败类别：

1. 读取当前 HEAD、05、本文和最近真实报告。
2. 用 Claude Code/Codex 行为写出对标差距和职责所有者。
3. 只复现一次，保存完整日志、成果物和版本。
4. 把失败转成最小 replay，先看到测试失败。
5. 审计同类入口、状态流、协议、恢复和 UI，确定架构修复范围。
6. 修改拥有该事实的核心边界，删除被替代旧逻辑。
7. 运行 focused unit 和 replay。
8. 运行 Extension/Bridge/PA0-PA13/architecture 完整 benchmark。
9. benchmark 通过后提交一个可回滚 commit。
10. 构建精确 commit VSIX，验证 packaged Bridge，安装精确 VSIX。
11. 先跑一个可见短 canary，审计运行日志、Replay、实际产物和 UI。
12. canary 通过才进入 medium/formal；失败则回到第 3 步。

停止规则：

- 同一失败类别连续出现两次，禁止第三次盲跑，必须重新审计架构和 oracle。
- 没有新 Evidence、状态推进或新 fixture 时，不继续让 Provider“再试一次”。
- 用户要求暂停时停止 harness、VS Code 测试窗口和 Bridge 后台进程。
- 确定性门禁通过只表示 regression-safe，不表示真实稳定。

## 7. 测试阶梯

### L0：静态和架构门禁

- TypeScript 编译、lint/diff check、架构预算、边界守卫。
- 禁止新增领域硬编码、重复完成判断和 Surface 业务逻辑。

### L1：Unit

- TaskContract 约束作用域。
- EvidenceRef 不可变与 claim validator。
- 状态迁移、失败粘性、恢复预算。
- Provider 完整性和 ToolCall 归一化。
- QualityPolicy obligation 组合。

### L2：Runtime Replay

必须永久覆盖：

- 工具意图未执行。
- 工具执行后短答。
- Provider 断线、截断、空响应、错误页和登录失败。
- 旧 Bridge/旧 VSIX 接管。
- 重复 continuation 和同一路径重复写入。
- 缺少结论、无终态和 UI 假完成。
- 源码事实与产物不一致。
- “只读源码 + 写新交付物”约束作用域。
- GUI/长运行等待人工确认。

### L3：Headless/仿真

- 使用真实 Agent Core、真实工具和临时工作区。
- Provider 可使用确定性 fixture，但不能绕过状态机。
- 断言文件内容、diff、命令、终态、Replay 和用户事件。

### L4：真实 VS Code + DeepSeek Web

- 使用精确 VSIX、可见浏览器、已登录 cookie 和真实工作区。
- 每次测试使用 `YYYYMMDDHHmm/docs`、`YYYYMMDDHHmm/src` 独立目录。
- 真实任务 prompt 不注入答案或领域固定模板。
- Harness assertion 必须检查任务特定事实，不只检查关键词和文件大小。

### L5：正式项目与竞品对标

- DevSeek 和 Codex/Claude 接收相同用户请求和相同初始工作区。
- 成果物分别保存在带时间戳的独立目录，Codex 目录可以包含 `codex` 标识。
- 由统一 rubric 盲审需求覆盖、项目证据、设计、代码、验证、风险和用户反馈。
- 不把 Codex 产物放入 DevSeek prompt，避免答案泄漏。

## 8. 资格门禁和评分

### 8.1 稳定资格

沿用 05 的最低稳定门禁。同一干净提交必须连续通过：

- 3 个 short canary。
- 2 个 medium integration task。
- 1 个 formal existing-project task。
- 所有报告 Replay 成功、版本匹配、无 P0/P1 错误。

### 8.2 优秀资格

“稳定”不等于“优秀”。优秀资格还必须在同一发布候选系列完成：

- 至少 10 个短任务，覆盖只读、写文档、单文件修改、命令验证和混合约束。
- 至少 6 个中型任务，覆盖不少于 3 种语言或项目形态。
- 至少 3 个正式项目任务，覆盖调查、设计、实现、测试和成果物审计。
- 至少 5 个故障恢复任务，覆盖 Provider、工具、版本、续作和人工验收。
- 至少 2 个与维保/license 无关的项目，证明通用性。
- 0 次假成功、0 个未声明的错误事实、0 个重复副作用、0 个无终态运行。

统一 100 分 rubric：

| 维度 | 分值 | 硬失败条件 |
| --- | ---: | --- |
| 意图和约束 | 10 | 任务类型或禁止项作用域错误 |
| 项目调查和证据 | 15 | 强事实无来源或关键入口遗漏 |
| 设计与集成边界 | 15 | 孤岛设计、与既有主流程脱节 |
| 代码正确性与范围 | 20 | 不编译、越界修改、明显缺陷 |
| 验证与恢复 | 20 | 测试未执行却宣称通过、重复副作用 |
| 交付物事实质量 | 10 | 臆造数值、路径、接口或验证结果 |
| 用户反馈与可追溯 | 10 | UI 假完成、终态和日志不一致 |

优秀资格要求平均分不低于 90，任一正式任务不低于 85，且没有任何硬失败。DevSeek 与 Codex/Claude 的同题结果逐项比较，差异必须转化为规则、fixture 或架构任务，不能只写主观点评。

## 12. 接管红线

- 不得把文件存在、Todo 变绿、Provider 长回答或模型自称完成当作成功。
