# DevSeek 运行形态与界面解耦需求

文档编号：REQ-09
最后更新：2026-06-18
状态：活跃需求审计
用途：确认 DevSeek 不只作为 VS Code 插件设计，而是具备 VS Code、CLI、非 VS Code 图形界面和跨平台运行的产品形态。

## 1. 审计结论

1. DevSeek 当前文档已经强调 Presentation Layer 不能承载业务，但目标描述仍偏 VS Code 插件，需要提升为多入口编程智能体。
2. VS Code 插件应作为 P0 首发入口，因为当前代码和用户体验都在 VS Code 内；但 Agent 能力必须沉入 Headless Agent Core。
3. CLI 交互模式应优先对标 Claude Code 的 terminal-first 使用方式：在项目目录启动、会话式交互、计划模式、权限确认、diff 审查、恢复历史。
4. CLI 不能另做一套 Agent；它必须通过 Surface Adapter 调用同一套计划、权限、工具、Provider、历史任务、记忆和验证。
5. 非 VS Code 图形界面可以作为 P2，以本地 Desktop 或 localhost Web UI 方式承载任务列表、diff、历史、Provider 配置、预览和诊断。
6. Linux / macOS / Windows 跨平台必须成为需求和测试维度，重点处理 shell、路径、换行、文件锁、大小写、浏览器桥接和 WSL 边界。
7. 本轮多入口重构与既有 VS Code 插件实现差异很大，应在 `devseek-multi` 分支开发，main 只接收可验证的阶段性合并。
8. 多入口产品必须有多目标构建矩阵，不能只保留 VSIX 打包路径。

## 2. 对标依据

| 对标对象 | 相关实现 | DevSeek 采用判断 |
| --- | --- | --- |
| Claude Code | VS Code extension 提供图形界面，同时可切换/运行 CLI；CLI 可在任何终端使用；Windows 支持 native 与 WSL 选择 | DevSeek CLI 交互体验优先参考 Claude Code，但保持与 VS Code 插件共享 Agent Core |
| Claude Desktop | Desktop 支持权限模式、计划模式、预览应用和会话恢复 | DevSeek 非 VS Code UI 可承载任务管理、权限、diff、预览，但不作为 P0 |
| OpenAI Codex | CLI、IDE extension、app、cloud 共享 Agent 能力；CLI/IDE 配置层共享；Windows 可 native 或 WSL2 | DevSeek 需要共享配置、Provider、权限和 sandbox 策略，避免每个入口重复实现 |
| GitHub Copilot | CLI 支持交互和 programmatic 模式；cloud agent 可从 IDE、GitHub、CLI、API、MCP 等入口启动 | DevSeek 至少支持 VS Code、本地 CLI、非交互 JSONL，远期再接 GitHub/issue/PR 自动化 |

## 3. 运行形态需求

| 运行形态 | 优先级 | 核心用户价值 | 设计约束 |
| --- | --- | --- | --- |
| VS Code 插件 | P0 | 面向当前 DevSeek 用户，提供 Chat、Inline Chat、File Changes、Problems、Terminal、Selection、WebView 状态流 | 只能作为 Surface Adapter，不直接实现业务规则、权限、Provider、记忆或工具执行 |
| CLI 交互模式 | P1 | 面向终端用户，适合大任务、远程服务器、SSH、脚本前人工确认 | 必须支持 Plan/Edit/Run 模式、权限提示、diff 审查、任务恢复、历史查看、可中断继续 |
| CLI 非交互模式 | P2 | 面向 CI、本地脚本、批处理和自动化验证 | 输出 JSONL 事件、明确退出码、可配置只读/写盘/命令权限、默认不执行高风险副作用 |
| 非 VS Code 图形界面 | P2 | 面向不使用 VS Code 的程序员，提供任务列表、diff、历史、Provider 配置和预览 | 本地优先，可采用 Desktop 或 localhost Web；不得直接绕过 Agent Core 和权限内核 |
| 云端/远程委派 | P3 | 面向 issue/PR/后台任务和团队流程 | 需要独立远程执行环境、安全边界、密钥隔离和审计后再做 |

## 4. 分支开发策略

| 分支 | 用途 | 合并条件 |
| --- | --- | --- |
| `main` | 保持当前稳定 VS Code 插件和已验证发布链路 | 只合入阶段完成、测试通过、文档同步、可回退的变更 |
| `devseek-multi` | 承接 Headless Agent Core、Surface Adapter、CLI、跨平台 adapter 和多构建矩阵重构 | 每个 Phase 都必须保留可运行 VS Code 插件；不能长期破坏主 release loop |
| feature 子分支 | 可选，用于 CLI、PlatformRuntime、BuildProfile 等较小主题 | 合并到 `devseek-multi` 前必须通过对应单元测试和最小 smoke test |

重构期间禁止在 `main` 上直接进行大规模移动、拆分和入口替换。若需要给用户发布 VSIX 修复，应从 main 或稳定 tag 单独处理。

## 5. 显示与功能分离要求

| 层 | 允许做什么 | 禁止做什么 |
| --- | --- | --- |
| Surface | 输入输出、布局、快捷键、终端/TUI 渲染、通知、diff 呈现 | 直接读写 workspace、直接执行终端、直接改 Provider 状态、直接写记忆 |
| Surface Adapter | 把 UI 操作转为 `AgentCommand`，把 `AgentEvent` 转为界面状态 | 携带业务分支、绕过权限、私自拼 prompt |
| Agent Core | Workflow、Plan、Permission、Tool、Provider、Memory、TaskHistory、QualityGate | 依赖 VS Code WebView、DOM、TUI 或 Desktop API |
| Infrastructure | VS Code API、fs、shell、browser、secret storage、MCP、bridge | 反向调用 Surface 业务逻辑 |

## 6. 多目标构建方式

| 构建目标 | 当前基础 | 目标命令形态 | 产物 | 验证 |
| --- | --- | --- | --- | --- |
| Shared/Core | `packages/shared` 已有 `npm run build` | `npm run build --workspace=packages/shared`，后续扩展为 Agent Core shared package | `dist/index.js`、类型声明 | type check、schema 单测 |
| Bridge | `packages/bridge` 已有 `dev/build/start/test` | `npm run bridge:build`、`npm run bridge:start`、`npm run verify:packaged-bridge` | `packages/bridge/dist`、packaged bridge | response extractor、health、packaged smoke |
| VS Code Extension | 已有 `compile/watch/test` 和根 `extension:package` | `npm run compile --workspace=packages/vscode-extension`、`npm run extension:package` | `dist/extension.js`、`.vsix` | extension unit、extension-host、VSIX install |
| CLI TUI | 待新增 | `npm run cli:build`、`npm run cli:dev` | `devseek` bin 或 npm workspace package | 启动、Plan、permission、diff、history smoke |
| CLI JSONL Exec | 待新增 | `npm run cli:exec -- --jsonl ...` 或 `devseek exec --jsonl` | JSONL 事件流、退出码 | machine-readable parser、CI smoke |
| Desktop/local Web | P2 待评估 | `npm run desktop:dev/build` 或 `npm run webui:dev/build` | 本地桌面包或 local web assets | 只在 Agent Core 稳定后加入 |
| 全量验证 | 根脚本已有 `verify`、`verify:artifacts` 等 | `npm run verify:all` 作为目标聚合命令 | 无发布产物 | shared、bridge、extension、cli、cross-platform smoke |

构建矩阵必须区分 dev、test、package、release 四类 profile。任何新增入口都必须能独立构建，也必须能进入全量验证；不能只在某个 UI 手工路径里工作。

## 7. 跨平台需求

| 维度 | Linux/macOS | Windows native | WSL |
| --- | --- | --- | --- |
| Shell | bash/zsh/fish adapter，命令引用和退出码解析 | PowerShell/CMD/Git Bash adapter，转义、编码、执行策略和路径转换 | Linux shell adapter，但 workspace 路径与 Windows IDE/浏览器互操作需显式标记 |
| 路径 | POSIX、大小写通常敏感 | drive letter、反斜杠、大小写通常不敏感、长路径 | `/mnt/c` 与 Linux home 差异必须进入 root profile |
| 文件写入 | POSIX 权限、symlink | 文件锁、CRLF、隐藏/系统属性 | 跨文件系统性能和权限差异 |
| 浏览器/DeepSeek Web Bridge | 本地 Chromium/Chrome/Edge 路径发现 | Edge/Chrome、用户数据目录、杀进程风险 | 浏览器通常在 Windows 侧，bridge 运行位置需要清楚 |
| 验证命令 | npm/pnpm/python/go/cargo 等按环境探测 | 同名命令可能来自 PowerShell、Git Bash、MSYS、WSL | 必须显示 cwd、shell、toolchain 来源 |

## 8. 验收标准

1. 新业务不能直接写入 VS Code WebView 或 `extension.ts`；必须先进入 Headless Agent Core 或 Surface Adapter。
2. VS Code 和 CLI 对同一任务产生一致的 `TaskRunRecord`、权限记录、工具证据、Provider 事件和验证结论。
3. CLI 交互模式至少支持启动会话、计划确认、执行工具、展示 diff、取消/继续、查看历史任务。
4. CLI 非交互模式必须输出机器可读 JSONL，失败时返回非零退出码并保留任务证据。
5. Linux/macOS/Windows native/WSL 至少有 smoke test，覆盖路径、shell、写盘、终端命令、Provider 配置读取。
6. Surface 缺能力时必须显式降级，不能让用户误以为已经完成同等级验证。
7. `devseek-multi` 分支上的每个阶段合并点必须说明 build profile、验证命令、可回退方式和是否影响 VSIX release loop。
8. 多目标构建矩阵至少覆盖 shared/core、bridge、VS Code extension、CLI TUI、CLI JSONL；Desktop/local Web 可在 P2 进入矩阵。
